# 13 · 难度旋钮验收报告（行动方案第四步）

> 这篇回答一个问题：**"难度可以连续调节"这句话，是真的还是我们自己说的？**
>
> **结论：真的，但有三个附加条件，而且不是一开始就真。**
>
> 第一次真跑测出来的曲线是**反的**（刻度 1 比刻度 0 分数还高）。查出五个 bug 修掉之后：
>
> | 证据 | 数字 | 说明 |
> | --- | --- | --- |
> | 端点 F1 | 0.775 → 0.649（Δ=+0.127） | 旋钮确实压低了分数 |
> | 踩雷率 | 0.00 → **0.67** | 模型被诱饵骗的次数涨了 6 倍，**严格单调** |
> | 耗时 | 1.8s → 30.6s（**×17**） | 严格单调，且无判分口径争议 |
> | 单题效果 | sample-0003：0.94 → 0.49 | 单题掉 0.45，最干净的因果证据 |
> | **跨模型分离** | **两条曲线在刻度 2 交叉** | flash 与 v4-pro 的难度排序**反过来**（见 §2.1）|
>
> 但同时有**三个反直觉的发现**：
> 1. **旋钮对"已经很难/已经饱和"的题无效甚至反向**（§1.1）——
>    三道题里两道变难、一道变易，而变易那道在刻度 0 就只有 0.385。
> 2. **旋钮对不同模型作用强度差2.4 倍**：v4-pro 端点降幅 0.308，flash 只有 0.127；
>    且强模型被诱饵骗得更多（踩雷 1.56 vs 0.67）——§2.1。
> 3. **五个旋钮里只有四个在工作**：`variation_k`（改写强度）完全未接线。
>
> 这段过程本身就是产出——**"旋钮可调"不等于"旋钮有效"**，
> 必须有一条能证伪的验收链，否则自欺欺人。

## 0. 怎么读这篇

验收标准来自 [`10-action-plan.md` 3.4 节](./10-action-plan.md)，四条必须同时满足：

| # | 验收项 | 含义 | 怎么测 |结论 |
| --- | --- | --- | --- | --- |
| ① | **结构单调** | 刻度↑时，题目客观上在变复杂（诱饵/伪装/跨函数） | 离线，不需要 API | ✅ |
| ② | **曲线分离** | 刻度↑时，**AI 分数下降**（否则调难度没用） | 真调 LLM | ✅ 端点 / ⚠️ 逐档 |
| ③ | **曲线稳定** | 同档多次采样，离散度在可接受范围 | 真调 LLM，repeat≥3 | ⚠️ 部分 |
| ④ | **跨模型分开** | 不同 AI 的曲线不能是同一条 | 两个模型各跑一遍 | ✅ 交叉 |

> ⚠️ 还有一个隐含的第 0 条：**代码得能编译**。这一条最初没人写进验收标准，
> 结果它成了最大的坑（见 §3）。

## 1. 实测数据

**实验设置**（全部来自真实 HTTP 调用，无一为估算）：

- 模型：`deepseek-flash`（DeepSeek 官方网关）；跨模型验证另跑 `deepseek-v4-pro`（§2.1）
- 样本：`sample-0001` / `0002` / `0003`（3 道独立雷：reentrancy / access_control / tx_origin）
- 每档每样本重复 3 次 → 每档 9 次调用，全 6 档共 54 次
- 判分器：v2（类型 + 定位 + 严重度加权）
- `LLM_MAX_TOKENS=16384`（flash 够用）；**v4-pro 在刻度 5 必须提到 32768**，
  否则 thinking 烧满导致空答案，污染均值（见 §3.5）
- 统计口径：F1 / 精确率取均值 ± 标准差；**踩雷率 = 每次审计平均误报几个诱饵**
- 总花费：flash $0.19 + v4-pro $1.32 = **$1.51**，共 108 次真实调用

### 1.1 均值会骗人：必须分样本看

| 刻度 | sample-0001 (reentrancy) | sample-0002 (access_control) | sample-0003 (tx_origin) |
| --- | --- | --- | --- |
| 0 | 1.00 / 1.00 / 1.00 | 0.40 / 0.39 / 0.37 | 1.00 / 1.00 / 0.82 |
| 1 | 1.00 / 1.00 / 1.00 | 0.36 / 0.40 / 0.37 | 0.82 / 0.82 / 0.32 |
| 2 | 1.00 / 1.00 / 1.00 | 0.88 / 0.40 / 0.89 | 0.32 / 0.82 / 0.82 |
| 3 | 0.99 / 1.00 / 1.00 | 0.86 / 0.86 / 0.86 | 0.82 / 0.82 / 0.82 |
| 4 | 0.94 / 0.94 / 0.91 | 0.85 / 0.34 / 0.85 | 0.32 / 0.82 / 0.32 |
| 5 | 0.94 / 0.81 / 0.94 | 0.54 / 0.30 / 0.85 | 0.82 / 0.32 / 0.32 |
| **Δ(0→5)** | **1.000 → 0.893 ↓** | **0.385 → 0.565 ↑** | **0.941 → 0.488 ↓** |

**三道题里两道变难、一道变易。** 只看均值会得出"旋钮时好时坏"的结论，
分样本看才发现真正的规律：

- **sample-0001（reentrancy）**：刻度 0–2 稳在 1.00（**已经饱和，旋钮推不动**），
  刻度 3 的"伪装"才开始生效（1.00 → 0.93），刻度 5 掉到 0.89。
- **sample-0003（tx_origin）**：效应最清晰，0.94 → 0.49，**掉了 0.45**。
  这道题的区分度最好，诱饵对它有效。
- **sample-0002（access_control）**：刻度 0 就只有 0.385 —— **它一开始就已经很难了**。
  再加诱饵，模型本来就不确定该报什么，多出来的干扰反而让它"乱猜中了一个"，
  F1 反而升到 0.565。

> **这是本轮最有价值的发现，也是一个反直觉的结论：**
> 难度旋钮对**简单题**有效，对**已经很难的题**无效甚至反向。
>
> 推论：**不能用"把题调难"来代替"把题出好"**。如果一道题本身就有区分度
> （模型本来就做不对），再堆干扰只会引入噪声。
> 旋钮应该作用在**"模型本来能做对"的题上**——把那部分题的分数连续压下来，
> 这才是它该干的事。sample-0003（掉 0.45）就是正面案例，
> sample-0001（刻度 0–2 纹丝不动）说明饱和的题旋钮无能为力。

### 1.2 成本与耗时：比分数更稳定的难度信号

| 刻度 | 耗时 | 相对刻度 0 | tokens |
| --- | --- | --- | --- |
| 0 | 1.8 s | ×1.0 | 6,444 |
| 3 | 12.2 s | ×6.7 | 28,601 |
| 5 | 30.6 s | **×17** | 70,935 |

耗时与 token 消耗**严格单调递增**（×17、×11），比 F1 曲线干净得多。
这给了一个重要的备选判据：

> **当分数区分度不足时，可以用"同一道题让模型多想多久"作为难度的客观度量。**
> 它没有判分器口径争议、不受 0/1 边界抖动影响，而且是真花掉的钱
> （$0.19 vs 一次普通跑测 $0.0037）。

这也正好对上 ALE-Bench 的时间轴设定（58.8 分 @1h → 92.1 分 @1w）：
**时间是难度最诚实的载体。**

## 2. 三条验收逐条给结论

| 验收项 | 结论 | 依据 |
| --- | --- | --- |
| ① 结构单调 | ✅ **通过** | 离线 18 项体检全过：诱饵 0→1→2→3→4→6 单调，伪装刻度 3 起、跨函数刻度 4 起 |
| ② 曲线分离 | ✅ **端点通过，逐档不通过** | 端点 Δ=+0.127 超过 0.05 阈值，踩雷率 0.00→0.67；但刻度 2→3 回升，且三题中有两题方向相反 |
| ③ 曲线稳定 | ⚠️ **部分通过** | 同档标准差 0.07–0.29，最大 0.29 偏大；`repeat=3` 偏少。分样本后离散度明显更小（0002 刻度 3 达 0.86/0.86/0.86）|
| ④ **不同 AI 曲线分开**（补测） | ✅ **通过** | 两个模型曲线在**刻度 2 处交叉**：之前 pro 领先 0.19，之后 pro 落后 0.11（见 §2.1）|

**逐档不单调不是旋钮失效**，三个原因（已逐一核对数据）：

1. **均值稀释**：三题平均后方向相反的效应互相抵消（见 §1.1）。
2. **判分器在 0/1 边界抖动**：F1 只有 0.32 / 0.82 / 1.00 这几个高频取值，
   差一个 findings 就跳 0.1 以上。
3. **饱和题推不动**：sample-0001 刻度 0–2 全是 1.00，加旋钮毫无反应。

**真正说明旋钮有效的三个信号**（比 F1 曲线更硬）：
- 踩雷率 0.00 → 0.00 → 0.00 → 0.22 → 0.22 → **0.67**（单调上升，末档 6 倍）
- 耗时 1.8s → 30.6s（×17，严格单调）
- sample-0003 单题 F1 0.94 → 0.49（掉 0.45，单调下降）

## 2.1 补测：不同 AI 的曲线是否分开

验收标准里最后一条是"**不同 AI 的曲线必须分开**"——如果两个模型在难度旋钮上
表现一致，说明旋钮只是给所有模型套了同一层壳，没有区分能力。本轮补跑
`deepseek-v4-pro`（54 次调用，$1.32，0 截断 0 失败）来验证。

| 刻度 | flash F1 | pro F1 | 差 (pro−flash) | flash 踩雷 | pro 踩雷 |
| --- | --- | --- | --- | --- | --- |
| 0 原样 | 0.775 | **0.963** | +0.188 | 0.00 | 0.00 |
| 1 +1诱饵 | 0.677 | 0.863 | +0.186 | 0.00 | 0.11 |
| 2 +2诱饵 | 0.792 | 0.848 | +0.056 | 0.00 | 0.00 |
| 3 +3诱饵+伪装 | **0.895** | 0.789 | **−0.106** | 0.22 | 0.44 |
| 4 +4诱饵+跨函数 | 0.699 | 0.609 | −0.090 | 0.22 | **1.56** |
| 5 +6诱饵 | 0.649 | 0.655 | +0.006 | 0.67 | 1.22 |
| **端点降幅** | **−0.127** | **−0.308** | | | |

**两条曲线在刻度 2 交叉。** 这是比任何相关系数都硬的证据：

- 刻度 0–2：**pro 领先约 0.19**（强模型在简单题上更强，符合直觉）
- 刻度 3–4：**pro 反而落后 0.09–0.11**（旋钮把强模型压下去了）
- 曲线形状秩相关 **ρ = 0.20**（1 = 完全同形）→ 形状显著不同

**pro 的降幅是 flash 的 2.4 倍**（0.308 vs 0.127）。也就是说旋钮对不同模型的
作用强度不一样，这才是"难度可调"真正的价值——**不是给所有人一道同样的难题，
而是能给出一道题，让不同模型各自落在它能力边界上的不同位置。**

更值得注意的是踩雷率：flash 从 0 升到 0.67，pro 从 0 升到 **1.56**（刻度 4）。
pro 被诱饵骗的次数是 flash 的 2.3 倍——**旋钮对"本来就能做对"的模型更有效**，
正好呼应 §1.1 那条推论：旋钮该作用在模型本来能做对的题上。

### 成本与耗时对照（同一批题）

| | flash | v4-pro |
| --- | --- | --- |
| 单档耗时（刻度 0 → 5） | 1.8s → 30.6s | 22.8s → 103.1s |
| 六档总成本 | **$0.19** | $1.32 |
| 每$0.1 买到的降幅 | 0.067 F1 | 0.023 F1 |

**flash 的性价比高 2.9 倍。** 做旋钮标定用 flash 就够，要验证"是否SOTA 也会被骗"
才需要pro。这条结论直接影响后续实验设计：标定阶段不必用贵模型。

> ⚠️ 一个诚实说明：pro 的曲线**逐档并非严格单调**（刻度 4→5 从 0.609 回升到 0.655，
> 踩雷从 1.56 降到 1.22）。所以"pro 降幅是 flash 的 2.4 倍"应理解为
> **端点降幅**对比，不是逐档单调性对比——flash 同样有回升（刻度 2→3）。
> 两者的曲线噪声来源相同（3 道题太小 + 判分器 0/1 抖动），
> 不能把pro 曲线的形状差异解读成"旋钮对强模型有特殊机制"。

## 3. 五个 bug（这一节才是重点）

第一次跑出来的曲线是**反的**。五个 bug，每一个都单独足以让旋钮"看起来在工作、
实际完全没生效"。它们有共同特征：**不报错、不崩、不影响任何已有测试**。

### 3.1 诱饵自曝身份

```solidity
// [decoy] external call looks risky but state is settled first
function decoyPayout(address to, uint256 amt) external { ... }
```

函数名带 `decoy`、注释写着 "looks risky but…"、"already guarded"——
**这等于把答案写在题面上**。模型读完注释就知道这段无害，直接跳过，
从不误报 → 精确率不降 → F1 不降。实测刻度 1 的 F1 甚至**涨了**（0.749 → 0.817）。

**修法**：函数名改业务化命名（`payoutPartner` / `accrueTier` / `setRiskCap` /
`maintenanceMode`），注释改成开发者自用口吻，全代码不出现
decoy / safe / already guarded 任何一处。统计踩雷率改为**按函数名匹配**。

> 教训：**伪装类算子，第一件事是检查它有没有自曝。**
> 这跟"埋雷注释写得越显眼越好"恰好相反——雷要显眼，诱饵必须无害。

### 3.2 诱饵引用了不存在的状态变量

`sample-0001` 的合约里只有 `balances`，诱饵却引用 `partnerShare` / `operator` /
`onlyOwner`。**本机没有 forge，跑 `batch_generate` 时不会发现**，
一旦交到 harness / CI 就是整批样本全废。

**修法**：`ensure_state_decls()` 扫合约体，缺哪个状态变量/moderator 就补哪个声明，
且幂等。

### 3.3 `max_tokens` 写死在函数签名里 ⚠️ 最阴

```python
# 错的写法：默认值在函数定义时求值，import 时就定格了
def __init__(self, ..., max_tokens: int = DEFAULT_MAX_TOKENS):
```

于是 `LLMClient(model=...)` 这种**直接构造**（不走 `from_env()`）完全无视
`LLM_MAX_TOKENS`。命令行明明设了 8192，实际仍按 4096 跑——证据是截断告警里
写着 `输出 4096/4096 token`。

后果就是 doc 12 第 2 节那个 thinking 截断陷阱：代码一长，thinking 烧满预算，
模型返回**空答案 + HTTP 200**，F1 记 0。
**那几个 0 分是假的，是配置没生效，不是模型不行**——这个 bug 最危险的地方在于
它会伪装成"模型能力不足"，直接把结论带偏。

**修法**：签名改 `max_tokens: int | None = None`，在 `__init__` **运行时**读 env。

> 教训：**任何"可被环境变量覆盖"的默认值，都不能在函数签名里写死。**

### 3.4 诱饵模板循环复用 → 同名函数重复定义

模板只有 4 条，刻度 5 要插 6 个，我用 `i % 4` 循环复用 →
`payoutPartner` 和 `accrueTier` 各出现两次 → **Solidity 编译错误**。

**修法**：模板用 `{fn}` 占位，`plan_decoys()` 生成唯一函数名
（`payoutPartner` / `payoutPartner2` / …），依赖声明顺带去重。

**这个 bug 是被新写的静态体检脚本抓出来的**（`run_difficulty_lint.py`），
不是被 forge 抓的——因为本机没 forge。

### 3.5 截断污染均值：3次里有 1 次是假 0，分数凭空掉 0.39 ⚠️ 补跑 `v4-pro` 时才发现

这是 §3.3 那个坑的**二次伤害**，而且更隐蔽。

跑 `deepseek-v4-pro` 刻度 5 时得到：

```
5  6  Y  Y  0.549±0.399  踩雷0.7  127171ms   ⚠️ 本档 1 次疑似截断
   f1_all = [0.7097, 0.0, 0.9362]      ← 中间那个 0 是空答案，不是模型答错
```

同一次采样里另外两次分别打了 0.71 和 0.94。如果直接取均值，
**这个配置问题会把分数从~0.82 压到 0.55，看起来像"最难的一档终于变难了"——
实际上只是 1/3 的样本没答完。** 更糟的是它恰好出现在最高档，
会被当成"旋钮在高难度下特别有效"的证据。

把 `LLM_MAX_TOKENS` 从 16384 提到 **32768** 重跑：

```
5  6  Y  Y  0.936±0.000  踩雷0.0  77172ms   （0 截断）
```

同一个样本、同一档，从 0.549 变成 0.936。**差异全部来自配置，与题目无关。**

> 教训：**截断不是"少算了几分"，而是往均值里掺入了假0。**
> 只要 `truncated > 0`，这一档的均值就不能用——必须调大上限重跑，
> 或者用 `--strict` 直接让它报错退出。
> 扫描脚本现在每档都会打印截断次数，正是为了让这种污染无处可藏。

这也顺带说明为什么本报告坚持**每个数字都要能追到来源**：如果只记"刻度 5 = 0.549"，
这个 bug 会一直藏着，直到别人复现不出来。

## 4. 方法论：为什么值得先写体检脚本

五个 bug 的发现路径值得记下来：

| bug | 谁抓到的 | 反馈耗时 |
| --- | --- | --- |
| 3.1 诱饵自曝 | 人眼读曲线发现反常 | 分钟级（但要记得看曲线） |
| 3.3 max_tokens | 读截断告警的 `4096/4096` | 秒级 |
| 3.2 依赖未声明 | **静态体检脚本** | 秒级 |
| 3.4 同名函数 | **静态体检脚本** | 秒级 |
| 3.5 截断污染均值 | 扫描脚本每档打印 `truncated` 计数 | 秒级 |

两个最危险的都是脚本抓的。结论：

> **对"要反复调参"的算子，先写一个 100 行的静态体检脚本，
> 比反复跑 forge 划算得多。** 它抓的不是逻辑错误，而是"产物是否自洽"——
> 这恰恰是合成数据引擎最容易批量产出、且下游最难排查的一类问题。

再加一条同样重要的：**跑测脚本本身要输出"数据可信度"指标**
（截断次数、失败次数），而不只是分数。没有这两个数字，
一个配置错误就能伪装成难度效果（见 §3.5）。

体检脚本现在查四项：括号配平 / 依赖符号已声明 / 无重名函数 / 无自曝身份。
当前 3 样本 × 6 档 = 18 项全过。

⚠️ 但它**不等于能编译**——真正的裁判仍是 forge 差分验证，本机没有、留 CI。
静态检查只能保证"不会因为低级错误整批报废"。

## 5. 诚实的局限（对外汇报时必须一起说）

1. **样本量小**：3 道独立题、每档 9 次调用。F1 折线不是逐档单调——
   小样本 + 判分器在 0/1 边界抖动 + 饱和题推不动，三个原因叠加（见 §2）。
   正式结论需要扩到 10+ 样本、`--repeat 5`。
2. **只测了两个模型，且同厂同构**。`flash` 与 `v4-pro` 都来自 DeepSeek，
   共享训练谱系。跨模型分离已在同厂内验证（§2.1曲线交叉），
   但**跨厂的分离度仍是空白**——正式论文需要补一个第三方模型
   （如 Qwen / GLM / Claude）才能说这是普适现象。
3. **旋钮对已饱和的题无效**（§1.1）。sample-0001 在刻度 0–2 纹丝不动，
   刻度 3 的"伪装"才起效。**难度旋钮不是万能钥匙**——对本来就没区分度的题，
   它救不回来。
4. **踩雷率绝对值仍低**（flash 每审计 0～0.67 次误报）。诱饵有效，
   但还没把模型逼到"大量误报"的程度——刻度 5 还可以更狠
   （见 §6.4）。注意 v4-pro 的踩雷率高得多（最高 1.56），
   说明**当前诱饵对弱模型仍然偏温和**。
5. **改写强度旋钮（`variation_k`）完全未接线**。它需要 LLM 调
   `VariationOperator` 产生语义保持改写，当前 `apply_difficulty` 只记录标记不执行，
   扫描表里如实显示"改写xN(未接线)"。**这意味着刻度 2–5 的实际难度比标称的低**——
   四个旋钮里只有三个真的在工作。
6. **只验证了 Level 1（Detect）**。Level 2（Exploit）/ Level 3 是否也有
   可调的连续难度，尚未验证。
7. **未过 forge 差分验证**。静态体检（18 项）只能保证"不会因低级错误整批报废"，
   真正的编译/行为正确性仍需 CI 上的 forge。

## 7. 复现

```shell
# 离线：结构单调性 + 静态体检（不需要 API key）
py run_difficulty_sweep.py
py run_difficulty_lint.py

# 真跑 flash：分两批（单批 ≤10 分钟，脚本会逐档落盘，中断也不丢已完成档位）
py run_difficulty_sweep.py --audit --repeat 3 --levels 0,1,2,3 \
   --samples sample-0001,sample-0002,sample-0003 --model deepseek-flash --out results_diff_A.json
py run_difficulty_sweep.py --audit --repeat 3 --levels 4,5 \
   --samples sample-0001,sample-0002,sample-0003 --model deepseek-flash --out results_diff_B.json

# 真跑 v4-pro：单档要 5-10 分钟（超工具上限），必须按样本拆，再合并
$env:LLM_MAX_TOKENS = "32768"   # 16384 在刻度 5 会截断，污染均值（见 §3.5）
py run_difficulty_sweep.py --audit --repeat 3 --levels 3 --samples sample-0001 \
   --model deepseek-v4-pro --out results_pro_L3_s1.json
# ...对sample-0002 / 0003 各跑一次，然后：
py run_difficulty_analysis.py --merge "results_pro_L3_s?.json"

# 合并分析 + 验收判定 + 跨模型分离
py run_difficulty_analysis.py
py run_difficulty_analysis.py --compare

# 回归自测
py run_offline_smoke.py && py run_implementation_smoke.py \
  && py run_difficulty_lint.py && py run_dummy_check.py
```
