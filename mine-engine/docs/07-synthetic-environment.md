## 0. 先建立一个判断标准：好环境要满足哪四条

AWM 论文给出的四条硬性要求，是所有合成环境工作的验收线：

| 要求 | 含义 | 我们现状 |
|---|---|---|
| **Executable 可执行** | Agent 真跑工具、拿到真实观测，不是模型脑补 | ✅ Foundry 真编译真测试 |
| **Diverse 多样** | 十几个环境会过拟合，要成百上千 | ❌ 7 个样本，无多样性度量 |
| **Resettable & Parallelizable 可重置可并行** | 在线 RL 要快速重置 + 大量并发实例 | ⚠️ 固定 seed 可复现，但无并发/隔离设计 |
| **Reliable reward 可靠奖励** | 环境必须自己能判定成败 | ✅ 差分验证（FoundryDiff） |

**四条里我们稳了两条，弱了两条。** 后面所有改进都围绕这两条。

再叠加综述的**环境四维质量**（正确性 / 多样性 / 复杂性 / 忠实度），得到一张体检表：

| 维度 | 论文里的做法 | mine-engine 现状 | 判定 |
|---|---|---|---|
| **正确性 Correctness** | 沙箱执行 + 单元测试验证可解性 | FoundryDiff 编译+测试差分 | ✅ 强 |
| **多样性 Diversity** | embedding 去重 + 类别上限防崩塌 | 无 | ❌ 缺 |
| **复杂性 Complexity** | 工具依赖图复杂度 / 计划长度分档 | 手填 difficulty 字段 | ⚠️ 弱，已加 IRT 但未接入生成 |
| **忠实度 Fidelity** | 与参考系统一致性对比 / 感知分布相似度 | 无 | ❌ 缺，且是我们最大的软肋 |

**这张表就是本文件的主线。** 正确性是我们唯一的强项，而它恰恰是四条里最成熟的
（综述原话：正确性的评估方法已相当成熟，多样性/复杂性/忠实度的定量评估仍处于早期）。
换句话说：**我们做出了最容易的那一维，难的三维基本没碰。**

## 1. AWM 的五阶段流水线，和我们的四组件一一对应

AWM 把每个环境建模成 POMDP，拆成五类被严格合成的组件。对照如下：

```
AWM                                    mine-engine / AuLE
─────────────────────────────────────────────────────────────
① Scenario synthesis   场景合成     ←  domains.py 的赛道/场景定义（3 条赛道）
② Task synthesis       任务合成     ←  instruction.md（detect / exploit 两种模式）
③ Database synthesis   状态后端     ←  合约源码 /（未来）账套 SQLite     ★ 差距最大
④ Interface synthesis  工具接口     ←  Harbor MCP / 命令行工具           ★ 我们几乎没有
⑤ Verification synth   验证逻辑     ←  FoundryDiff + report_score_v2     ✅ 我们最强
```

**③ 状态后端**是 AWM 敢说自己可靠的原因：环境平均 18.5 张表、129 条样本记录、1,984 行代码，
状态转移发生在**真实 SQLite 上**，不是 LLM 脑补的。论文原话：

> code-driven and backed by databases，提供了比 LLM 模拟环境更可靠、更一致的状态转移。

我们目前的状态后端是「一份 Solidity 源码」，比 SQLite 更硬（还能编译能跑测试），
**这一点不比 AWM 差**。但扩展到审计三条赛道时，我们必须自己造状态后端：
- 企业审计 → 三表 + 凭证链的 SQLite（**必须真做**，不能让 LLM 生成数字）
- 国家审计 → 资金流 DAG + 法条库
- 审计师 → 底稿 + 证据链

这正是 `engine/adapters/domains.py` 里 adapter 契约要补的第一件事：**每个赛道必须自带一个
可执行状态后端，不能只给一段文本描述。** 这是从 AWM 学到的最重要的一条。

**④ 工具接口**我们基本是空白。AWM 每个环境平均暴露 35 个 MCP 工具，
Agent 通过原子 API 操作数据库。我们现在的出题是「给一份代码，写一份报告」——
**没有工具交互，就没有过程观测，也就拿不到过程指标**（见 08 号文档）。
改进方向：审计赛道天然适合 MCP 化（查凭证 / 对账 / 抽样 / 函证 / 查法条），
这反而比合约赛道更容易做出工具环境。

## 2. 三件我们必须补的工程件

### 2.1 自我修正循环（Self-Correction Loop）

AWM 最值得抄的一条，成本低得离谱：

> 组件生成后立即执行，遇到 runtime error 就触发 LLM 重生成。
> **平均 1.13 次迭代即可修复**，各阶段成功率 > 85%。

1.13 次——**几乎一次就过**。这意味着「生成 → 执行 → 报错 → 重生成」这个循环
是整个流水线能扩到 1,000 个环境的关键，而不是什么高深算法。

**我们现在的做法**：`FoundryDiff` 验证失败就丢弃这个样本，重新抽样。
**应该改成**：把编译/测试的错误信息（forge 的 stderr）喂回 LLM，让它修自己的埋雷代码。

改造点很小，收益很大：
```
现在：generate → validate → 失败 → 丢弃（浪费一次 LLM 调用）
应该：generate → validate → 失败 → {stderr + 源码} → LLM 修复 → validate → ...（最多 N 轮）
```
预期把算子成功率从「看运气」提到 AWM 同款的 >85%。
这是**投入产出比最高的一个改动**，半天能写完。

### 2.2 多样性度量（Diversity）

AWM 的做法：场景/schema/工具集都用 embedding 算语义多样性，并设**类别上限**，
防止池子崩塌到电商等少数主导类型。论文 Figure 明确展示了"类别覆盖随环境池单调上升"。

综述也列了同一手段：**把所有任务转成向量，看是均匀分布还是扎堆在某个角落。**

**我们完全没有这一步。** 7 个样本全是 reentrancy / tx_origin / access_control 三种雷，
这就是典型的 mode collapse。

落地方案（已实现在 `engine/analytics/env_quality.py`）：
- `diversity_score(tasks)` —— embedding 余弦 + 最远点采样估计覆盖度；无 embedding 时降级为
  **结构性指标**（算子组合、雷型分布、代码结构哈希、难度分布的熵）
- `category_cap_check(tasks, cap)` —— 单类别占比超上限就报警
- `dedup_by_embedding(tasks, threshold)` —— 生成期去重，防止池子注水

**关键设计**：不依赖 embedding 也能跑。因为对我们这种符号合成的环境，
结构性指标（雷型组合、算子序列、CFG 形状）比 embedding 更准，也不需要额外花钱调用模型。

### 2.3 混合判分（Hybrid Verification）

这是 AWM 论文里结论最干净的一处。三种判分模态的对比：

| 模态 | 有轨迹理解 | 有 DB 证据 | 结论 |
|---|---|---|---|
| LLM-only（纯模型判） | ✅ | ❌ | 会幻觉，无 grounding |
| code-only（纯代码判） | ❌ | ✅ | 环境有缺陷时很脆 |
| **code-augmented（代码证据 + 模型判）** | ✅ | ✅ | **最佳完成率与可靠性** |

**这条直接纠正了我之前的一个判断。** ALE 论文强烈反对 LLM-as-judge（因为长任务上
judge 与人工一致率崩塌），我据此在文档里把模型判分基本否掉了。
但 AWM 的对照实验说明：**不是"能不能用 LLM 判"，而是"LLM 判的时候有没有 grounded 证据"。**

修正后的立场：
- **判定权必须在代码**（DB 状态差分 / 编译测试），这点不变
- 但**在代码证据之上**，可以用 LLM 做语义层的补充判定（比如审计结论是否与证据自洽）
- 混合判分对**合成环境本身不完美**（约 4% 环境错误率）尤其重要——纯代码判会在这 4% 上翻车

对应到我们：`report_score_v2` 是纯代码判。下一步加 `hybrid` 开关：
代码先给出结构化证据（命中了哪些雷、定位 IoU、严重度），
再让 judge 只在这一小片证据上做语义判断（结论是否与证据自洽）。
**judge 不看全量轨迹，只看代码提供的证据摘要**——这样就避开了 ALE 指出的长轨迹 judge 崩塌问题。

## 3. 综述给的分类：我们站在哪一格

中科院自动化所综述把环境自动化合成分为两大流派、六条路径：

```
符号合成（代码规则驱动，可验证）
├─ 任务驱动合成     把静态数据集包装成可交互环境
│                    → SWE-Gym（GitHub 仓库 + 修复方案打包成 Docker）
│                    → SWE-smith（多智能体分工：环境构建者/单测创建者/问题陈述者）
│                    → AgentScaler（~3 万个 API 包装成工具环境）
│                    优势：复用现有数据质量    劣势：受限于原始数据覆盖
│
├─ 真实世界驱动合成  把真实系统简化映射成虚拟环境
│                    → AgentSynth（长任务拆子任务，用"信息不对称"降成本）
│                    → OSWorld-MCP（GUI 操作 + MCP 工具融合）
│                    → AutoWebWorld（有限状态机建模网站状态转移）
│                    → AI Gamestore（从 Steam / App Store 抓真实游戏）
│                    优势：高度真实            劣势：工程量大
│
└─ 从零合成         完全靠生成模型，无需真实世界输入  ★ 我们在这
                     → AutoForge（先建工具依赖图，再生成多工具工作流）
                     → LOGIGEN（"前向逻辑推演"，架构师 Agent 把规则编译成物理环境）
                     → InfiniteWeb（轻量规格 → 完整网站 + 任务 + 评分逻辑）
                     → gg-bench（随机采样发明全新双人游戏规则，避免训练污染）
                     优势：理论上无限扩展      难点：逻辑自洽 + 执行正确

神经合成（神经网络直接学环境动态 = 世界模型）
├─ 像素级  → DIAMOND（扩散模型学 Atari 画面） / NeuralOS / Cosmos
├─ 词语级  → WebDreamer（LLM 当网页世界模型） / Code2World（HTML 表示 GUI 状态）
└─ 潜在表示级 → I-JEPA / V-JEPA 2 / DINO-WM
```

**我们是「从零符号合成」**——不需要真实数据输入，靠程序化埋雷凭空造题。
综述给这一档的评价很准确：

> 终极优势是理论上无限的扩展性，难点是如何保证**自动生成内容的逻辑自洽性和执行正确性**。

而我们恰好用**差分验证**解决了这一档的最大难点——埋的雷是否真的、是否就是这次埋的，
靠 `forge test` 的前后对比证明，不靠 LLM 自觉。

**这一点应该写进论文叙事里**：我们不是"又一个 benchmark"，
我们是**从零符号合成路线在审计领域的第一个可执行实例**，并且用差分验证解决了该路线的核心难点。

综述还特意点了一条跟我们高度同构的工作：**gg-bench 用随机采样发明全新游戏规则，
避免训练数据污染。** 这就是我们"现出题抗污染"思路的同类证据，值得引用。

## 4. 最该警惕的一条：忠实度（Fidelity）

综述定义：忠实度追问的是"**任务的完成方式是否符合真实逻辑**"。原话举例很锋利：

> 一个软件工程环境里的任务，即使技术上可以运行，如果它的 bug 模式与现实项目中的
> bug 完全不同，这个环境就缺乏忠实度。

**换成我们的场景**：一个合成的智能合约，即使能编译、能触发重入、能拿到 POC，
如果它的代码风格、命名、业务语义跟真实链上合约完全不同，
那我们测出来的分数能不能外推到真实审计？——这就是忠实度问题，而我们**完全没有度量**。

这是埋雷引擎最深的风险：**在合成题上刷分，不等于在真实审计上变强。**
AWM 自己也有同样的局限：合成环境缺真实 API 的噪声、延迟、失败模式，
且**混合训练（合成 + 真实 API）未探索**。

我们能做的（也是别人做不到的）：
1. **现实锚定集**：拿一批真实历史漏洞（如 Code4rena / 审计报告的公开发现）作为**只读锚点**，
   不参与出题，只用来算「合成题 ↔ 真实题」的分布距离（雷型分布、代码复杂度、业务语义）
2. **跨域迁移检验**：在合成题上训练/调优的 prompt 或策略，是否在真实题上同样有效？
   如果合成题分数涨、真实题分数不动，说明忠实度崩了
3. **忠实度作为一个显式指标写进每份评测报告**，跟准确率并列

**这可以直接变成一个科研点**（见 05-ideas 的 I9）。

## 5. 规模化时会被卡住的地方（提前记下）

AWM 在 1,000 环境规模上暴露的问题，我们迟早也会撞上：

- **Blocked task rate（任务不可解率）**：AWM 把它当 RL 信号可靠性的关键指标，
  做到 < EnvScaler 的 1/3。我们目前**完全没有这个指标**——
  一道题如果连黄金解答都跑不通，它就是废题，必须被检出并剔除。
- **环境错误率 ≈ 4%**：AWM 承认仍有 4% 的环境有问题，靠混合奖励 + 重生成缓解。
  我们的对应物是「埋雷成功但验证不稳定」的样本，也应该有个检出率。
- **并行与状态隔离**：AWM 假设可跑 1,024 个并行实例。我们想在远程服务器
  （ubuntu@43.143.231.106）批量跑，需要每个实例独立的 workspace + 固定 seed。
- **成本—质量 frontier 未研究**：AWM 自己也承认没研究「生成成本 vs 最终性能」。
  这是我们可以补的空档：埋雷引擎的成本是可控变量（用哪个模型埋、重试几次），
  把「每题成本 vs 该题区分度」画出来，是一条很干净的消融实验。

## 7. 一句话总结

**AWM 证明了"全合成 + 代码驱动 + 状态后端 + 差分验证"这条路能规模化到 1,000 个环境，
而且训练出来的 Agent 能 OOD 泛化到三个公开基准。**

我们的架构和它在骨架上是同构的（都是符号合成、都有状态后端、都用差分验证），
而且我们在**抗污染**上比它更强（现出题 vs 静态池）。
差距在于它补齐了三件工程件——**自我修正、多样性度量、混合判分**——
而这三件恰好都不难，是"知道就能做"的东西。

**接下来最值得做的三件事：抄自我修正循环、接上多样性度量、把忠实度做成显式指标。**
