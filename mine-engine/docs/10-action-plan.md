## 第 0 章 · 先看一个比喻，后面全靠它

**传统 benchmark 像一套「历年高考真题」。**

题一公开，培训机构就把答案编进教材，学生背下来考 700 分——
但这个分数**不能说明他会做题**，只能说明他见过这道题。
这就是行业里说的 **benchmark 腐烂**，而且是**一发布就开始烂**。

**我们做的是另一件事：一台「每次考试现场出题的机器」。**

不是出好了给你，而是**你进考场那一刻，机器才当场写卷子**——
而且它写的每道题，都当场自己验算过一遍，确认"这题确实有这个问题"。
题没公开过，也就**无从背起**。

一句话：**别人是"出卷老师"，我们是"会自己出卷的考试院"。**

## 第 1 章 · 一道题的一生（全文唯一例子，务必看懂）

下面所有内容都会回到这个例子。代码是仓库里真实的文件，不是编的。

### 1.1 第一步：先写一份「好代码」

`datasets/sample-0001/clean/Vault.sol` —— 一个存钱的保险箱：

```solidity
function withdraw() external {
    uint256 amount = balances[msg.sender];
    require(amount > 0, "no balance");

    balances[msg.sender] = 0;                        // ① 先记账：把你的余额清零

    (bool ok, ) = msg.sender.call{value: amount}(""); // ② 后给钱：真的把币转给你
    require(ok, "transfer failed");
}
```

**为什么这样写是安全的？** 因为**先把账记了，再给钱**。
就算收款方是个坏蛋，收到钱后立刻又来取一次——
账上已经是 0 了，取不到第二次。

### 1.2 第二步：埋雷——只移动一行

`datasets/sample-0001/planted/VaultPlanted.sol`。我们做的事是：
**把第 ① 行挪到第 ② 行后面。** 就这一行，别的全不动。

```solidity
function withdraw() external {
    uint256 amount = balances[msg.sender];
    require(amount > 0, "no balance");

    (bool ok, ) = msg.sender.call{value: amount}(""); // ② 先给钱
    require(ok, "transfer failed");

    balances[msg.sender] = 0;                        // ① 后记账  ← 雷在这里
}
```

现在坏蛋收到钱后可以**立刻再调用一次 withdraw**——
因为账还没记，系统以为他还有钱，**可以无限取**。这就是**重入漏洞**。

> 💡 **这就是"埋雷"的全部含义**：在好代码上做一个**极小、精确、已知**的破坏。
> 雷在哪、是什么类型、严重到什么程度——**我们全都知道**，因为是我们自己埋的。
> 这一点极其重要，它是后面一切的基石。

### 1.3 第三步：自证清白——差分验证

光说"我埋了雷"不够，得证明。做法是**把两份代码都跑一遍测试**：

| | 健康版 | 埋雷版 |
|---|---|---|
| 正常取钱 | ✅ 通过 | ✅ 通过 |
| 坏人连续取钱 | ✅ 被挡住 | ❌ **钱被取光** |

**两份代码只差一行，运行结果一个挡住一个被抢** →
铁证：这个漏洞**确实是这一行造成的**，不是代码本来就有的。

这一步叫**差分验证**，是我们整个项目最值钱的东西——
**它让我们可以在没有专家、没有人工标注的情况下，自动生成"标准答案"**。

### 1.4 第四步：拿去考 AI

把埋雷版代码发给 AI，问："这段代码有什么安全问题？"

AI 的回答被整理成这样（我们的判分格式）：

```json
{"findings": [
  {"vuln_type": "reentrancy", "function": "withdraw",
   "line": 26, "severity": "critical", "evidence": "..."}
]}
```

拿它跟**标准答案**比对。标准答案是埋雷时自动生成的，长这样
（`datasets/sample-0001/meta.json` 的真实内容，不是编的）：

```json
{"vuln_type": "reentrancy", "swc": "SWC-107", "severity": "critical",
 "location": {"function": "withdraw", "start_line": 19, "end_line": 31},
 "operator": "ReentrancyInjector", "seed": 42}
```

比对三个维度算分：**找到了吗**（recall）· **指对位置了吗**（定位 IoU）·
**严重程度说对了吗**（severity）。

> 💡 **注意 AI 报的是第 26 行，标准答案是 19–31 行，它算命中吗？算。**
> 这里有一条我们自己定的规矩：**判分不能比标准答案的标注粒度更严。**
> 标准答案只标到"函数级区间（19–31 行）"，那 AI 只要报在这个区间内就算指对位置。
> 反过来，如果我们要求 AI 必须精确报到第 26 行，那就是**用我们没有的信息去扣分**——
> 这个坑上一版真的踩过（判分器一度把位置分算成 0.08，等于冤枉了答对的模型）。

> 💡 注意标准答案里的 `"seed": 42`。**同一个 seed 永远生成同一道题**，
> 这就是"可再生"的含义——别人可以完整复现我们的每一道题，
> 而且**就算全部公开也不怕被背**（因为题是现场生成的，不是从题库里取的）。

### 1.5 第五步：**问题来了——全班都考 100 分**

这是我们现在的真实处境：

| 考试 | 结果 |
|---|---|
| Level 1（找漏洞） | 早期 qwen 三轮 **F1 = 1.000**（仅 4 道独立题，已饱和）；<br>真实 DeepSeek 跑测 flash=**0.730** / pro=**0.871**（[doc 12](./12-真实模型接入与踩坑记.md)，7 样本） |
| 数据集规模 | 目录 **7** 个，但**独立题只有 4 道**（0001/0002/0003/0004），<br>另 3 个是同一批题的 LLM 改写变体（`*-v1`） |
| 环境体检 | 多样性 **0.3665**、复杂性 **0.3673**，另外两维**没法测** → 综合 **weak** |

**"全班都考 100 分"意味着这张卷子没有区分度——它不是一张好卷子。**

> ⚠️ **这里必须说实话，不能自己骗自己：独立题只有 4 道。**
> 4 道题上考满分，说明不了任何事——也许只是这 4 道太简单。
> 所以"题太少"和"题太简单"是**同一个问题**，
> 而第 3 章第四步的**难度旋钮恰好同时解决这两个**（见 3.4 节末尾）。

这就是这份方案要解决的问题，也是我们目前**唯一的真问题**。
下面所有工作，都是为了让这张卷子重新变得"能把人分开"。

## 第 2 章 · 三个老师各教了我们一件事

我调研了三个标杆。它们**名字很像但完全不是一回事**，别搞混：

| 名字 | 一句话 | 教我们的事 |
|---|---|---|
| **Harbor** | 一个"跑考试的插座" | 试卷和答案要分袋密封 |
| **ALE** | 一套超难的专家题 | 不许考生自己给自己改卷 |
| **ALE-Bench** | 一套算法竞赛题 | **别用满分制，用举重制** |

### 2.1 Harbor 教我们：试卷袋和答案袋要分开

> **比喻**：高考试卷袋和答案袋是分开密封的，答案袋在考完前谁也不能拆。

Harbor 规定一道题必须打包成三样东西：

```
题面（给 AI 看的）    ← 可以公开
环境（代码 + 依赖）    ← 可以公开
答案 + 判卷程序        ← 单独放，AI 看不见   ← 关键
```

**我们做到了吗？做到了。** 上一轮写的 `run_harbor_export.py` 就是干这个的。

**但 Harbor 还有一条我们没做**：
> 一道题合并前，必须验证两件事——
> **① 标准答案能拿满分；② 交白卷必须得 0 分。**

第 ② 条听起来像废话，其实是最容易翻车的地方：
**如果一道题"什么都不答"也能得高分，那它就是一道废题。**
我们现在**只有 1 道诱饵题（sample-0004）**，没有系统地查过这件事。

### 2.2 ALE 教我们：能代码判的，绝不用 AI 判

> **比喻**：不能让考生自己给自己改卷——他会给自己打满分。

ALE 的铁律是：**判分权必须交给程序，不交给模型**。
因为模型判分会"老好人"（都给高分）或"幻觉"（编造没发生的事）。

**我们做到了吗？做了一半。** 我们的判分是代码算的，这很好。
但 ALE 还有一条**"先卡资格，再评质量"**，我们只做了一半：

```
Gate 1  输出能解析吗？        → 不能 = 0 分     ✅ 我们做了
Gate 2  攻击代码能编译吗？    → 不能 = 0 分     ❌ 没接
Gate 3  攻击代码真跑了吗？    → 跑了但失败 = 0  ❌ 没接
──────── 过了关才评质量 ────────
```

打个比方：**现在相当于"交了作文就给分，还没查他有没有真的去实验室做实验"。**

> ⚠️ **先说清楚一个硬约束，别到动手时才发现：Gate 2/3 需要 `forge`（以太坊测试工具），
> 本机没装，所以这一步现在跑不了。** 两条路：
> - **A.** 装 forge（或上远程服务器）—— 才能真正接上 Gate 2/3
> - **B.** 先只做 Gate 1 + 白卷检查（第 3 章第二步），这两件本机就能跑
>
> 我的建议是 **先 B 后 A**：白卷检查不需要 forge，且性价比更高（见 3.2 节）。
> Gate 2/3 属于"锦上添花"，不是当前瓶颈——**当前瓶颈是全班 100 分，不是判分不够严。**

### 2.3 ALE-Bench 教我们：别用满分制，用举重制 ★ 最重要

> **比喻**：
> **跳高**有世界纪录，人类跳不过 2.45 米，这个项目会到顶；
> **举重**没有顶——你永远可以再加 2.5 公斤。
>
> 百分制考试是跳高：**一旦大家都考 100 分，这场考试就死了。**
> 举重是另一种设计：**分数永远有上升空间，永远能分出高下。**

ALE-Bench 用的是举重制：题目是那种"最优解算不出来"的问题
（比如给 1000 个快递订单安排路线），所以**你可以永远做得更好一点**。

它用真实数字证明了这条路的威力——同一批题，只改**给多少时间**：

| 给的时间 | 1 小时 | 几小时 | 几天 | 1 周 |
|---|---|---|---|---|
| 分数 | 58.8 | 77.7 | 87.6 | **92.1** |

而且它**同时报花了多少钱**：

| 方案 | 分数 | 每题花销 |
|---|---|---|
| 便宜方案 | 905 | **$3.25** |
| 贵方案 | **1879** | **$100.33** |

> ⚠️ **贵 30 倍只换来 2 倍分数。如果只看分数，你会以为贵的方案完胜。**
> 但看完成本表，答案取决于你有多少钱。**只报分数不报成本，是评测报告里最常见的失真。**

**对照我们自己——这条我们一条都没做到：**

1. 我们的"打穿"测试是**成功/失败二值**（要么打穿要么没打穿），不是连续分
2. 我们**不记时间**
3. 我们**不记钱**

### 2.4 三个坐标串成一条流水线

```
第1章的埋雷  →  Harbor 打包  →  ALE 定判分纪律  →  ALE-Bench 定分数形态
（怎么生题）     （怎么交付）     （怎么判才不作弊）    （怎么判才不封顶）
```

## 第 3 章 · 方案：四步走

按**性价比**排序，不是按重要性。每一步都写清楚：做什么 / 为什么 / 验收标准 / 工作量。

---

### 3.1 第一步 · 给每次考试记账（时间 + 钱）　⏱ 半天

> 🔴 **上一版我说这一步 1 小时、风险无。这是错的，已修正。**
> 我原以为 `openended.py` 写好了就只差接线，去读了代码才发现：
> **`engine/llm/client.py` 的 `chat()` 只返回回答文本，把 API 响应里的 `usage` 字段整个丢掉了。**
> 没有 token 数，成本就是无米之炊——不是接线，是要**先改客户端**。

**做什么**（三小步，缺一不可）：

1. **改 LLM 客户端**：让 `chat()` 把 API 返回的 `usage`（输入/输出 token 数）一并带出来
   —— 这是**必须第一步做**的，否则后面两步都无从谈起
2. **建一张单价表**：每百万 token 多少钱，按模型名查（不同供应商价格差 10 倍以上）
3. **接线**：`run_benchmark.py` 记录 wall-clock 秒数 + 按单价表算钱，写进结果文件

**为什么**（回到第 1 章的例子）：

> 两个 AI 都在那道重入题上拿了 90 分。
> A 用了 **3 分钟 / 2 分钱**；B 用了 **1 小时 / 30 块钱**。
> **谁更强？**
>
> 只看分数——平手。看完这两列——如果你是甲方，你每天要审 10 万个合约，
> A 比 B 好得多。**没有这两列，这个问题根本答不出来。**

> ⚠️ **成本的口径要特别注意，我上一版写错了。**
> 我原来写的是"记录每次调用花了多少钱"——**这个口径不对**。
> 小红书 Muse 团队（InfoQ 访谈）给过正确口径：
> **应该算"每成功一道题的成本"（cost per solved task）**，
> 分子要把**重试、升级配置、验证器开销**都算进去，分母**只算做对的题数**。
> 原话："一个便宜的配置，如果需要重试三次再由人改一遍，**其实它并不便宜**。"
>
> 差别有多大？看这个例子（4 道题）：
>
> **公式：每成功一题的成本 = 每题成本 ÷ 命中率**
>
> | 模型 | 每题成本 | 做对 | **每成功一题的成本** |
> |---|---|---|---|
> | A | $0.03（只调 1 次） | 1/4 道（25%） | $0.03 ÷ 0.25 = **$0.120** |
> | B | $0.09（调 3 次重试） | 4/4 道（100%） | $0.09 ÷ 1.00 = **$0.090** |
>
> **只看每题成本会以为 A 便宜 3 倍，按成功任务算其实是 B 便宜。**
>
> ⚠️ **本版修正**：上一版这一格写成 `$0.0375`，是把"每题成本 $0.15"直接除以 4 道题了。
> **0.15 是每题的成本，不是 4 道题的总成本**——总成本是 0.15 × 4 = 0.60，
> 每成功一题是 0.60 ÷ 4 = **0.15**，不是 0.0375。
> 按错误的算法会得出"B 划算 3 倍"的结论，实际上原数字下 **A 更便宜**。
> 为了让"重试多反而便宜"这个真实的反转成立，上表把 B 的调用次数调成 3 次。

**验收标准**（做完一眼就能看出成没成）：

```bash
py run_benchmark.py --repeat 3
```
输出的 `results_benchmark.json` 里，每个模型多出这些列：
```json
{"model": "qwen3.8-max", "f1": 1.0, "wall_ms": 4210,
 "tokens_in": 3820, "tokens_out": 410,
 "cost_usd": 0.031, "cost_per_solved_usd": 0.031}   // 全对时两者相等
```
**并且 `cost_usd` 不能全是 0 或全是 null** —— 全 0 说明第 1 小步没做成。

**工作量**：约半天（第 1 小步约 1 小时，第 2 小步查单价表约 1 小时，第 3 小步约 1 小时）。

**风险**：低，但有两个真实坑：
- **不同供应商返回的 `usage` 字段名可能不一样**（有的叫 `prompt_tokens`，有的叫 `input_tokens`），
  要兼容；万一某个供应商压根不返回，就如实记 `null`，**不要填 0 假装算出来了**
- 单价会变，单价表要能改，不能写死在代码里

### 3.2 第二步 · oracle + dummy 检查（防伪检查）　⏱ 半天

> 💡 **这一步行业里早有标准名字，我们以后统一用，别自己造词：**
> - **oracle check** —— 跑"标准答案"，必须拿满分
>   （Terminal-Bench 里就是 `harbor run --agent oracle`）
> - **dummy check** —— 交白卷，必须拿 0 分
>
> 而且 Terminal-Bench 官方 README 要求 **oracle 要跑 5 次**，
> 确认题目是稳定的、不是这次能过下次过不了。
> **我们之前不知道这两个词，自己做的时候起了别的名字——现在对齐。**

> 🔴 **上一版我把诱饵题的验收标准写反了。** 我写的是 `sample-0004 白卷 0.00 ✅`，
> 实际上**诱饵题交白卷应该得满分**——因为诱饵题里根本没有雷，
> "什么都不报"恰恰是正确答案。已实测确认（数字见下方表格）。
> 这也说明一件事：**防伪检查必须先分清题目类型，否则会误杀好题。**

**做什么**：对数据集里每一道题，自动生成三种答案跑一遍判分：

| 检查项 | 普通题（有雷） | 诱饵题（没雷） |
|---|---|---|
| **① 白卷**：什么都不报 | 必须 **0 分** | 必须 **满分** ← 注意符号是反的 |
| **② 标准答案**：照抄埋雷记录 | 必须 **满分** | 必须 **满分** |
| **③ 反向白卷**：乱报一个不存在的漏洞 | 应 **低分** | 必须 **0 分** |

**实测过一遍的当前结果**（已跑通，不是设想）：

```
sample-0001（普通题）
  白卷            -> F1 = 0.0   ✅ 符合预期
sample-0004（诱饵题）
  白卷            -> F1 = 1.0   ✅ 符合预期（我上一版这里写成了 0.00，是错的）
  乱报一个漏洞    -> F1 = 0.0   ✅ 符合预期
```

**为什么**（回到第 1 章的例子）：

> 假设我们的第 8 道题长这样：代码里已经写了 `// 这里有重入漏洞` 的注释。
> 那 AI 什么都不用懂，照抄注释就能拿满分。
>
> **这道题就是废题**——它测的是"AI 会不会读注释"，不是"AI 会不会审计"。
>
> 更隐蔽的情况：判分逻辑写错了，导致"一份 findings 都不报"反而算全对。
> 这种 bug 不会报错，只会让你的分数**悄悄虚高**。
> **白卷检查就是抓这个的——这是性价比最高的一道保险。**
>
> 而**反向白卷**（第 ③ 项）抓的是另一种病：判分器太宽松，
> AI 胡乱报一堆也能拿分。抓不到这个，模型就会学会"宁可错报不可漏报"。

**验收标准**：

```bash
py run_dummy_check.py          # 新建脚本
```
输出一张表，每道题三行：
```
sample-0001   白卷 0.00 ✅   标准答案 1.00 ✅   乱报 0.10 ✅
sample-0004   白卷 1.00 ✅   标准答案 1.00 ✅   乱报 0.00 ✅
...
全部通过防伪检查
```
**任何一项不符预期，就判这道题不合格，必须从数据集里踢出去。**

**工作量**：约半天。**风险**：低。
**额外收益**：诱饵题目前只有 **1 道**（sample-0004），
这个脚本会逼着我们把诱饵题补起来——**没有诱饵题就无法测量"误报"，
而没有误报率，一个审计评测是瘸腿的。**

### 3.3 第三步 · 题坏了别扔，喂回去修　⏱ 半天　✅ 已实现骨架（2026-10-02）

> ✅ **状态**：`batch_generate.py` 的变体段从"失败就丢弃"改为**"验证失败 → 把 `validation_log`（forge 报错）喂回 `VariationOperator.fix_variant` 重试"**，最多 `GEN_MAX_RETRIES`（默认 2）次，并在样本上记录 `retry_count`、报告平均重试次数。离线自测见 `run_implementation_smoke.py`（失败→喂错→1 次收敛）。forge 实跑（验证真实重试收敛到业界 ~1.13 次）留 CI，因为本机无 forge。

**做什么**：现在埋雷失败就丢弃，改成**把错误信息喂回给 AI，让它改**。

**为什么**（回到第 1 章的例子）：

> 埋雷时 AI 把那一行挪错了位置，结果代码**编译不过**。
>
> - **现在的做法**：扔掉，重新生成一次。→ 又花钱又可能再失败。
> - **正确的做法**：把编译器的报错原文（`Error: Undeclared identifier...`）连同源码
>   一起发给 AI，说"你改错了，报错是这样的，请修一下，只输出完整修正后的代码"。
>
> 这个做法有实测数据支撑：业界对标方法 **平均只要 1.13 次就能修好**，
> 各阶段成功率 **>85%**。也就是说**失败一次就扔，是纯粹的浪费。**

> ℹ️ **好消息：这一步的地基已经有了。** `batch_generate.py` 已经会统计
> `差分通过 / 丢弃 / 有效率` 并把失败项记进 `failures`——
> 所以**不用从零建**，只要把"丢弃"改成"重试"，并补记重试次数。

**验收标准**：
- **先测一次基线**：用现在的脚本跑一批，记下**当前有效率是多少**。
  这个数字现在没人知道，它是后面一切的前提——**不知道起点，就没法说"提升了"**
- 每个埋雷算子记录 `成功率` 和 `平均重试次数`
- 目标：成功率 **≥85%**，平均重试 **≤2 次**（对标业界实测的 1.13 次 / >85%）

> 💡 **顺手加一件几乎不花钱的事：把失败分类。**
> 小红书 Muse 团队的经验（InfoQ）是：如果只记"失败了"，
> 团队最后只会不停地改 Prompt。他们把失败分成
> **模型 / 路由 / 工具 / 状态 / 控制 / 交付** 几类，
> 每类要有严重度、代表性样本和明确的修复动作，然后说了一句很关键的话：
> **"把工具参数类的失败从两成降到几个点，比总分涨了几个点更有说服力，
> 因为它有机制解释。"**
>
> 套到我们身上，失败至少该分成这几类：
> `埋雷算子` / `编译失败` / `差分验证不通过` / `判分器问题` / `模型没找到`。
> **改动很小（给 failures 加一个字段），但实验记录会从"分数"升级成"有机制解释的发现"。**

**工作量**：约半天（不含跑基线那次）。**风险**：低。
**⚠️ 为什么必须先做这一步**：不做这个，后面"扩到 50–100 道题"会被成功率卡死。
如果当前有效率只有 30%，那扩题的成本是 3 倍——**先知道这个数字再谈扩题。**

### 3.4 第四步 · 难度旋钮：让同一道题能任意调难　⏱ 2–3 天 ★ 我们独有的牌　✅ 已实现（2026-10-02）

> ✅ **状态**：`engine/operators/difficulty.py` 定义 5 个旋钮（雷数量/诱饵密度/代码伪装/跨函数/改写强度）+ 刻度 0..5 预设；`run_difficulty_sweep.py` 扫描出"难度刻度 → 结构指标 / AI 分数"曲线。离线已验证**诱饵数、伪装、跨函数随刻度单调增加**（`run_implementation_smoke.py` + `run_difficulty_sweep.py`）。
>
> ✅ **已用两个真实模型跑通验收**（`deepseek-flash` + `deepseek-v4-pro`，共 108 次调用 / $1.51），
> 完整数据见 [`13-难度旋钮验收.md`](./13-难度旋钮验收.md)。四条验收现状：
> - **结构单调** ✅ 离线可验，18 项静态体检全过
> - **分离** ⚠️ **端点通过、逐档不通过**：F1 0.775→0.649（Δ=0.127），踩雷率 0.00→0.67、耗时 ×17（这两项严格单调）；
>   但逐档有回升，且**三题中两题变难、一题变易**（变易那题刻度 0 就只有 0.385）
> - **稳定** ⚠️ 部分通过：同档标准差 0.07–0.29，`repeat=3` 偏少
> - **跨模型分开** ✅ **两条曲线在刻度 2 交叉**：之前 pro 领先 0.19，之后落后 0.11（ρ=0.20，远非同形）
> - **未覆盖** ❌ Level 2/3、`variation_k` 未接线、**跨厂模型未测**（两个模型同属DeepSeek）
>
> ⚠️ 真实跑测暴露 **5 个会让旋钮"看似工作、实则完全失效"的坑**
> （诱饵自曝身份 / 依赖符号未声明 / `max_tokens` 环境变量不生效 / 诱饵重名导致编译失败 /
> 截断空答案污染均值），其中两个由**静态体检脚本**抓出、一个由每档的 `truncated` 计数抓出。
> 详见 [doc 12 第 7 节](./12-真实模型接入与踩坑记.md)。
>
> **三个反直觉发现**（写论文时是亮点）：
> 1. **旋钮对"已经很难/已饱和"的题无效甚至反向** —— 不能用"把题调难"代替"把题出好"；
> 2. **耗时比 F1 更适合当难度硬指标** —— ×17 严格单调、无判分口径争议、且是真花的钱；
> 3. **旋钮对不同模型作用强度差2.4 倍** —— v4-pro 端点降幅 0.308 vs flash 0.127，
>    且强模型被诱饵骗得更多（踩雷 1.56 vs 0.67）。两条曲线在刻度 2 处交叉，
>    说明旋钮是**改变题目本身**、而非给所有模型套同一层壳。
>
> 💡 **附带结论（省钱）**：flash 的每 $0.1 买到的降幅是 pro 的 2.9 倍，
> **旋钮标定阶段用 flash 就够**，只在验证"是否 SOTA 也会被骗"时才需要 pro。

**做什么**：给埋雷引擎加 5 个**可以连续调节的旋钮**。

**为什么**（回到第 1 章的例子——**这是全文最重要的一段**）：

同样是"重入漏洞"这一个雷，下面这 5 种出法，难度天差地别：

| 旋钮 | 简单（刻度 0） | 困难（刻度 5） |
|---|---|---|
| ① 雷的数量 | 全篇就 1 个雷 | 同时埋 4 个，还有 2 个是假的 |
| ② 藏多深 | 就在 `withdraw()` 里，一眼看到 | 藏在 3 个文件外的辅助函数里 |
| ③ 诱饵密度 | 没有干扰 | 放 3 处"看着像漏洞其实没问题"的代码 |
| ④ 代码伪装 | 变量叫 `balances` | 变量叫 `b`，函数叫 `_f1` |
| ⑤ 改写强度 | 原样 | 用 AI 把整段代码重写一遍，语义不变 |

**刻度 0 时 AI 考 100 分，刻度 5 时 AI 可能考 20 分。**
中间的每一个刻度，都对应不同的分数——**这就是我们的"举重"。**

**为什么这是我们的王牌**：
- ALE-Bench 的难度是**题目自带**的，调不了
- ALE 的难度是**三档**（简单/中等/难），是离散的
- **我们是连续的，而且题还能换**——两者兼得，别人都没有

**验收标准**（三条必须同时满足，缺一算失败）：

1. **曲线分离**：固定一个 seed，从刻度 0 扫到刻度 5，画出
   「难度刻度 → AI 分数」曲线。**不同 AI 的曲线必须分开**，否则没区分度。
2. **曲线稳定**：换一个 seed 重新生成一批题，重画曲线。
   这里**不是要求分数数值重合**（换 seed 题就变了，分数本来就该变），
   而是要求**曲线的形状、单调性、以及"谁在谁上面"的排名保持一致**。
   如果换个 seed 两个 AI 的高下就颠倒，说明测出来的是噪音不是能力。
   > *上一版我写的是"分数应该基本重合"，这个说法是错的，已修正。*
3. **曲线单调**：难度刻度上升时，分数**总体应该下降**。不下降说明旋钮没起作用。

**工作量**：2–3 天。**风险**：中（旋钮 ②⑤ 需要改算子，会动到现有代码结构）。

### 💡 顺带解决一个你可能正在担心的问题：题从哪来？

第 1 章说了，**独立题只有 4 道**，第 5 章又问"题量 50 还是 100"。
**这两个问题其实是同一个问题，而难度旋钮一次性把它们都解决了。**

因为旋钮是连续可调的，**同一道题可以变出很多道题**：

```
4 个基础题  ×  5 个旋钮  ×  6 个刻度  ×  3 个 seed
        = 数量级上足够撑起一篇论文
```

关键在于：这些**不是同一道题重复 100 遍**（那样没有意义），
而是**同一个漏洞类型在不同难度、不同伪装、不同干扰下的 100 种考法**——
就像高考不会两次考同一道题，但会反复考同一个知识点、变着花样考。

**所以"扩题"不需要单独排期，它搭第四步的顺风车。**
这也是为什么第四步虽然最贵（2–3 天），我仍然认为它是**性价比最高的一步**。

## 第 6 章 · 明确不做的事（避免跑偏）

| 不做 | 为什么 |
|---|---|
| 不做 RL 训练 | 我们做的是**评测**，不是训练。先跑稳再说 |
| 不接 LLM-as-judge 做整体打分 | 三个标杆都警告过。要用也只能"程序出证据、模型看摘要" |
| 不追求"模型排名" | 分数本身不是目的，**区分度**才是 |
| 不在这轮扩赛道 | 见决策 ① |
| 不**推倒重写**引擎 | 前三步是纯增量，向后兼容，现有脚本不用改 |
| 不做 DataFlow 式的 storage / prompt 抽象 | 统一算子抽象**已经做完了**（四个算子都继承 `IssueOperator`），剩下那两件是"形式统一"，不是功能缺口。详见 [代码实现方案 v0.2](./AuLE-代码实现方案.md) 第 6 章。<br>**唯一例外**：LLM 客户端补 usage 透传（第一步依赖它，已列为 S1） |

> ⚠️ **上一版这里写"不重写现有引擎"，但第四步又写"可能要动现有代码结构"——自相矛盾。**
> 准确说法是：
> - **第一~三步：不动现有结构**，纯增量，现有脚本照跑
> - **第四步：会动算子内部**（旋钮 ②⑤ 需要算子支持参数化），
>   但**接口保持不变**——对外仍是"给一份代码，出一份埋雷代码"，
>   现有调用方不用改。这叫**重构**，不叫**重写**。

## 第 7 章 · 风险与兜底

| 风险 | 概率 | 兜底方案 |
|---|---|---|
| 第四步的旋钮 ②⑤ 改不动现有算子 | 中 | 先只做旋钮 ①③④（不动算子结构），一样能出曲线 |

| 忠实度一直测不了 | 高 | 降级方案：先做"相对锚定"（对照人类分布），不断言绝对能力 |
