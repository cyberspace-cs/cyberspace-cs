## 第 0 章 · 先看一个比喻，后面全靠它

**传统 benchmark 像一套「历年高考真题」。**

题一公开，培训机构就把答案编进教材，学生背下来考 700 分——
但这个分数**不能说明他会做题**，只能说明他见过这道题。
这就是行业里说的 **benchmark 腐烂**，而且是**一发布就开始烂**。

**我们做的是另一件事：一台「每次考试现场出题的机器」。**

不是出好了给你，而是**你进考场那一刻，机器才当场写卷子**——
而且它写的每道题，都当场自己验算过一遍，确认"这题确实有这个问题"。
题没公开过，也就**无从背起**。

一句话：**别人是"出卷老师"，我们是"会自己出卷的考试院"。**

## 第 1 章 · 一道题的一生（全文唯一例子，务必看懂）

下面所有内容都会回到这个例子。代码是仓库里真实的文件，不是编的。

### 1.1 第一步：先写一份「好代码」

`datasets/sample-0001/clean/Vault.sol` —— 一个存钱的保险箱：

```solidity
function withdraw() external {
    uint256 amount = balances[msg.sender];
    require(amount > 0, "no balance");

    balances[msg.sender] = 0;                        // ① 先记账：把你的余额清零

    (bool ok, ) = msg.sender.call{value: amount}(""); // ② 后给钱：真的把币转给你
    require(ok, "transfer failed");
}
```

**为什么这样写是安全的？** 因为**先把账记了，再给钱**。
就算收款方是个坏蛋，收到钱后立刻又来取一次——
账上已经是 0 了，取不到第二次。

### 1.2 第二步：埋雷——只移动一行

`datasets/sample-0001/planted/VaultPlanted.sol`。我们做的事是：
**把第 ① 行挪到第 ② 行后面。** 就这一行，别的全不动。

```solidity
function withdraw() external {
    uint256 amount = balances[msg.sender];
    require(amount > 0, "no balance");

    (bool ok, ) = msg.sender.call{value: amount}(""); // ② 先给钱
    require(ok, "transfer failed");

    balances[msg.sender] = 0;                        // ① 后记账  ← 雷在这里
}
```

现在坏蛋收到钱后可以**立刻再调用一次 withdraw**——
因为账还没记，系统以为他还有钱，**可以无限取**。这就是**重入漏洞**。

> 💡 **这就是"埋雷"的全部含义**：在好代码上做一个**极小、精确、已知**的破坏。
> 雷在哪、是什么类型、严重到什么程度——**我们全都知道**，因为是我们自己埋的。
> 这一点极其重要，它是后面一切的基石。

### 1.3 第三步：自证清白——差分验证

光说"我埋了雷"不够，得证明。做法是**把两份代码都跑一遍测试**：

| | 健康版 | 埋雷版 |
|---|---|---|
| 正常取钱 | ✅ 通过 | ✅ 通过 |
| 坏人连续取钱 | ✅ 被挡住 | ❌ **钱被取光** |

**两份代码只差一行，运行结果一个挡住一个被抢** →
铁证：这个漏洞**确实是这一行造成的**，不是代码本来就有的。

这一步叫**差分验证**，是我们整个项目最值钱的东西——
**它让我们可以在没有专家、没有人工标注的情况下，自动生成"标准答案"**。

### 1.4 第四步：拿去考 AI

把埋雷版代码发给 AI，问："这段代码有什么安全问题？"

AI 的回答被整理成这样（我们的判分格式）：

```json
{"findings": [
  {"vuln_type": "reentrancy", "function": "withdraw",
   "line": 26, "severity": "critical", "evidence": "..."}
]}
```

拿它跟**标准答案**比对。标准答案是埋雷时自动生成的，长这样
（`datasets/sample-0001/meta.json` 的真实内容，不是编的）：

```json
{"vuln_type": "reentrancy", "swc": "SWC-107", "severity": "critical",
 "location": {"function": "withdraw", "start_line": 19, "end_line": 31},
 "operator": "ReentrancyInjector", "seed": 42}
```

比对三个维度算分：**找到了吗**（recall）· **指对位置了吗**（定位 IoU）·
**严重程度说对了吗**（severity）。

> 💡 注意标准答案里的 `"seed": 42`。**同一个 seed 永远生成同一道题**，
> 这就是"可再生"的含义——别人可以完整复现我们的每一道题，
> 而且**就算全部公开也不怕被背**（因为题是现场生成的，不是从题库里取的）。

### 1.5 第五步：**问题来了——全班都考 100 分**

这是我们现在的真实处境：

| 考试 | 结果 |
|---|---|
| Level 1（找漏洞） | 3 个模型 **F1 = 1.000**（满分） |
| 数据集规模 | **7 道题** |
| 环境体检 | 多样性 **0.3665**、复杂性 **0.3673**，另外两维**没法测** → 综合 **weak** |

**"全班都考 100 分"意味着这张卷子没有区分度——它不是一张好卷子。**

这就是这份方案要解决的问题，也是我们目前**唯一的真问题**。
下面所有工作，都是为了让这张卷子重新变得"能把人分开"。

## 第 2 章 · 三个老师各教了我们一件事

我调研了三个标杆。它们**名字很像但完全不是一回事**，别搞混：

| 名字 | 一句话 | 教我们的事 |
|---|---|---|
| **Harbor** | 一个"跑考试的插座" | 试卷和答案要分袋密封 |
| **ALE** | 一套超难的专家题 | 不许考生自己给自己改卷 |
| **ALE-Bench** | 一套算法竞赛题 | **别用满分制，用举重制** |

### 2.1 Harbor 教我们：试卷袋和答案袋要分开

> **比喻**：高考试卷袋和答案袋是分开密封的，答案袋在考完前谁也不能拆。

Harbor 规定一道题必须打包成三样东西：

```
题面（给 AI 看的）    ← 可以公开
环境（代码 + 依赖）    ← 可以公开
答案 + 判卷程序        ← 单独放，AI 看不见   ← 关键
```

**我们做到了吗？做到了。** 上一轮写的 `run_harbor_export.py` 就是干这个的。

**但 Harbor 还有一条我们没做**：
> 一道题合并前，必须验证两件事——
> **① 标准答案能拿满分；② 交白卷必须得 0 分。**

第 ② 条听起来像废话，其实是最容易翻车的地方：
**如果一道题"什么都不答"也能得高分，那它就是一道废题。**
我们现在**只有 1 道诱饵题（sample-0004）**，没有系统地查过这件事。

### 2.2 ALE 教我们：能代码判的，绝不用 AI 判

> **比喻**：不能让考生自己给自己改卷——他会给自己打满分。

ALE 的铁律是：**判分权必须交给程序，不交给模型**。
因为模型判分会"老好人"（都给高分）或"幻觉"（编造没发生的事）。

**我们做到了吗？做了一半。** 我们的判分是代码算的，这很好。
但 ALE 还有一条**"先卡资格，再评质量"**，我们只做了一半：

```
Gate 1  输出能解析吗？        → 不能 = 0 分     ✅ 我们做了
Gate 2  攻击代码能编译吗？    → 不能 = 0 分     ❌ 没接
Gate 3  攻击代码真跑了吗？    → 跑了但失败 = 0  ❌ 没接
──────── 过了关才评质量 ────────
```

打个比方：**现在相当于"交了作文就给分，还没查他有没有真的去实验室做实验"。**

### 2.3 ALE-Bench 教我们：别用满分制，用举重制 ★ 最重要

> **比喻**：
> **跳高**有世界纪录，人类跳不过 2.45 米，这个项目会到顶；
> **举重**没有顶——你永远可以再加 2.5 公斤。
>
> 百分制考试是跳高：**一旦大家都考 100 分，这场考试就死了。**
> 举重是另一种设计：**分数永远有上升空间，永远能分出高下。**

ALE-Bench 用的是举重制：题目是那种"最优解算不出来"的问题
（比如给 1000 个快递订单安排路线），所以**你可以永远做得更好一点**。

它用真实数字证明了这条路的威力——同一批题，只改**给多少时间**：

| 给的时间 | 1 小时 | 几小时 | 几天 | 1 周 |
|---|---|---|---|---|
| 分数 | 58.8 | 77.7 | 87.6 | **92.1** |

而且它**同时报花了多少钱**：

| 方案 | 分数 | 每题花销 |
|---|---|---|
| 便宜方案 | 905 | **$3.25** |
| 贵方案 | **1879** | **$100.33** |

> ⚠️ **贵 30 倍只换来 2 倍分数。如果只看分数，你会以为贵的方案完胜。**
> 但看完成本表，答案取决于你有多少钱。**只报分数不报成本，是评测报告里最常见的失真。**

**对照我们自己——这条我们一条都没做到：**

1. 我们的"打穿"测试是**成功/失败二值**（要么打穿要么没打穿），不是连续分
2. 我们**不记时间**
3. 我们**不记钱**

### 2.4 三个坐标串成一条流水线

```
第1章的埋雷  →  Harbor 打包  →  ALE 定判分纪律  →  ALE-Bench 定分数形态
（怎么生题）     （怎么交付）     （怎么判才不作弊）    （怎么判才不封顶）
```

## 第 3 章 · 方案：四步走

按**性价比**排序，不是按重要性。每一步都写清楚：做什么 / 为什么 / 验收标准 / 工作量。

---

### 第一步 · 给每次考试记账（时间 + 钱）　⏱ 1 小时

**做什么**：让 `run_benchmark.py` 在跑分时自动记录两个数字，并写进结果文件。

- **wall-clock**：这次考试花了多少秒
- **cost**：这次调用花了多少钱（token 数 × 单价）

**为什么**（回到第 1 章的例子）：

> 两个 AI 都在那道重入题上拿了 90 分。
> A 用了 **3 分钟 / 2 分钱**；B 用了 **1 小时 / 30 块钱**。
> **谁更强？**
>
> 只看分数——平手。看完这两列——如果你是甲方，你每天要审 10 万个合约，
> A 比 B 好得多。**没有这两列，这个问题根本答不出来。**

**验收标准**（做完一眼就能看出成没成）：

```bash
py run_benchmark.py --repeat 3
```
输出的 `results_benchmark.json` 里，每个模型多出两列：
```json
{"model": "qwen3.8-max", "f1": 1.0, "wall_ms": 4210, "cost_usd": 0.031}
```

**工作量**：约 1 小时。**风险**：无。模块 `openended.py` 已经写好了，只是接线。

---

### 第二步 · 白卷必须得 0 分（防伪检查）　⏱ 半天

**做什么**：给数据集里**每一道题**自动生成一份"空答案"，跑一遍判分，
**得分 > 0 就报警**。再生成一份"标准答案"，必须**拿满分**，否则也报警。

**为什么**（回到第 1 章的例子）：

> 假设我们的第 8 道题长这样：代码里已经写了 `// 这里有重入漏洞` 的注释。
> 那 AI 什么都不用懂，照抄注释就能拿满分。
>
> **这道题就是废题**——它测的是"AI 会不会读注释"，不是"AI 会不会审计"。
>
> 更隐蔽的情况：判分逻辑写错了，导致"一份 findings 都不报"反而算全对。
> 这种 bug 不会报错，只会让你的分数**悄悄虚高**。
> **白卷检查就是抓这个的——这是性价比最高的一道保险。**

**验收标准**：

```bash
py run_dummy_check.py
```
输出一张表：
```
sample-0001   白卷 0.00  ✅    标准答案 1.00  ✅
sample-0004   白卷 0.00  ✅    标准答案 1.00  ✅
...
7 道题全部通过防伪检查
```
**任何一道题白卷得分 > 0，就判这道题不合格，必须从数据集里踢出去。**

**工作量**：约半天。**风险**：低。

---

### 第三步 · 题坏了别扔，喂回去修　⏱ 半天

**做什么**：现在埋雷失败就丢弃，改成**把错误信息喂回给 AI，让它改**。

**为什么**（回到第 1 章的例子）：

> 埋雷时 AI 把那一行挪错了位置，结果代码**编译不过**。
>
> - **现在的做法**：扔掉，重新生成一次。→ 又花钱又可能再失败。
> - **正确的做法**：把编译器的报错原文（`Error: Undeclared identifier...`）连同源码
>   一起发给 AI，说"你改错了，报错是这样的，请修一下，只输出完整修正后的代码"。
>
> 这个做法有实测数据支撑：业界对标方法 **平均只要 1.13 次就能修好**，
> 各阶段成功率 **>85%**。也就是说**失败一次就扔，是纯粹的浪费。**

**验收标准**：
- 每个埋雷算子记录 `成功率` 和 `平均重试次数`
- 目标：算子成功率从当前水平升到 **≥85%**，平均重试 **≤2 次**

**工作量**：约半天。**风险**：低。
**⚠️ 为什么必须先做这一步**：不做这个，后面"扩到 50–100 道题"会被成功率卡死。

---

### 第四步 · 难度旋钮：让同一道题能任意调难　⏱ 2–3 天 ★ 我们独有的牌

**做什么**：给埋雷引擎加 5 个**可以连续调节的旋钮**。

**为什么**（回到第 1 章的例子——**这是全文最重要的一段**）：

同样是"重入漏洞"这一个雷，下面这 5 种出法，难度天差地别：

| 旋钮 | 简单（刻度 0） | 困难（刻度 5） |
|---|---|---|
| ① 雷的数量 | 全篇就 1 个雷 | 同时埋 4 个，还有 2 个是假的 |
| ② 藏多深 | 就在 `withdraw()` 里，一眼看到 | 藏在 3 个文件外的辅助函数里 |
| ③ 诱饵密度 | 没有干扰 | 放 3 处"看着像漏洞其实没问题"的代码 |
| ④ 代码伪装 | 变量叫 `balances` | 变量叫 `b`，函数叫 `_f1` |
| ⑤ 改写强度 | 原样 | 用 AI 把整段代码重写一遍，语义不变 |

**刻度 0 时 AI 考 100 分，刻度 5 时 AI 可能考 20 分。**
中间的每一个刻度，都对应不同的分数——**这就是我们的"举重"。**

**为什么这是我们的王牌**：
- ALE-Bench 的难度是**题目自带**的，调不了
- ALE 的难度是**三档**（简单/中等/难），是离散的
- **我们是连续的，而且题还能换**——两者兼得，别人都没有

**验收标准**（三条必须同时满足，缺一算失败）：

1. **曲线分离**：固定一个 seed，从刻度 0 扫到刻度 5，画出
   「难度刻度 → AI 分数」曲线。**不同 AI 的曲线必须分开**，否则没区分度。
2. **曲线可复现**：换一个 seed 重新生成一批题，同刻度下的分数**应该基本重合**。
   不重合说明题目不稳定，白搭。
3. **曲线单调**：难度刻度上升时，分数**总体应该下降**。不下降说明旋钮没起作用。

**工作量**：2–3 天。**风险**：中（旋钮 ②⑤ 需要改算子，可能要动现有代码结构）。

## 第 4 章 · 做完我们能说什么

| 做完哪步 | 我们能对外说的一句话 |
|---|---|
| 第一步 | "我们的评测报告**同时报分数、时间和成本**"——同行基本做不到 |
| 第二步 | "**每一道题都通过白卷检查**"——这是 Harbor 的验收纪律，我们有 |
| 第三步 | "算子成功率 ≥85%，**能稳定扩题**" |
| 第四步 | "难度是**连续可调**的——这是我们的举重制，分数不会到顶" |

**四步全做完**，我们可以把第 1 章那个"全班 100 分"的表，换成这样一张：

> 同一个 AI，在难度刻度 0 上考 100 分，刻度 3 上考 71 分，刻度 5 上考 34 分。
> 另一个 AI，刻度 0 上 100 分，刻度 3 上 88 分，刻度 5 上 62 分。
> **——这两个 AI 的真实差距，原来看不出来，现在一眼看穿。**

## 第 5 章 · 需要你拍板的 6 件事

我不替你决定，列出选项和我的倾向：

**① 先深挖智能合约，还是直接上"企业审计"赛道？**
- A. 继续在合约上做深（推荐）——四步走全部在合约上验证，风险最低
- B. 合约做到能跑，就立刻复制到企业审计（财报/账套）——更早证明"跨赛道"
- C. 两条并行
> 我的倾向：**A**。四组件跨赛道的说法目前还是**设计**，不是**事实**。
> 先在合约上把四步走完，再用同一个框架复制第二条赛道，那时候"跨赛道"才是硬证据。

**② 每次考试给 AI 多少时间预算？**
- 建议设 **3 档**：5 分钟 / 30 分钟 / 2 小时，正好对应 ALE-Bench 的时间轴打法
- 需要你确认：预算是不是也按"钱"封顶（比如每题最多 $1）

**③ 忠实度：要不要去找真实链上合约做对照？**
- 这是目前**最大的盲区**：我们不知道"合成题考 90 分"能不能代表"真实合约也能考 90 分"
- 需要你决定：花不花时间收集一批真实合约（比如 50 个有历史漏洞的）当锚定集
> 我的倾向：**要做，但可以放到四步之后**。没有它，论文会被审稿人问死。

**④ 远程服务器（43.143.231.106）现在要不要上？**
- 本机没有 `forge`，验证只能靠 CI，扩题会卡住
- 上了就能本地批量跑，但要先部署环境（约半天）

**⑤ 这套东西最终要变成什么？**
- A. 论文（学术）
- B. 产品/服务（商业）
- C. 都要
> 影响很大：论文要"新颖"，产品要"稳定"，两者优先级不同。

**⑥ 题量目标：50 道还是 100 道？**
- 你自己的 MVP 清单里写的 DoD 是 **≥50**
- 但要撑起一篇论文，我建议 **≥100**

## 第 6 章 · 明确不做的事（避免跑偏）

| 不做 | 为什么 |
|---|---|
| 不做 RL 训练 | 我们做的是**评测**，不是训练。先跑稳再说 |
| 不接 LLM-as-judge 做整体打分 | 三个标杆都警告过。要用也只能"程序出证据、模型看摘要" |
| 不追求"模型排名" | 分数本身不是目的，**区分度**才是 |
| 不在这轮扩赛道 | 见决策 ① |
| 不重写现有引擎 | 四步走都是**增量**，向后兼容，现有脚本不用改 |

## 第 7 章 · 风险与兜底

| 风险 | 概率 | 兜底方案 |
|---|---|---|
| 第四步的旋钮 ②⑤ 改不动现有算子 | 中 | 先只做旋钮 ①③④（不动算子结构），一样能出曲线 |
| 加了诱饵后 AI 过度敏感、误报暴增 | 中 | 这正是诱饵要测的东西；误报率高本身就是一个有效发现 |
| 扩到 50 题时成功率先崩 | 中 | 第三步就是为此做的；先跑通再扩量 |
| 时间/成本预算超标 | 低 | 每题设硬上限，超了就按当前输出判分 |
| 忠实度一直测不了 | 高 | 降级方案：先做"相对锚定"（对照人类分布），不断言绝对能力 |

## 附录 · 一句话给不同的人

- **给老板**：我们在做一个"会自己出卷、且卷子永远考不烂"的考试院。
- **给投资人**：现有 AI 评测榜单全都会腐烂，我们这个不会——这是结构性优势。
- **给审稿人**：我们的贡献是①可再生防污染，②难度连续可调，③时间/成本双轴报告规范。
- **给工程师**：就四件事——记时间钱、查白卷、失败重试、加难度旋钮。加起来 5 天。
