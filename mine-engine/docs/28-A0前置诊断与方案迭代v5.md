## 0. 结论速览

> **v4 承诺的"会计域 ≥4 档难度"，在代码层面目前不成立 —— 但缺的不是算子，是参照 oracle。**

## 1. 实测：oracle 覆盖坍缩

### 1.1 违反签名矩阵

方法：`certify(led, op, θ, trial)` 对 4 个算子 × 4 档注入金额（默认/ 1 / 500 / 50000）× 10 seed
= 每个算子 40 次，取违反集合的并集。

| 注入算子 | 对应审计认定 | 违反的 oracle（40/40 次全一致） | 未触发 |
|---|---|---|---|
| `offbook` 账外账/体外循环 | **completeness** 完整性 | `o_tie_detail`, `o_rollforward` | `o_equation`, `o_policy` |
| `cutoff` 跨期调节 | **cutoff** 截止性 | `o_tie_detail`, `o_rollforward` | 同上 |
| `depreciation` 折旧计提不足 | **valuation** 计价准确性 | `o_tie_detail`, `o_rollforward` | 同上 |
| `capitalize` 费用资本化 | **presentation** 分类列报 | `o_tie_detail`, `o_rollforward` | 同上 |

**读法**：行与行之间**没有任何差异**。四个算子虽然作用科目完全不同
（银行存款/应收账款 / 应收账款 / 累计折旧 / 固定资产），但从 oracle 视角看是同一个点。

### 1.2 oracle 实际参与度

| oracle | 语义 | 被触发？ | 根因 |
|---|---|---|---|
| `o_tie_detail` | 表账一致（报表 = 明细账结转后） | ✅ 4/4 算子 | 改报表期末数必然破坏 |
| `o_rollforward` | 期末递推（上期 + 本期发生额） | ✅ 4/4 算子 | 同上 |
| `o_equation` | 会计恒等式（资产 = 负债 + 权益） | ❌ **0** | 四个算子都是**资产与权益同增**，恒等式差恒为 0 |
| `o_policy` | 累计折旧率不得超过准则上限 | ❌ **0** | 见 §2.1，判定方向反了|

**声明 oracle 数 = 4，实际参与判别的 = 2。**

### 1.3 为什么这不是"实现偷懒"，而是设计后果

`audit_core.py` 注释里已记录过这个发现（原话）：

> 改报表期末数必然连带破坏 `o_tie_detail` 与 `o_rollforward`。
> 所以"每个手法恰好破坏一条 oracle"在会计域不成立。

这句话是对的，但**结论下早了**：当时据此把判据改成"无意外项 + 核心项被破坏"，
于是 DIC 通过了、A0 就算过了。但从**测量效度**看，两个恒被触发的 oracle 只能提供
一个比特的信息——**参照层失去了分辨四个认定的能力**。

> ⚠️ 这是本项目"看似生效实则失效"的第5 类坑：
> **判据从"集合相等"放宽到"包含"，指标随之变好，但被测量的构念（construct）被悄悄换掉了。**
> 与已记录的"伪装类算子自曝身份"同类——**指标达标不等于测到了想测的东西**。

## 2. 🔴 两个必须修的代码缺陷

### 2.1 `o_policy` 是死代码，且判定方向与注释相反

```python
if dep / fa > hi + 1e-6:   # 只判上限
    return False
```

| 实测项 | 值 |
|---|---|
| 累计折旧率区间（200 seed × 全期，800 个样本） | **0.0125 – 0.0500** |
| `POLICY["depreciation_rate_range"]` 上限 `hi` | **0.10** |
| `o_policy` 判假次数 | **0 / 800** |
| `op_depreciation` 造成的累计折旧率变化 | 0.0500 → **0.0100（调低）** |

**三重矛盾**：

1. **注释与代码反向**。注释写"累计折旧率过高 = 折旧不足（虚增利润）"——
   会计上恰好相反：折旧**不足**会使累计折旧率**偏低**；折旧**超额**计提才使累计折旧率偏高。
2. **算子与 oracle 反向**。`op_depreciation` 减少累计折旧（少提折旧），
   而 `o_policy` 只在累计折旧率**超上限**时报警 ⇒ **结构上不可能抓到它**。
3. **参数使其不可达**。即使注入方向改对，实测上限 0.05 < 阈值 0.10，仍永不触发。

**修法（二选一，建议 a）**：
- **(a) 改为区间判定 + 认定化**：新增 `o_accum_dep` 判**下限**（累计折旧率 < 应计提下限 = 折旧不足），
  并用**期数相关的应计提下限**而非固定值，与 `o_policy` 现有上限语义分离。
- **(b) 只保留上限语义**，则必须能触发——需把注入改为"超额计提折旧"，
  但这会变成另一种舞弊（激进折旧节税），**与"虚增利润"叙事相反**，不推荐。

> ⚠️ **同时暴露一个更深的问题**：`o_policy` 原本就**只有上限、没有下限**，
> 注释里解释了理由（"首期累计折旧天然低于稳态年折旧率"）。
> 但这意味着**"折旧不足"这个最常见的舞弊类型，在参照层根本没有对应的检测器**——
> 而它正是 `depreciation` 算子要注入的东西。
> ⇒ **`op_depreciation` 目前是一个"注入成功但无人能证"的算子。**

### 2.2 `o_equation` 在当前算子集下不参与判别

四个算子全部是"资产 +X、权益/损益 +X"的**同增型**注入，恒等式差恒为 0。
这在会计上是**正确的**（资产与权益同增不破坏恒等式），代码注释也已指出。

**但后果是**：`o_equation` 是审计学里最核心、最容易被审稿人独立验证的一条约束
（注释原话："审计最核心的一条，审稿人可自行查准则"）。
它现在**不参与判别**，等于我们放弃了"最容易防守的一条"，
却把全部判别重量压在 `o_tie_detail`（表账一致）上——后者恰恰是最容易被质疑
"这是不是只是数值比对、不是审计判断"的那一条。

**修法**：补**异增型**注入算子（只动一侧），至少一条：
- 虚增资产不冲权益（`o_equation` 触发，`o_tie_detail` 也触发）
- 或反向：冲减权益不虚减资产

⚠️ 这类注入在会计上更接近"明显错误"而非"隐蔽舞弊"，
**难度偏低**，需在论文中说明它只用于验证参照层的**完备性**，不作为主难度档。

### 3.0.1 实施中被实测否掉的四版设计（**本节最贵，勿重犯**）

每一版都是"看代码觉得对"，跑起来才发现抓不到。这四步花掉的约 3 小时
**全部花在 oracle 上，零 LLM 成本** —— 反过来说，
如果没做这一步就直接跑 A0，那 $8–12 会打在四档退化成一档的数据上。

| 版本 | 设计 | 实测 | 否掉它的根因 |
|---|---|---|---|
| **v1 折旧下限** | `floor = min(r_stable, p×r_stable) × 0.5` | **误报 150/600** | 种子账套实际年折旧率 **0.05**，而政策下界 `r_stable`=**0.03**，两者不一致；p=1 时 floor 0.015 > 干净值 0.0125 |
| **v1 截止检测** | "收入下降但应收未动" | **零触发** | `6001_revenue` 在**结转后报表恒为 0**（`expected_reported` 清零 TEMP），判据第一条腿不存在 |
| **v2 截止检测** | 用 `period_flow` 比应收增量 vs 收入 | **0/80 全漏** | **所有算子只改 `reported`，从不改 `vouchers`**；`period_flow` 读明细账 ⇒ 注入在它眼里不存在 |
| **v1 分类检测** | "结转后费用科目仍有余额" | **零触发且两头都不成立** | 干净账套费用也恒为 0.0，`op_capitalize` 也不动费用科目 |

**最终解法（两点）**：

1. **不用固定阈值，用逐期相对判据**（`o_accum_dep`）：
   `本期累计折旧 ≥ 上期累计折旧 + 本期应计提`。
   ⚠️ 为什么必须这样：干净值 0.0125 与注入值 0.0100 **仅差 0.0025**，
   任何固定阈值都极易判反；而**相邻期之差**与账套绝对参数无关。
2. **不用余额，用"报表 vs 明细账的科目级偏离"**（`o_cutoff_period` / `o_classification`）：
   `o_tie_detail` 是**全科目一次性比较**，只知"有偏离"不知"哪个科目偏离"，
   对认定不敏感；**把同一判据按科目组拆开**即得认定级信号。
   四个算子各打不同科目（`1002_bank` / `1122_ar` / `1602_accum_dep` / `1601_fa`）
   ⇒ 天然分离。

> 🔴 **这一轮的教训已升格为通用规则（写进 `audit_core.py` 注释）**：
> **注入只改报表时，任何读明细账的判据都看不见注入；
> 而结转后损益科目恒为 0，任何读结转后余额的判据都看不见损益类舞弊。**
> 两条都不是 bug，是会计口径的必然结果，但都会伪装成"我的 oracle 写错了"。

### 3.1 ⚠️ `offbook` 仍未取得认定级信号（诚实边界）

F4 后 `offbook` 的签名仍与`cutoff`/`capitalize` 同为 `{tie_detail, rollforward}`，
只靠 `o_cutoff_period`（应收组）与 `capitalize` 拉开。
原因：`op_offbook` 打的是 **`1002_bank`**（银行存款），
而现有认定级 oracle 覆盖 `1122_ar` / `1601_fa` / `1602_accum_dep`。

- **技术上易修**：加一条 `o_cash_receipt`（银行存款组偏离）即可全分离。
- **但本轮刻意不做**：先验证"新增认定级 oracle 会不会引入假阳性"这个机制本身
  （已验证三次，全部零误报），再补第四条。
- **对 A0 的影响**：**不影响四档可区分性**——因为区分靠的是
  「`{tie,roll}` / `{tie,roll,cutoff}` / `{tie,roll,accdep}` / `{tie,roll,class}`」
  四种**互不相同**的签名，`offbook` 作为**基准档**（签名最简）是合理的。
  ⚠️ 但论文里必须写明：`offbook` 是"其他认定的参照基线"，其completeness 属性
  由**注入形态**（账外账、不入明细账）保证，**不由 oracle 签名区分**。

**算子层早就按审计认定分层了（4 个算子 = 4 条认定），但参照层没有——
所以当时的"难度"只有一个比特。已修好：7 条 oracle、4/4 签名分离、零误报，
花约 3 小时与零 LLM 成本，换掉的是 $8–12 打在退化数据上的风险。**

而这四轮失败给出的最重要一条经验是：

> **注入只改报表时，任何读明细账的判据都看不见注入；
> 结转后损益科目恒为 0，任何读结转后余额的判据都看不见损益类舞弊。**

这两条都不是 bug，是会计口径的必然，但都会伪装成"我的 oracle 写错了"。
已写进 `audit_core.py` 注释，逐条标注"被实测否掉的设计，勿重犯"。
