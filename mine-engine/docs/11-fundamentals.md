# 11 · 这个领域的基础（从零讲起）

> **写给完全没基础的人。** 看这一篇不需要任何前置知识——

>
> 全文用**一场考试**作比喻讲到底，并标明每一节的国内来源（CSDN / 小红书）。
> 最后落到一个问题：**这些基础怎么一块块拼成我们的 AuLE。**
>
> 版本：AuLE v0.6 ｜ 2026-10-01

## 第 0 章 · 这个领域到底在解决什么问题

先说清楚我们在干什么，否则后面全是名词。

**一句话：AI 越来越强了，但没人知道它到底有多强。**

原因是这样——你问一个 AI"这段代码安全吗"，它回答"安全"。
你怎么知道它对不对？

- 找专家看？慢，贵，而且专家之间还会吵架
- 让它自己说对不对？**等于让考生自己给自己改卷**

于是大家想到一个办法：**像高考一样，出一套标准考卷，让所有 AI 都来考，用分数排序。**
这个"标准考卷"，就是 **benchmark（评测基准）**。

**但麻烦来了**：题一公开，AI 公司就把答案喂给模型背。
下次考试它考 700 分——**不是因为它会做题，是因为它见过这道题。**

这就是整个领域现在最头疼的事，业内叫 **benchmark 腐烂**。

> 我们这个项目（AuLE）要解决的，就是这个"考卷会腐烂"的问题。
> **别人的解法是"少公开几道题"（ALE 只敢公开 10%），我们的解法是"每次现场出题"。**

## 第 1 章 · 三个词，用一场考试讲清楚

这个领域所有的名词，都能用考试讲明白。

### 1.1 Agent（智能体）= 考生

不是"一个会聊天的模型"，而是**一个能自己动手干活的东西**。

- 普通模型：你问它"1+1 等于几"，它回答"2"。**只动嘴。**
- Agent：你说"帮我把这个 bug 修了"，它会**自己读代码、自己改、自己跑测试、错了再改**。**动手。**

> **例子**：让 AI 审计一段合约代码。
> 普通模型：把代码贴给它，它说"这里有重入漏洞"。
> Agent：它自己打开文件、自己搜索 `call{value:}`、自己写攻击代码验证、自己出报告。

### 1.2 Environment（环境）= 考场

Agent 要动手，就得有个地方让它动手。

> **例子**：让 Agent"修复这个 bug"，你得给它——
> 一台能跑的机器、装好依赖的代码仓库、能执行测试的权限。
> 这一整套东西就是**环境**。

**环境是被评测圈最看重的部分，也最容易被外行忽略。**
为什么？因为**同一个 AI，在不同考场里考出来的分完全不一样**。

> 就像同一个考生，在有空调的考场和漏雨的考场，考分能一样吗？
> 很多"AI 进步了"的新闻，其实是"考场换了个好的"。

### 1.3 Benchmark（评测基准）= 考卷 + 评分规则

一套 benchmark 至少包含三样：

```
① 一批题（task）          考什么
② 每个题的正确答案         标准答案
③ 一套判分规则             怎么算分
```

**这三样缺一个，就不叫 benchmark，只能叫"一堆题"。**

> ⚠️ 新手最容易忽略的是第 ② 项。
> 很多人以为"出题"是最难的，其实**"怎么知道正确答案是什么"才是最难的**。
> 我们后面会看到，这个项目最值钱的东西恰恰是解决这一条。

### 1.4 第四个词：Harness = 监考老师

这个词国内讲得少，但它最实用。

**Harness 就是那个"把考试整个流程跑起来"的程序。** 它负责：

```
把考场搭起来 → 把题发给考生 → 盯着他别作弊/别超时 → 收卷 → 判分 → 出排行榜
```

> **例子**（Terminal-Bench 官方结构，CSDN 有过完整解读）：
> ```
> tb run --agent claude-code --n-concurrent 4
> ```
> 敲这一行，harness 就在后台：拉起 Docker 容器、把题交给 AI、
> 等它做完、跑判分脚本、最后打印一张准确率表。

**没有 harness，你有题也考不了试**——就像有考卷但没人监考、没人收卷。

### 1.5 四个词串起来：一次完整考试

```
  出题人 ──▶ 考卷(benchmark) ──▶ 考场(environment) ──▶ 监考(harness)
                                       │
                                       ▼
                                    考生(agent)
                                       │
                                       ▼
                                   判分 → 分数 → 排行榜
```

**记住这张图，后面所有内容都是往里面填东西。**

## 第 2 章 · 国内是怎么讲这套基础的

我查了 CSDN 和小红书上关于"基础"的讲法，挑出**四个讲得最好、也对我们最有用的**。

### 2.1 CSDN 讲法一：AgentBench = AI 的高考

> 来源：CSDN《智能体评估基准(AgentBench)解读》

讲法是：**8 个任务域就是 8 个考试科目**——
语文（创意写作）、数学（逻辑推理）、英语（网页浏览）、
理综（操作系统/数据库/知识图谱）、文综（卡牌游戏）、实操（家务机器人）。

每个科目有权重，总分就是"高考分数"，可以横向对比不同 AI。

**它澄清了三个新手最容易搞混的点**，我原样转述：

| 常见误解 | 正确理解 |
|---|---|
| "这是考大模型的" | **考的是整个 Agent 系统**。同一个 GPT-4，套个 AutoGPT 壳再考，分数能差 100%+ |
| "就是一套题" | **是动态交互测试**。不是"给问题要答案"，是"给任务，让它和环境来回互动直到完成" |
| "做对就得分" | **多维度加权**。除了做没做完，还看效率、错误率、稳定性 |

> 💡 **对我们的用处**：它那张"传统基准 vs Agent 基准"对比表，
> 可以直接拿来解释"我们和 MMLU/GSM8K 这类东西不是一回事"。

### 2.2 CSDN 讲法二：Terminal-Bench = 一场标准化考试 ★ 讲得最好

> 来源：CSDN《Terminal-Bench入门指南》

这篇把整个系统拆成**考试的四个角色**，是我见过最清楚的讲法：

| 文件 | 考试的比喻 | 实际作用 |
|---|---|---|
| `task.yaml` / `instruction.md` | **题干** | 用英文说明要完成什么事 |
| `Dockerfile` | **考场** | 一个隔离的容器环境 |
| `tests/` + `run-tests.sh` | **判分脚本** | 在容器里跑 pytest |
| `solution.sh` | **参考答案** | 标准解法 |
| `harness` | **监考老师** | 拉起容器、发题、收卷、判分 |

**它还有三个我们直接能抄的工程经验：**

1. **`--agent oracle` 是干什么用的？**
   > 不加 `--agent` 参数时，默认跑"参考答案"，
   > **用来验证整条评测链路通不通**（安装、Docker、判分解析）。
   >
   > 💡 这就是我方案里"标准答案必须拿满分"那条检查——
   > **原来业内早有标准名字，叫 `oracle`（神谕/标准答案）**。
   > 我们之前自己起名叫"标准答案检查"，以后统一叫 **oracle check**。

2. **`--n-attempts 3`**：每题跑 3 次，算 pass@k，
   **"用于抹平单次运气成分"**——和我们 `run_benchmark --repeat N` 是同一件事。

3. **跑 oracle 要跑 5 次**：官方 README 要求
   "Run the oracle solutions **5x** to confirm all tasks work as expected"。
   > 跑 5 次是为了确认**题目是稳定的**，不是这次能过下次过不了。
   > 这正是我方案第四步"曲线稳定"那条验收的行业依据。

### 2.3 小红书 Muse 讲法：评测要分三层，中间那层最容易被忽略 ★ 最有价值

> 来源：InfoQ《AI 写代码飞快，为何交付没有变快？小红书 Muse 的 Agentic 架构实践》

这是小红书工程团队在 AICoding 上的实战总结。他们说 Agent 评测必须分三层：

| 层 | 看什么 |
|---|---|
| **最外层 · 结果评测** | 业务任务**是否真的完成** |
| **中间层 · 轨迹评测** | 有没有选对工具、有没有重复执行、**出错后有没有恢复** |
| **最里层 · 组件评测** | 单独测某个 Prompt、某个路由、某个工具、某个验证器 |

然后他们说了一句**我认为是整个领域最该被记住的话**：

> "**最终结果正确但轨迹并不合格的情况非常常见**：
> 它可能绕了二十步，可能重复提交了两次，也可能在一个本该请求确认的地方直接改了。
> 这类结果如果只按成功率统计，会被记成一次成功，
> **于是我们就把运气当成了能力。**"

**把运气当成能力**——这八个字精确地指出了我们现在的问题。
我们三个模型 F1 都是 1.000，看着是"都会做"，
但**它们是怎么做出来的，我们完全没有记录**，也许是蒙的。

**他们还有一条：失败要分类。**

> 如果只记录"失败了"，团队最后只会不停地改 Prompt。
> 我们把失败分成**模型 / 路由 / 工具 / 状态 / 控制 / 交付**几类，
> 每一类都要有严重度、代表性轨迹和明确的修复动作。
> **分类分布的变化本身就是指标**：
> 把工具参数类的失败从两成降到几个点，**比总分涨了几个点更有说服力，
> 因为它有机制解释。**

> 💡 **对我们的用处（很实在）**：
> 我们现在的 `failures` 只记"这道题失败了"。
> 应该改成**分类记录**：是埋雷算子的问题？是编译的问题？
> 是判分器的问题？还是模型根本没找到？
> 这个改动很小，但会让我们的实验记录从"分数"升级成"有机制解释的发现"。

### 2.4 小红书 dots 讲法：把主观题拆成 1247 个是非题

> 来源：小红书 dots 实验室开源的 VibeLifeBench

他们做"生活类长程任务"评测，比如"规划一次家庭旅行"。
这种任务**没有标准答案**——怎么判分？

他们的办法：**不做整体评分，而是拆成一大堆可判是非的小检查项**，
叫 **atomic checks（原子检查项）**。VibeLifeBench 里有 **1247 项**。

> **例子**：不要问"这次旅行规划得好不好"（没法判），
> 而是问这 1247 个小问题：
> "航班改期后，行程里的接机时间有没有跟着改？"
> "预算超了之后，有没有主动提示？"
> ——**每个都是明确的是或否。**

另一套 VibeSearchBench 用的指标叫 **Triplet F1**：
把模型找到的信息抽成知识图谱的三元组，跟标准答案比对算 F1。

> 💡 **对我们的用处**：**这正是审计任务的解法。**
> "这份审计报告好不好"没法判，但
> "这笔账借贷是否平衡"、"这笔凭证有没有附件"、"这条法条有没有命中"——
> **每一条都能判是非**。我们的三条赛道（国家/企业/审计师）就该这么拆。

### 2.5 小红书 Muse 讲法：成本要按"每个成功任务"算

> 来源：同上（InfoQ 访谈）

原文：

> "单看 Token 单价其实越来越没有意义，
> 应该看**每一个成功任务的成本**。
> **分母是通过的任务数**，分子要把**重试、升级到更强配置、
> 验证器本身的开销和人工返工**都算进去。
> 一个便宜的配置，如果需要重试三次再由人改一遍，**其实它并不便宜。**"

> 🔴 **这条直接修正了我方案第一步的写法。**
> 我原先写的是"记录每次调用花了多少钱"——**口径不对**。
> 正确的口径是 **cost per solved task**：
> 把重试、升级、验证、返工全算进分子，分母只算**成功的题数**。
>
> 差别在哪？假设一共 4 道题，**公式是「每题成本 ÷ 命中率」**：
>
> | 模型 | 每题成本 | 做对 | 每成功一题的成本 |
> |---|---|---|---|
> | A | $0.03（只调 1 次） | 1/4（25%） | $0.03 ÷ 0.25 = **$0.120** |
> | B | $0.09（调 3 次重试） | 4/4（100%） | $0.09 ÷ 1.00 = **$0.090** |
>
> **只看每题成本会以为 A 便宜 3 倍，按成功任务算其实是 B 便宜。**
>
> ⚠️ **本版修正**：这里原先两处都算错了——A 漏掉了分母（写成 $0.03，
> 实际 4 道题里只对 1 道，总成本 0.12），B 把"每题成本 $0.15"
> 当成"4 道题的总成本"直接除 4（得 0.0375，实际应为 0.15）。

### 2.6 小结：国内讲法 vs 我们

| 国内讲法 | 我们现状 |
|---|---|
| 考场（Docker 隔离环境） | ✅ 有（Harbor 导出） |
| oracle check（标准答案必须满分） | ❌ 没做（方案第二步，现在有标准名字了） |
| 跑 5 次验稳定性 | ❌ 没做（`--repeat` 有了，但没用在题目稳定性上） |
| 三层评测（结果/轨迹/组件） | ❌ **只有结果层，轨迹层完全空白** |
| atomic checks（拆成可判是非的小项） | 🔨 判分器有雏形（类型/定位/严重度三维），但没到"原子项"粒度 |
| 失败分类（带机制和修复动作） | ❌ 只记"失败"，不分类 |
| cost per solved task | ❌ 完全没记 |

**结论：七个基础件，我们只稳稳做对了一个。**

## 第 3 章 · 三个标杆，各管一件事

现在讲你问的三个方向。**它们名字像，但完全不是一回事**，别再搞混：

| 名字 | 是什么 | 管的环节 | 一句话 |
|---|---|---|---|
| **Harbor** | 评测**框架** | 考场 + 监考 | 怎么把考试跑起来 |
| **ALE** | 评测**基准** | 判分纪律 | 怎么判才不作弊 |
| **ALE-Bench** | 评测**基准** | 分数形态 | 怎么判才不封顶 |

### 3.1 Harbor：考场和监考老师

**它是什么**：laude-institute 出的评测执行框架，Terminal-Bench 2.0 的底座。

**它解决什么**：在没有 Harbor 之前，每个 benchmark 都要自己写"拉容器、发题、收卷、判分"这套活。
Harbor 把这层抽出来，你只要**按它的格式出题**，剩下的它全包了。

**它的任务长什么样**（官方结构）：

```
task-name/
├── instruction.md     题干（给 AI 看的）
├── task.toml          元数据（难度、类别、标签、预计耗时、资源限制）
├── environment/
│   └── Dockerfile     考场
├── solution/
│   └── solve.sh       参考答案（AI 看不见）
└── tests/
    ├── test_outputs.py  判分脚本
    └── test.sh
```

**关键设计**：`solution/` 和 `tests/` 是**分开的**，
而且 AI 只能看到 `instruction.md`。
> 这就是"试卷袋和答案袋分开密封"——**AI 永远拿不到标准答案。**

**它的两个杀手锏命令**：

```bash
harbor run --agent oracle      # 跑标准答案，验证链路通不通
harbor run --agent claude-code --model ... --n-concurrent 4   # 真考
```

> 💡 **`oracle` 这个概念请记住**，它是我们方案第二步的行业标准名字。

### 3.2 ALE：判分纪律（怎么判才不作弊）

**它是什么**：Berkeley RDI（Dawn Song 组）的 Agents' Last Exam，arXiv:2606.05405。
1,490 个真实专家任务，分三层难度，**最难层通过率只有 2.6%**。

**它教我们的事**：判分权必须交给程序，不能交给模型。

> **比喻**：不能让考生自己给自己改卷——他会给自己打满分。
> 模型判分有两个毛病：**老好人**（都给高分）和**幻觉**（编造没发生的事）。

它的具体做法是 **Gate-and-score（先卡资格，再评质量）**：

```
Gate 1  输出能解析吗      → 不能 = 0 分
Gate 2  ...能编译吗       → 不能 = 0 分
Gate 3  ...真跑了吗       → 跑了但失败 = 0
────────── 过了关才评质量 ──────────
```

**它还有一条震惊人的数据**：
Codex + GPT-5.5 在 Terminal-Bench 上拿 **82%**，在 ALE 最难层拿 **0%**。

**它最狠的一招**：1,490 题**只公开 150 题（10%）**——因为怕污染，90% 不敢公开。

> ⚠️ 这一条是我们最重要的论据：
> **它不敢公开题，我们敢全公开**——因为我们的题是现场生成的。

### 3.3 ALE-Bench：分数形态（怎么判才不封顶）

**它是什么**：Sakana AI × AtCoder 的 ALgorithm Engineering Benchmark，arXiv:2506.09050。
40 道 NP-hard 优化题（路径规划、排班、调度）。

**它教我们的事**：**别用满分制，用举重制。**

> **比喻**：
> **跳高**有世界纪录（2.45 米），人类跳不过，这个项目会到顶；
> **举重**没有顶——你永远可以再加 2.5 公斤。
>
> 百分制考试是跳高：**一旦全班考 100 分，这场考试就死了。**
> 举重是另一种设计：**分数永远有上升空间。**

**为什么它能做到？** 因为它的题是 NP-hard，**最优解算不出来**，
所以"更好的解"永远存在——国内解读原话是
"由于 NP-困难性质，这类问题本身没有明确的最优解，因此**分数可以不断提升**"。

**它的三条纪律**（我们一条都没做到）：

1. **连续分代替二值分** —— 不是"过/没过"，是实打实的分数
2. **必须报时间预算** —— 1h **58.8** → 几小时 **77.7** → 几天 **87.6** → 1 周 **92.1**
3. **必须报成本** —— 便宜方案 905 分/$3.25，贵方案 **1879 分/$100.33**

**它的数据包有四部分**（CSDN 解读整理）：

| 组成 | 作用 |
|---|---|
| `Problem` | 题目完整描述（Markdown + 图示） |
| `Scorer` | Rust 写的评分程序 |
| `Visualizer` | 网页可视化 + Rust 程序，动态展示执行过程 |
| `Leaderboard` | 排名参考数据 |

还有一个细节很妙：**它有个 lite 版，只精选 10 道题**——
方便人快速评估，**不用跑完 40 道**。这个设计我们可以直接抄。

### 3.4 三者不是竞品，是一条流水线的三段

```
     造环境        打包交付        判分纪律         分数形态
       │              │              │               │
       ▼              ▼              ▼               ▼
     AWM  ──▶   Harbor  ──▶   ALE  ──▶   ALE-Bench
   （怎么生题）   （怎么跑题）   （怎么判不作弊）   （怎么判不封顶）
```

> **AWM** = Agent World Model（UNC + Snowflake，arXiv:2602.10090），
> 环境合成流水线，1,000 个全合成环境 / 10,000 个任务。
> 它不在你问的三个里，但它是"题从哪来"这一段的答案。

## 第 4 章 · 这些基础如何一块块拼成 AuLE

现在回答问题：**这些基础，AuLE 里分别对应什么？**

### 4.1 逐块对照

| 基础件 | 行业做法 | AuLE 里对应什么 | 状态 |
|---|---|---|---|
| **考场** | Docker 容器 | Harbor 任务导出（`run_harbor_export.py`） | ✅ 有 |
| **题干/答案分袋** | instruction 与 tests 分离 | 同上，ground truth 只在 `tests/` 下 | ✅ 有 |
| **监考** | Harbor CLI | 我们自己的 `run_benchmark.py` | ✅ 有 |
| **题从哪来** | 人工出题 / AWM 合成 | **埋雷引擎**（健康代码 + 程序化破坏） | ✅ **有，且是独有的** |
| **答案从哪来** | 人工标注 | **差分验证**（健康版 vs 埋雷版行为不同 → 雷确实在这） | ✅ **有，且是独有的** |
| **oracle check** | `harbor run --agent oracle` | 待建（方案第二步） | ❌ 缺 |
| **dummy check（白卷）** | 交白卷必须 0 分 | 待建（方案第二步） | ❌ 缺 |
| **稳定性（跑 5 次）** | oracle 跑 5x | 待做 | ❌ 缺 |
| **轨迹层评测** | 小红书 Muse 三层 | **完全空白** | ❌ 缺 |
| **原子检查项** | VibeLifeBench 1247 项 | 判分器有三维雏形，未到原子粒度 | 🔨 半成品 |
| **失败分类** | 小红书 Muse 六类 | 只记"失败" | ❌ 缺 |
| **时间轴** | ALE-Bench 四档 | 模块写好（`saturation_check`），未接线 | ❌ 缺 |
| **成本（每成功任务）** | ALE-Bench / 小红书 Muse | **完全没记** | ❌ 缺 |
| **难度连续可调** | ALE 三档 / ALE-Bench 题目自带 | 埋雷旋钮（方案第四步） | ❌ **缺，但这是我们的王牌** |

### 4.2 我们比别人多出来的那一块

看上表会发现：**行业里"题从哪来"和"答案从哪来"这两块，别人都是靠人。**

- AgentBench：人出题
- Terminal-Bench：人出题（还有 ScaleAI、Snorkel 这类数据供应商）
- ALE：人出题（1,490 道专家任务）
- ALE-Bench：从 AtCoder 历史比赛里挑的（本质还是人出的）
- AWM：AI 合成，但要靠"自我修正循环"反复修

**我们是唯一的例外——题和标准答案都是程序自动生成的。**

怎么做到的？回到第 1 章那个例子（`datasets/sample-0001`）：

```solidity
// 健康版：先记账，后给钱  → 安全
balances[msg.sender] = 0;                          // ① 先记账
(bool ok, ) = msg.sender.call{value: amount}("");   // ② 后给钱
```

```solidity
// 埋雷版：把 ① 挪到 ② 后面  → 重入漏洞
(bool ok, ) = msg.sender.call{value: amount}("");   // ② 先给钱
balances[msg.sender] = 0;                           // ① 后记账  ← 雷
```

**两份代码只差一行，跑出来的结果一个挡住攻击、一个被抢光。**
这个"行为差异"就是铁证——**雷确实在这一行，不是代码本来就有的**。

于是我们**不需要专家、不需要人工标注**，就同时拿到了：

```
题（埋雷后的代码）+ 标准答案（雷在哪、什么类型、多严重）
```

**这就是 AuLE 的地基。** 上面表里所有"缺"的项，
都是在这个地基之上补的工程件——**地基不用改，只是往上盖。**

### 4.3 我们缺的三块，和最该先补的那块

按"不补会怎样"排序：

**① 成本和时间（最该先补）**
不补，报告里只有分数。小红书 Muse 说得很清楚：
分词数不报成本的评测是失真的。
而且我们已经踩过一次坑——
**本来以为"只差接线"，结果 `client.py` 把 `usage` 字段丢了，成本根本算不出来。**

**② oracle + dummy 检查**
不补，我们不知道自己的题是不是废题。
**分数悄悄虚高，而且不会报错**——这是最阴险的失败模式。
行业里这两个检查有标准名字，是 Terminal-Bench 的硬性验收纪律。

**③ 难度连续可调（最贵，但是王牌）**
不补，我们永远是"全班考 100 分"。
**ALE 的难度是三档离散的，ALE-Bench 的难度是题目自带不可调的，
我们是连续可调的——这是别人都没有的一行。**

### 4.4 拼完之后，AuLE 长什么样

```
┌──────────── 别的 benchmark ────────────┐   ┌──────── AuLE ────────┐
│  人出题 → 题库固定 → 公开即开始腐烂     │   │  埋雷引擎 → 现场出题  │
│  人标答案 → 贵、慢、会吵架             │   │  差分验证 → 答案自证  │
│  难度固定 → 大家考满分后榜单失效        │   │  难度旋钮 → 永不封顶  │
└──────────────────────────────────────┘   └──────────────────────┘
                                                      │
                                              Harbor 格式导出
                                                      │
                                              oracle/dummy 验收
                                                      │
                                              时间 + 每成功任务成本
```

## 第 5 章 · 用一句话向外人解释 AuLE

按对象分：

- **给完全不懂的人**：
  "别人是出卷老师，我们是**一台会自己出卷的考试院**——
  你进考场那一刻机器才写题，所以没人能提前背答案。"

- **给懂 benchmark 的人**：
  "ALE 只敢公开 10% 的题来防污染，**我们从结构上 100% 可以公开**。"

- **给工程师**：
  "埋雷引擎出题，差分验证出答案，Harbor 格式交付，
  oracle/dummy 验收，难度旋钮保证分数不封顶。"

- **给审稿人**：
  "贡献有三：① 可再生基准（抗污染，CRS 可量化）；
  ② 难度连续可调（ALE 离散三档、ALE-Bench 不可调）；
  ③ 时间 + 每成功任务成本的双轴报告规范。"
