## 1. 我们从哪来：AuLE 现在手上有什么

### 1.1 已建成（事实）

四组件抽象 —— `Generator`（种子程序）/ `Operator`（注入变换）/ `Validator`（差分验证）/ `Scorer`（判分），
换赛道只换这四个类的实现，编排层不动。已落地：智能合约赛道（7 样本）+ 三赛道设计文档。

核心原理：**不问"这段代码有没有漏洞"，而问"我把它改坏之后，行为是否按预期变了"**。
前者是判断（会吵架、会幻觉），后者是实验（可复现、不会错）。
一次注入动作同时产出题（`injected_source`）和答案（`issues` 记录）——**答案不是对代码的猜测，是变换本身的事实**。

### 1.2 两个结构性优势（判断）

| 编号 | 优势 | 为什么别人没有 |
|---|---|---|
| **I1** | **题目可再生 → 天然抗污染** | ALE 只敢公开 10%（150/1490）防污染；我们 100% 公开也不怕被背，因为重生成即可 |
| **I11** | **难度连续可调** | ALE-Bench 的开放上限是题目自带、不可调；ALE 的三层是离散的；我们的注入参数可连续调 |

### 1.3 已实测出的两条反直觉结论（事实，见 [13-难度旋钮验收](./13-难度旋钮验收.md)）

1. **旋钮对"已很难/已饱和"的题无效甚至反向**。分样本：`0001` 1.000→0.893、`0003` 0.941→0.488，
   但 `0002` **0.385→0.565**（它刻度 0 就只有 0.385）。
   → **不能用"把题调难"代替"把题出好"**；报告必须给分样本表，均值会把方向相反的效应抵消掉。
2. **耗时比 F1 更适合当难度硬指标**。1.8s → 30.6s（×17，严格单调），
   无判分器口径争议，且是真花掉的钱。误报率（chaff bug 误报数）0.00→0.67 也是严格单调。
   → **存在不依赖被测模型的难度代理指标**，这条后面会变成 H3。

### 1.4 现状的诚实边界（事实，别对外吹）

- `variation_k`（改写强度）**未接线**，四个旋钮实际只工作三个。
- 本机**没有 forge**，验证只能靠 CI；自我修正循环**无真实 forge 收敛数据**。
- Level 2 / Level 3 **未验证**；样本仅 7 个（实际是 4 道独立题加变体）。
- 现有任务是**微任务**（单文件 → findings 列表），不是宏任务。见 §4.1。

## 2. 外部版图（事实）

| 项目 | 规模 | 判分方式 | 最高水平 | 对我们的意义 |
|---|---|---|---|---|
| **ALE**（Agents' Last Exam） | 1500+ 长程真实任务，55 行业 | 端到端 full pass | Last-Exam 层 **2.6%** | 分级考试的源头；**只敢公开 10%** |
| **Terminal-Bench 2.0** | 89 题，3 人时人工审核 | 容器内隐藏测试，全通才算过 | 前沿 **<65%** | 宏任务范式；Harbor 的载体 |
| **ProgramBench** | 200 题 | ~248k 条 fuzz 行为测试 | fully 4.5% / almost 37% | 给二进制+文档**从零架构**，不给骨架 |
| **SWE-bench Verified** | 500 | 仓库测试 | **~97%，已饱和** | 通用代码题不该再做了 |
| **Harbor** | 框架 | task.toml + 容器 + tests + solve.sh | — | Terminal-Bench 2.0 官方 harness；**支持 RL rollout** |
| **DataFlow** | ~200 算子，6 条 pipeline | — | SIGMOD'27 | 算子/流水线抽象来源 |

**共同点**：ALE / Terminal-Bench / ProgramBench / Harbor **全部是宏任务**——
扔进一个装满文件的容器，要求产出**一个可验证的工作产品**。

## 3. OpenDCAI 家底与那个缺口

### 3.1 组织（事实）

北大张文涛组 **PKU-DCAI**，45 个公开仓、累计近万 star，定位 Data-Centric AI 基础设施。
同时是 `LLaMA-Factory`（65k⭐）与 `Camel` 的数据模块建设方。

### 3.2 与我们相关的九个仓

| 仓库 | ⭐ | 是什么 | 相关性 |
|---|---|---|---|
| **DataFlow** | 8.2k | 算子化数据准备（SIGMOD'27） | 抽象来源、主仓 |
| **DataFlow-Agent** | 12（最新） | DataFlow 化的 agent 轨迹合成 | **首选接入点** |
| **AgentFlow** | 140 | "First Unified Agent Data Synthesis Framework"，all-in-one 沙箱（RAG/Code/SQL/GUI/具身…） | **疑似 DataFlow-Agent 前身/兄弟，需确认** |
| **DataFlex** | 2.9k | NeurIPS'26 D&B；LLaMA-Factory 训练循环内的 Select/Mix/Reweight | 有**文档化扩展点** |
| **Data-Preparation-Bench** | 241 | 下游锚定的数据准备基准（Construction / Selection / Quality） | quality 赛道支持**自定义 metric** |
| **Paper2Any** | 2.8k | 论文 → 可编辑科研插图 / 路线图 / PPT | ⚠️ **legacy，不收新 PR** |
| **RayOrch** | 18 | Ray 上血缘可控多粒度 dataflow | 可托"可再生/可追溯" |
| **DataFlow-Skills / -Doc** | — | 算子开发规范、CI 规范 | 决定外部包怎么提 |
| One-Eval / DataMind / -KG / -MM / -LoopAI | — | 评测 / RAG / KG / 多模态 / 自优化环 | 次要 |

### 3.3 核心洞察（这是整篇的立论）

我把 OpenDCAI 整条 agent 数据栈翻了一遍：

> **从头到尾，没有一个 verifier。**

它们的质量信号只有两类：

1. **LLM-as-judge** —— `DataFlow-Agent` 的 `TrajectoryQualityEvaluator`（goal / efficiency / coherence / tool-use 四轴，1–5 分）
2. **分布或启发式** —— `AgentFlow` 用 depth + information richness + tool diversity 筛轨迹；`Data-Preparation-Bench` 用 DAS（MMD，training-free）估数据质量

**这两类都不是 ground truth。一个会说谎，一个不懂语义。**

而我们手里的是**第三类信号 —— 构造性信号**：
标签不是"判"出来的，是**这件东西被造出来的副产物**（注入动作顺手写下 `Issue`）。免费、精确、不可争辩。

**更关键的是**：验证这套信号有没有用的下游设施，他们**全都有了**
—— DataFlex 训练 + Data-Preparation-Bench 评测 + LLaMA-Factory。

**所以我们的定位不是"又造了个工具"，而是「这条流水线唯一缺的那个操作数」。**
这句话是去谈合作的第一句，也是论文 related work 的最后一节。

## 4. 核心假设与主张

### 4.1 一个必须先定的结构性分歧（判断，请推翻我）

我们现在的引擎产的是**微任务**：「看这一个合约 → 输出 findings 列表」。
而 ALE / Terminal-Bench / ProgramBench / Harbor 全是**宏任务**：「一个装满文件的容器 → 产出可验证的工作产品」。

**这不是换数据，是换题的定义。** 它决定架构图长什么样、验证器怎么写、代码怎么改。
我的判断：**必须转宏任务**，否则进不了 Harbor，也对不上 DataFlow-Agent 的 sandbox 抽象。

### 4.2 四条假设

| 编号 | 假设 | 怎么证伪它 |
|---|---|---|
| **H1**<br>可验证性可构造 | 在**没有天然 oracle** 的领域，只要给出 `(种子程序, oracle 程序, 变换族)` 三元组，就能产出 `(task, label, verifier)`，且 label 正确性由构造保证、无需人工标注 | 建不出审计域的 oracle 程序 |
| **H2**<br>奖励质量 | 用 verifier 奖励筛出的轨迹，下游训练收益优于 LLM-judge / 启发式筛出的；且对"看似成功实则失败"的轨迹**漏判率显著更低** | 一号实验跑出来无显著差异 |
| **H3**<br>难度可控 | 注入参数可连续调节难度，且存在**不依赖被测模型**的单调代理指标（耗时 / 误报率） | 换域后耗时不再单调 |
| **H4**<br>可再生抗污染 | 因为标签来自变换而非人工，公开生成器不会造成污染 —— 重生成即可 | 公开后模型分数仍显著上涨 |

### 4.3 主张（一句话）

> **把可验证奖励从"本来就有 verifier"的领域，扩展到需要构造 verifier 的领域。**

### 4.4 Novelty 的诚实边界（这段决定能不能过审，别自欺）

**不新**（别人做过，我们只是用）：
- RLVR 方法本身（Tulu-3 / R1 时代）
- 程序注入 / 变异测试（LAVA 2008、CyberForge）
- 差分测试
- 算子化数据流水线（就是 DataFlow）

**新**（我认为这是我们的增量）：
1. **适用范围的扩展** —— 今天 RLVR 只在"本来就有 verifier"的领域成立（math / code / SQL）。
   我们给出的是**构造 verifier 的通用操作**，让它能进无 oracle 的领域。
2. **构造性标签 = 第三类数据质量信号** —— 独立于 LLM-judge 与分布启发式，且能被 OpenDCAI 现成设施检验。
3. **不依赖被测模型的难度代理指标** —— 建 benchmark 通常要烧大量模型调用来标定难度，我们的耗时/误报率是免费且单调的。
4. **再生式基准协议** —— 用"公开生成器 + 每次重生成"替代"藏测试集"，回应 ALE 只敢公开 10% 的困境。

## 5. 交付：六个接入点与优先级

| # | 接入点 | 落在哪 | 价值 | 成本 | 评级 |
|---|---|---|---|---|---|
| **A** | `HarborSandboxClient`（实现 `SandboxClientABC`：`list_tools` + `execute`） | DataFlow-Agent | 中 | 低（300–600 行） | **必做** |
| **B** | `VerifierJudgeOperator` —— 用任务自带 verifier 替换 LLM-as-judge | DataFlow-Agent / AgentFlow | **最高** | 中 | **核心** |
| **C** | `VerifiedTaskSynthesis` 算子包 + `ArtifactStorage`（DataFlow 现有 Storage 只吃 JSON 表，装不下文件树） | DataFlow 主生态 | 高 | 高 | **主线** |
| **D** | `VerifierRewardSelector` / `Weighter` | DataFlex（有 `how_to_add_algorithm.md` 扩展点） | 高（闭环） | 高（要真训） | **第二篇入口** |
| **E** | 自定义 quality metric（verifiability score） | Data-Preparation-Bench | 中 | 低 | **低成本背书** |
| **F** | 用 Paper2Figure 出架构图 + 引其两篇论文 | Paper2Any / Paper2SysArch / SciFlow-Bench | 工具 | 极低 | **顺手** |

**建议节奏**：

```
P0（两周内出结果）：A + B   ← 唯一能在一次真机跑测里证实/证伪核心命题的东西
P1（主线）：        C       ← 把主张整个落成 DataFlow 的一个 domain package
P2（第二篇入口）：  D + E   ← 闭环 + 拿第三方背书
顺手：              F
```

**发布形式**：外部包 `dataflow-aule`，按他们 roadmap 的 claim 机制认领，**不硬推主仓**。
理由：我们还不熟他们的 CI / review 规矩，而第三方生态包 + claim 是官方认可的路；进主仓留给后面 PR-by-PR。

## 6. 实验设计

### Exp-1（一号实验，paper 的 Figure 2）

> 同一条 DataFlow-Agent pipeline、同一批 seed、同一个模型 —— **只换 backend**：
> `HTTPSandboxClient` + LLM-judge 　vs　 `HarborSandboxClient` + `VerifierJudgeOperator`。

量三件事：
1. **漏判率**：judge 把"看似成功实则失败"的轨迹判成好的比例（verifier 应为 0）
2. **下游收益**：各自筛出的轨迹去 SFT/RL，测下游差距
3. **成本**：judge 的 API 开销 vs verifier 的执行开销

### Exp-2（难度旋钮跨域单调性）

在合约 + 企业审计两个域跑 6 档 × 3 样本 × 3 次。
**主指标用耗时和误报率，不用 F1**（§1.3 已证 F1 在边界抖动）。
**必须给分样本表** —— 均值会把方向相反的效应抵消掉。

### Exp-3（再生抗污染）

公开全部生成器 + 种子 + 答案生成逻辑 → 隔一段时间重生成一批新题 →
测模型在新题上的分数是否与旧题一致（一致 = 没被污染，说明协议成立）。

### Exp-4（跨三域泛化）

合约 / 企业审计 / 电子数据审计，各跑同一套四组件 → 证明"换赛道只换四个类"是真的，不是 PPT。

### Exp-5（下游闭环，第二篇）

`VerifierRewardSelector` 接进 DataFlex → LLaMA-Factory 训练 → Data-Preparation-Bench 评测。

## 7. 风险

| 风险 | 后果 | 应对 |
|---|---|---|
| **verifier 奖励 vs LLM-judge 无显著差异** | 整个 idea 降级为"工程改进"，不能成篇 | 这就是 P0 先做 A+B 的原因 —— **尽早知道** |
| **审计域的 oracle 程序建不出来** | 退回只做 code 域，novelty 大打折扣（变成"第 N 个代码 RLVR 数据集"） | 先做 3 个算子验证可行性再铺开 |
| **P0「verifiable rewards」已被 lab 内部认领** | 撞车 | **必须先问**（见 §8） |
| **AgentFlow / DataFlow-Agent 选错** | 前期投入白费 | **必须先问** |
| **难度旋钮对已饱和的题反向** | 分样本表会暴露 | 已证，写进论文反而加分（诚实） |

### 9.2 术语纪律（延续 [15 篇](./15-术语审查与换词对照.md)）

- 注入 / 注入算子（不是"埋雷"）
