## 1. 术语硬伤：项目里有两个"审计"

这是本轮最先要解决的，因为它会让审稿人第一句话就问"你到底做的是哪个 audit"。

| 位置 | 实际在做什么 | 正确学科归属 | 标准词 |
|---|---|---|---|
| `engine/operators/{reentrancy,access_control,tx_origin}.py` | 往 Solidity 合约注入经典漏洞，PoC 用 Foundry 触发 | **区块链安全 / 智能合约安全** | smart contract security，**漏洞/故障注入 = vulnerability / fault injection** |
| `vts/audit_core.py` | 复式记账下篡改报表而不动明细账，用会计恒等式做判据 | **财务审计（财务报告审计）** | financial statement audit，**错报注入 = misstatement injection** |
| `engine/agents/audit_agent.py` | 给 Solidity 源码让模型报漏洞 | **智能合约漏洞检测** | smart contract vulnerability detection |
| `engine/scorers/report_score.py` | 对模型报告判 P/R/F1 | 跨域通用 | criterion-referenced scoring |

**处置**：

- **对外与论文里，中文一律区分**：智能合约那个叫**"合约漏洞检测"**，
  会计那个叫**"财务审计（错报检测）"**。绝不并列成"审计/金融/coding"——那是混词。
- 英文里 `audit` **只保留给财务审计**；合约那个一律用 `vulnerability detection` 或
  `smart contract security`。
- `engine/agents/audit_agent.py` 与 `vts/` 同名不同物，属于历史遗留，
  在论文的 artifact 描述里必须分开写，否则复现者会读错。

> ⚠️ 顺带一条纪律：`vts` 这个目录名（Verifier Test Suite）本身也是自造词，
> 但它指代清楚、不易误解，**可保留**，只需在论文首次出现时给一句定义。

## 3. 审计域（财务审计）：我们的学术位置在哪

这是三个领域里术语红利最大的一块，因为**审计学有 100 年的风险模型，我们的量能直接挂进去**。

### 3.1 审计风险模型的正式结构

PCAOB **AS 1101（Audit Risk）** 的原文结构是：

```
Audit Risk  =  Risk of Material Misstatement (RMM)  ×  Detection Risk
RMM         =  Inherent Risk  ×  Control Risk
```

原文对 **Detection Risk** 的定义（逐字）：

> "Detection risk is the risk that the procedures performed by the auditor
> will not detect a misstatement that exists and that could be material."

**逐字对照**：他们说的"审计程序未能发现**已存在的**错报"——
这正是我们说的**漏报（FNR）**。区别只在于：

| | 传统审计 | 我们 |
|---|---|---|
| Detection Risk | 只能**定性评估**（substantive procedures 的性质/时间/范围） | **可定量实测** |
| 怎么定 | 注册审计师凭职业判断 | 构造性 reference oracle，零人工标注，毫秒级，可复现 |
| 抽样 | 统计抽样，有抽样风险 | 全域枚举（我们账套可完整遍历） |

**⇒ 这就是我们的立论，而且不需要我们自己造词**：
> 审计准则把 Detection Risk 定义为一个乘数项，但行业只能定性对待它；
> 我们第一次能在**零人工标注**的前提下把它算成一个带置信区间的实数。

### 3.2 我们的三个层对应审计准则的哪一层

| 我们的术语 | 审计准则术语 | 准则出处 |
|---|---|---|
| 检测层 FNR | **Detection Risk** | AS 1101 §.09 |
| 归因层 FNR | **assertion-level misattribution** | AS 2110（认定层风险） |
| 结构性不可见 | **assertion 未被程序覆盖**（procedures not responsive to the assessed RMM at assertion level） | AS 2110 / ISA 315 |
| FPR（在干净报表上报警） | **false-positive detection / overstatement of detected risk** | 实务术语，非准则术语，**要自己定义清楚** |
| 报告的四维评分 | **finding quality: detection / accuracy in assertion / severity / documentation** | 我们自定，需给效度论证 |

### 3.3 财务域的 assertion 分类（我们的注入算子应对齐它）

审计准则把错报风险在**认定（assertion）层**评估，通行分类
（ISA 315 / CAS 190 / PCAOB AS 2110 体系）：

`existence` 存在性 ｜ `occurrence` 发生 ｜ `completeness` 完整性 ｜
`accuracy` 准确性 ｜ `valuation` 计价 ｜ `rights and obligations` 权利和义务 ｜
`presentation and disclosure` 列报与披露

**我们当前的三类注入算子应显式映射到 assertion**，这样才进得了审计的话语体系：

| 我们的注入（`vts/audit_core.py`） | 应归 assertion | 审计准则下的典型舞弊手法 |
|---|---|---|
| 只改报表不改明细账 | **completeness** / **existence** | 虚增收入、未记录负债（side agreements） |
| 收入跨期（提前确认） | **occurrence**（cutoff） | 提前确认收入 / 推迟确认费用 |
| 费用资本化 | **classification**（presentation） | 资本化利息、费用转资产 |
| 应收坏账计提不足 | **valuation** | 减值计提不足 |
| 关联方未披露 | **presentation and disclosure** | 未披露关联交易、关联方资金占用 |

**⚠️ 这是 A0 的一处硬要求**：会计域的 ≥4 档难度，**必须是四个不同 assertion**，
而不是同一 assertion 的四个强度档。理由：审计准则的整个风险模型是按 assertion
分层构建的，同 assertion 的难度档在学科上等价于"同一条风险调了个量"，没有独立意义。
**这一条会改 A0 的样本设计，此前方案没写。**

### 3.4 保险与"保证层级"——这是 τ 的正式落点（见 §5）

审计准则有**保证层级**与**结论形式**的正式区分：

| 业务 | 准则 | 保证层级 | 结论措辞 |
|---|---|---|---|
| 审计 audit | ISAE 300（上市实体） | **reasonable assurance** 合理保证 | **positive expression** 积极式 |
| 审阅 review | **ISAE 2402** | **limited assurance** 有限保证 | **negative expression** 否定式（"nothing has come to our attention…"） |

⇒ **τ>0 ≈ positive assurance**（可作审计级用）
⇒ **τ<0 ≈ negative assurance**（只能作审阅级用）

⚠️ **但 §5.1 的实测已细化这条**：J<0 有两种成因，审计准则的降级映射只适用于 (a)。
- (a) 真反转（极性接反，取反可救）
- (b) FPR 主导的过度敏感（取反更差）—— **pro 实测属此类**
⇒ 论文不得笼统写"J<0 ⇒ 降级为审阅级"，必须先区分成因。

## 4. 金融域：术语要往"财务报告 + 保证"上靠，不要往"量化投资"上靠

我们做的是**财务报告语境下的 AI 审计**，不是 alpha/交易。术语必须区分，否则投错审稿人：

| 应该用（财务报告 / 审计） | 不要用（会投错方向） |
|---|---|
| financial statement audit / financial reporting | quant finance / alpha / trading |
| misstatement detection | fraud detection（**舞弊 vs 错报是两个概念**：舞弊含推定舞弊 management override，且准则要求 ASA 240 单独应对；我们注入的应严格称 misstatement） |
| XBRL、SEC 10-K/10-Q、内控 over financial reporting | — |
| assertion-level risk | model risk（银行巴塞尔语境，不同） |
| going concern、revenue recognition (ASC 606) | — |
| reasonable assurance / **long-horizon engagement** | — |

**一条必须写进论文的定位句**：
> 金融域的长时程属性不是我们的包装，而是**审计业务的本质**——
> 一次真实财务审计约 **15 人时**（Theta Software 金融长时程基准的实测口径），
> 且天然是**顺序依赖**任务（前期决策改变后续可得证据），
> 正好落在 long-horizon task 定义内。

## 5. 测量学与信号检测：三条白拿的红利（本轮最值钱的发现）

### 5.1 🔴 τ 就是 Youden's J index（决定性）

我们的信号保留因子：

```
τ = 1 − FPR − FNR
```

信号检测理论（Signal Detection Theory, SDT）里，Youden 1947 定义的判别指数：

```
J = Sensitivity + Specificity − 1
  = TPR + TNR − 1
  = (1 − FNR) + (1 − FPR) − 1
  = 1 − FNR − FPR          ← 与我们的 τ 完全相同
```

**⇒ τ 在学科里就是 Youden's J。** 这一步给了我们三件事：

1. **J 的取值范围是 [−1, 1]，且 J = 0 有精确含义**：
   `J = 0 ⟺ TPR = FPR ⟺ ROC 曲线落在随机猜测对角线上 ⟺ d' = 0 ⟺ 无判别力`。
   我们此前说"τ<0 是反转区、τ>0 是同向区"，用 J 的语言是**教科书表述**，
   不再需要我们自己论证分界线的合法性。

2. **J<0 在学科里有名字**：`reversed discrimination`（判别反转）。
   概率上"把错判成对"比"把对判成错"更可能。
   ⇒ 我们的贡献表述从"我们发现误报把训练方向带反"（被 2510.18924 的定理推翻过）
   升级为：**"我们首次在 LLM verifier 上系统测出判别力跨过 d'=0"**。
   注意措辞——前者是定理的直接后果（不是新发现），后者是关于 verifier 的新事实。

3. 🔴 **J 必须分层计算，实测证明分层与端到端符号相反。**

   这是本轮实测最重要的一条纠正。按 arm 分别算 J_detection 与 J_end2end：

   | 模型 / arm | det_FNR | attr_FNR | e2e_FNR | FPR | **J_det** | **J_e2e** |
   |---|---|---|---|---|---|---|
   | flash A | 0.500 | 0.150 | 0.575 | 0.100 | **+0.400** | +0.325 |
   | **flash B** | 0.113 | 0.422 | 0.487 | 0.925 | **−0.038** | **−0.413** |
   | flash C | 0.494 | 0.012 | 0.500 | 0.000 | **+0.506** | +0.500 |
   | **pro C** | **0.070** | 0.333 | 0.380 | 0.800 | **+0.130** ⚠️ | **−0.180** ⚠️ |

   两个必须写进论文的后果：

   - **pro 在检测层判别力是正的（+0.130），只在端到端层转负。**
     机制已核清：`e2e_FNR = 1 − (1−det)(1−attr) = 1 − 0.930×0.667 = 0.3797`，
     与实测 0.380 吻合到小数点后三位 ⇒ **归因层的 0.333 把检测层的优势全部吃掉**。
     诊断结论因此完全不同：**pro 不是"判别力反转"，是"检测极准但归因不可靠，
     而误报率高达 0.800 把端到端判别力拖到负区"**。
   - ⚠️ **我原先推断"pro 是极性接反，取反即可修复"——被数据否掉。**
     取反后 FNR=0.800 / FPR=0.070，比原来的 FNR=0.070 / FPR=0.800 **更差**。
     ⇒ **J<0 不能一律解释为"极性反了、可用取反修复"**。
     必须区分两种成因：(a) 真反转（取反可救）；(b) FPR 主导的"过度敏感"
     （取反会更差，只能靠调阈值/减敏感度）。**我们测到的 pro 属于 (b)。**
     这条纠正了此前文档里"τ<0 ⇒ 该 verifier 只能作审阅级用"过于简化的说法。

4. **J 的符号不是模型属性，是 arm（提示配置）属性。**
   flash 的 B arm J=−0.038 为负、C arm J=+0.506 为正，**同一模型不同配置符号相反**。
   ⇒ "某个模型判别力为负"这种表述是错的，正确表述是
   **"该 verifier 在该提示配置下的判别力为负"**。
   这也顺带证明把 J 作为可调量（而非模型固有属性）来研究是成立的。

5. **🔴 J 失效的第三种情形：参照层本身没有分辨力（2026-10-05 实测新增）。**
   上面 (a)(b) 两类讲的都是**被测verifier** 的问题。但还有第三种：
   **若参照 oracle 无法区分难度档位，则"J 随难度的变化"在构造上就不可测量。**

   实测事实：四个注入算子分属四条不同审计认定，但违反的 oracle 集合**完全相同**
   （`{o_tie_detail, o_rollforward}`），4 条 oracle 中 2 条**从未被任何算子触发**。
   ⇒ 参照层只提供一个比特的信息，**四档难度退化为同一档**。

   ⚠️ 这属于 **measurement validity** 问题，不是准确率问题：
   即使 J 算得很精确，它描述的也只是"**判分器在这一个构念上的**判别力"，
   而非"判分器在四个难度上的判别力"。
   ⇒ **在 F1–F4（oracle 按认定分层）通过之前，任何"J 随难度变化"的表述都不成立。**
   详见 `28-A0前置诊断与方案迭代v5.md`。

   ⚠️ 这也是本项目"看似生效实则失效"的**第 5 类坑**：
   判据从"集合相等"放宽到"包含"后 DIC 通过、指标变好，
   **但被测量的构念被悄悄换掉了**。与"伪装类算子自曝身份"同类——
   **指标达标不等于测到了想测的东西**。

### 5.2 σ=0 退化区的正式说法

我们称"σ=0 退化组"。在 GRPO 文献里这是 **zero-variance group**：
group-normalized advantage `A_i = (r_i − mean)/std` 在组内奖励全同时 `std = 0`，
group 内样本全部零优势、**该组不产生梯度**。

正式表述（论文里用这个）：
> **degenerate group collapse**：当 verifier 在一组样本上给出全同奖励时，
> GRPO 的 group-normalized advantage 归零，该组贡献零梯度。
> 我们在 `equation_only` 条件上观测到 **100% 退化组**，且系统不报错。

⚠️ 注意口径：`2510.18924` 只在介绍 Dr.GRPO 时提过
"identical group rewards yield zero gradient"，**未做系统分析**——这条仍成立，
但**不能用我们早先的措辞暗示这是我们发现的机制**，只能声称"我们提供了实证与规模刻画"。

### 5.3 测量学词汇：我们的信度理论用在 verifier 上

教育测量学（classical test theory）的核心对象是**测验的信度与效度**。
我们做的是把同一套工具用在**判分器**上，这个迁移本身值得写进论文：

| 测量学 | 我们用它做什么 |
|---|---|
| `criterion-referenced`（标准参照）vs `norm-referenced`（常模参照） | 我们的分数是**绝对参照**（对构造真值），不是排名参照 |
| `reliability`（信度） | verifier 在同一题上的**重测一致性**（我们已有 repeat=3 多数投票 + 分歧率） |
| `construct validity`（构念效度） | verifier 是否真的在测它声称测的东西（**AutoBenchmark 用了这个词，我们审计的正是它的效度**） |
| `test information` / `item difficulty bᵢ` | 难度参数化 |
| `nonparametric IRT`（Rasch / 1PL） | 我们已有 `fit_rasch`，是三条骨架之一 |

**一条更锋利的表述**：
> 现有工作把 verifier 的效度当作**假设**，把 verifier 的分数当作**数据**。
> 我们把 verifier 本身当作**测量工具**来评估其 reliability 与 construct validity——
> 这在方法论上等价于"用测量学审计测量工具"，其前提是存在构造性真值。

## 6. coding 长时程域：术语与红线

### 6.1 我们的注入算子在 coding 域有确切学术名，且**已被研究透了**（红线）

我们的合约注入算子，在软件测试里就是 **mutation operator**，产物是 **mutant**，
检出与否是 **mutation score / kill rate**。而这一支已经有完整实证：

> **arXiv:2406.09843**（Wang, Chen, Deng, Lin, **Harman**, Papadakis, Zhang；
> TOSEM/JFCS）— 851 个真实 Java bug、7 个 LLM、BugFarm/LLMorpheus/新 prompt。
> - 真实缺陷检出率：**LLM 87.98% vs 规则基线 41.64%**（+46.34 pp，相对 +111.29%）
> - 代价：non-compilable **+26.60 pp**、duplication **+10.14 pp**、
>   equivalent mutant **+3.51 pp**
> （早期版本另报 77.4%/79.1% 等数字，**引用一律用最终版 87.98%/41.64%**）

**⇒ 红线：coding 域我们绝不能声称"我们让注入更真实/更有效"。**
这条路已被 UCL 这篇做完了，且做在更强的证据上（真实 bug、851 个）。

我们能卖的只有一句：
> 变异体的**有效性**已有充分研究；**谁在检查这些变异体**（即 verifier / 判分器）
> 的可靠性从未被测量。

**而这个缺口恰好成立**——变异测试里"变异体活着"被解释为"测试套件不够"，
但把同一批变异体喂给 LLM judge 时，**judge 的漏检率没有任何人测过**。
mutation testing 关心的是 *test suite adequacy*，我们关心的是 *judge adequacy*。

### 6.2 coding 域的定位（用长时程任务的标准语言）

| 我们的能力 | 长时程任务的标准术语 | 出处 |
|---|---|---|
| 难度连续可调 | **controlled / continuously parameterized difficulty** | 我们原创表述 |
| 耗时 ×17 严格单调 | **horizon length scaling**（工作量随难度线性增长） | 与 human-hour / token / episode 三种度量并列 |
| 三层考试 | **difficulty-stratified evaluation** | |
| 变体生成 | **semantics-preserving task variants**（蜕变关系 MR） | software testing |
| 判分器审计 | **verifier reliability / outcome reward model (ORM) adequacy** | RLVR 文献 |

**coding 域现状判断（必须写清，别含混）**：
> coding 域有大量"任务难度不可调"的基准（SWE-bench Verified 等固定数据集）。
> 我们在该域的贡献**不是新任务**，而是
> **在可连续参数化的任务族上测量 verifier 误差随难度的形状**。

### 6.3 长时程任务的度量口径（引用时要准）

长时程任务没有单一公认度量，通行三种，**论文必须声明用哪一种**：

- **human-time**（人时）：最接近"真实工作量"，Theta Software 金融基准用，平均约 15 人时
- **token consumption**：LLM 口径，噪声大
- **episode / step count**：可复现，与 agent 框架强耦合

⚠️ **我们用的"耗时秒数"属于哪一种？答案是 execution wall-clock，
不属于以上任何一种标准口径。** 它是真实工作量、跨模型可比、无判分器依赖，
但**不能声称与 human-hour 对齐**。论文里必须原话写明：
> 难度以 agent execution wall-clock 刻画（非 human-time、非 token），
> 该度量不可由人工时间直接换算。

**这条不写会被审稿人当场抓住。**

## 7. 三领域统一后的定位（论文摘要级表述）

```
框架名（保持 AuLE，不再改）：
  AuLE = Auditable Verification and Learning Environment
       —— 可审计的判分环境（不是"考试院"，是"判分环境的可审计性"）

统一主命题（三领域共用，一个判分器）：
  对任何判分器 v，我们给出零人工标注的
  (Detection Risk, False Positive Rate) 及其 J-index，
  并测出它随任务难度（连续参数化）的形状。

三领域的分工（注意不是并列的三个"审计"）：
  财务审计域（会计）  —— 主战场。承接审计准则 Detection Risk 的既有定义，
                          拿到制度性合法性 + 甲方需求。
  金融域              —— 财务报告语境的长时程审计（同上，但数据来自公开披露）
  coding 长时程任务    —— 方法学外化。注入算子 = mutation operator（已有文献），
                          我们测 judge adequacy（无人做），并用可连续参数化的难度。

三域的差异只在"错报/故障的语义"，机制层完全共享：
  构造性真值 → 误差测量 → J 记账 → 保证层级判定 → RL 后果
```

**一句话对外话术（每域一句，都用学科词）：**

- **审计域**：
  "审计准则把检查风险定义为审计风险模型的一个乘数，但行业只能定性对待；
  我们用构造性参照把它算成带置信区间的实数，并测出它随难度与断言类型的形状。"
- **金融域**：
  "财务审计是天然的顺序依赖长时程任务，平均约 15 人时；
  我们在这类任务上测量判分器的可靠性，给出可交付的保证层级判定。"
- **coding 域**：
  "LLM 生成的变异体有效性已有充分实证（851 个真实缺陷，检出率 87.98% vs 41.64%）；
  但从没有人测量**检查这些变异体的判分器**有多可靠——我们测这个。"
