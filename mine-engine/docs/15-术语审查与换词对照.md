# 15 · 术语审查：哪些是行业真词，哪些是我们自造的

> **触发原因**：我们一直用"埋雷""健康体""考试院"讲自己的系统。
> 查证后发现——**这三个词在 DataFlow / ALE / ALE-Bench / Harbor 里都不存在**。
> 自己造词不是错，但**对外场合用自造词等于自缚**：
> 审稿人/工程���第一反应是"这不是我们这行的说法"，然后就不接了。
>
> 本文做三件事：① 逐词判定来源；② 给出替换词与出处；
> ③ 说明哪些**故意保留**（自造词有时是对的）。
>
> 版本：2026-10-03 ｜ 依据：DataFlow arXiv:2512.16676、ALE arXiv:2606.05405、
> ALE-Bench arXiv:2506.09050、Harbor（Terminal-Bench 团队）、
> Chaff Bugs arXiv:1808.00659 (CCS'18)、LAVA/LAVA-M、CyberForge arXiv:2608.06471

---

## 0. 一句话结论

```
DataFlow  里没有"埋雷"    → 它的词是 Generate / Evaluate / Filter / Refine
ALE       里没有"埋雷"    → 它的词是 task / gate-and-score / held-out / contamination
Harbor    里没有"埋雷"    → 它的词是 task / environment / tests / verifier / reward
漏洞注入领域里没有"埋雷"  → 它的词是 vulnerability injection / injected / PoV / chaff bugs

"埋雷"是我们自造的。    → 换成 vulnerability injection（学界），
                          中文明说"注入漏洞"（不用"埋雷"）。
```

**"埋雷"唯一的毛病是它是中文口语里的军事比喻**，进英文论文就变成一个
找不到出处的词；进中文对外演讲倒是能懂。**建议：代码/论文里换词，
口头演讲可以保留"埋雷"这个比喻，但第一次出现时立刻给出学界对应词。**

## 1. 逐词审查表

图例：✅ 行业标准词 ｜ ⚠️ 自造但可接受（需加注释） ｜ ❌ 应换

| 我们的说法 | 判定 | 应改为 | 出处 / 说明 |
|---|---|---|---|
| **埋雷** | ❌ | **vulnerability injection**（注入漏洞）<br>中文"注入漏洞" | LAVA / LAVA-M / CyberForge 官方用词。**DataFlow、ALE、Harbor 全都不用这个说法** |
| **雷** | ❌ | **injected vulnerability**（注入的漏洞）<br>或 **bug** | 同上 |
| **埋雷算子** | ❌ | **injection operator** | 保留"算子"（DataFlow 用词），换掉"埋雷" |
| **健康合约 / 健康基准体** | ❌ | **seed program**（种子程序）<br>或 **clean version** | LAVA/CyberForge 用 `seed program`；CyberForge 用 `clean build`。**"健康"是我们的直译自造** |
| **干净版本** | ⚠️ | **clean version** 即可 | "clean"在变异测试（mutation testing）里是标准对偶词 |
| **planted** | ⚠️ | **injected** 或 **vulnerable version** | `planted bug` 在软件测试里有"故意植入的缺陷"含义（defect seeding），**不算错**；但论文里 `injected vulnerability` 更常见。⚠️ 见 §3 |
| **诱饵** | ❌→✅ | **chaff bug**（诱饵漏洞） | **arXiv:1808.00659 (CCS'18) 正式术语**，定义与我们完全一致：<br>*provably but not obviously non-exploitable* |
| **decoy** | ⚠️ | 英文可用 `decoy`，但学术语境建议 `chaff bug` | `decoy` 在军事语境是"诱饵弹"；软件安全文献里 `chaff bugs` 才是命名 |
| **差分验证** | ✅ | **differential validation** | CyberForge 原文：*differential proof-of-vulnerability oracle*；McKeeman 1998 提出 `differential testing`（编译器领域经典）|
| **ground truth / 标准答案** | ✅ | 保留 | 通用 |
| **PoC** | ✅ | 保留，但**注意区分** | 见 §4：我们 Level 2 的 PoC 与 `proof-of-vulnerability` 不完全等价 |
| **算子 / Operator** | ✅ | 保留 | DataFlow 核心用词 |
| **流水线 / Pipeline** | ✅ | 保留 | DataFlow 核心用词 |
| **考卷 / 考试院** | ⚠️ | 保留为**比喻**，但别当术语用 | ALE 自己用 `exam`（"Last Exam"），比喻是通用的；只要不写成"我们的术语"就没事 |
| **闸门 / gate** | ✅ | 保留 | ALE 的 `gate-and-score` 是正式术语 |
| **判卷 / 判分器** | ✅ | `verifier` / `scorer` | Harbor 用 `tests/` + verifier；**"判卷"是中文比喻** |
| **样本 / sample** | ✅ | 保留 | 通用 |
| **难度旋钮** | ❌ | **difficulty knob** 可接受，但建议 **difficulty scaling** 或 **controlled difficulty manipulation** | `scaling` 是这个领域描述"连续调难度"的标准动词（task scaling / difficulty scaling）|

## 2. DataFlow 怎么解释（学它的说法）

DataFlow（arXiv:2512.16676，北大 DCAI）的官方表述，**它反而是我们的上游**：

> "基于**算子（operator-based）**的设计，DataFlow 将整个数据清洗工作流
> 转化为可重现、可重用、可共享的**流水线（pipeline）**。"
> —— README-zh 原文

### 2.1 它的分层（我们说"架构"时应对齐这套）

```
Pipeline  →  Operator  →  Prompt
                 ↓
        Storage（数据管理）+  Serving（LLM 服务）
```

官方 demo 的调用方式（原文）：

```python
from dataflow.operators.core_text import PromptedGenerator
from dataflow.utils.storage import FileStorage
from dataflow.serving import APILLMServing_request

storage  = FileStorage(first_entry_file_name="./input.json")
llm_serving = APILLMServing_request(api_url="https://api.openai.com/v1/chat/completions")

prompted_generator = PromptedGenerator(llm_serving=llm_serving,
                                      system_prompt="Please solve this math problem.")
prompted_generator.run(storage=storage.step(),    # 数据管理
                       input_key="problem",      # 从该列读取
                       output_key="solution")    # 写入该列
```

> **要点**：DataFlow 的算子**不改变 schema 之外的语义**，
> 它是"读一列 → 处理 → 写一列"的表格化流水线。
> **存储（Storage）是一等公民**，不是 `dict` 随手传。

### 2.2 它的算子四分类（我们该照抄）

官方明确分四类：

| DataFlow 分类 | 含义 | **我们对应的组件** |
|---|---|---|
| **Generate** | 生成数据 | `ContractGenerator` + 三个**注入算子** |
| **Evaluate** | 打分/评估 | `FoundryDiffValidator`（差分验证）+ `ReportScorer` |
| **Filter** | 过滤 | `dedup`（指纹去重）+ AI filter |
| **Refine** | 精炼/改写 | `VariationOperator`（LLM 语义保持改写）|

> **这是一个重要的对齐发现**：我们把组件分成
> `ArtifactGenerator / IssueOperator / IssueValidator / ReportScorer`，
> 这是**我们自己发明的四分法**（按"出题流程顺序"分的）。
>
> DataFlow 的四分法是**按功能性质**分的。两者不冲突，但**对外描述时
> 用 DataFlow 的分类更有说服力**——因为它是 200 个算子、6 个领域验证过的框架。
>
> 对应关系：`IssueOperator` 属于 Generate 类；`IssueValidator` 属于 Evaluate 类；
> `dedup` 属于 Filter 类；`VariationOperator` 属于 Refine 类。
> **我们缺的是 Storage 与 Serving 两个一等公民**（已在代码实现方案里记为未做）。

### 2.3 学 DataFlow 的一个措辞习惯

它把同类算子按用途命名，而不是按对象：
`PromptedGenerator`（用 prompt 的生成器）、`APILLMServing`（API 服务）。

> 我们可以照此把三个注入算子重命名，让"它们是 Generate 类"一眼可见：
> `ReentrancyInjector` → 已经是 `Injector`，**这个 `-or` 后缀是对的**，符合 DataFlow 风格
> （`Generator`/`Operator`/`Refiner` 都是施动者命名，不用名词）。

## 3. `planted` 要不要改？（一个真实的判断题）

**结论：代码里可以保留 `planted`，论文里改 `injected`。理由如下。**

`planted bug` / `planted defect` 在软件测试文献里确有含义——
指"故意植入的缺陷"，相关技术叫 **defect seeding**（见 Software Testing Glossary）。
所以**这个词不是我们发明的**，用它不算外行。

但有两点不利：
1. **它太泛**：`planted` 在密码学、博弈论里还有其他含义（planted cipher、planted LWE），
   在安全语境里会引入歧义。
2. **它不区分"雷"和"答案"**：我们的 `planted_source` 是"注入后的代码"，
   `planted` 本身没有表达"含已知漏洞"这层意思。

**建议的最小改动**（不动数据集目录名，避免破坏 7 个样本与已有结果）：

| 位置 | 现状 | 改为 |
|---|---|---|
| 论文/对外叙述 | planted vulnerability | **injected vulnerability** |
| 论文里"埋雷" | — | **vulnerability injection** |
| 论文里"健康合约" | — | **seed program** 或 **clean version** |
| 论文里"诱饵" | decoy | **chaff bug**（引 CCS'18）|
| 代码内部 | `planted_source` / `planted_contract_name` | **保留**（见 §6 风险说明）|

> ⚠️ **为什么不改代码**：数据集目录名是 `datasets/sample-0001/planted/`，
> `index.jsonl` 里 7 行都含这个路径，已有的 `harbor_tasks/`、
> `results_*.json` 全部引用它。改名要同步 21 个 py 文件 + 重建数据集 + 重跑全部结果，
> **而收益仅仅是措辞**。**这属于"改了更划算"之外的情况——不值得。
>
> 但**论文和对外材料必须改**，因为那才是被审稿人看的地方。

## 4. 一个必须分清的术语：PoC ≠ proof-of-vulnerability

我们 Level 2 叫 "PoC"，但**漏洞研究领域有个更严格的词**：

| 词 | 含义 | 严格程度 |
|---|---|---|
| **PoC**（proof-of-concept） | "证明这个漏洞能被打"的代码 | 宽松——能跑就行 |
| **PoV**（**proof-of-vulnerability**） | 满足**差分条件**的可执行制品 | 严格——必须在注入版上触发、在官方修复版上不触发 |

CyberForge（arXiv:2608.06471）的原文定义：

> "a generated PoV must **trigger on the injected build** while leaving
> the **clean build** unaffected."

**我们其实做的是 PoV，不是 PoC。** 因为我们的验证器要求三件事同时成立：
① 注入版攻击成功 ② 清洁版攻击失败 ③ happy-path 全过。
这正是 PoV 的差分定义。

> 💡 **这是一个可以白拿的学术加分项**：
> 论文里把 Level 2 改成 "**PoV-based exploitability verification**"，
> 直接蹭上 CyberForge / LAVA 的表述体系，
> 而且**准确描述了我们比"写个 PoC"更严格的地方**。
> 顺带把 `run_exploit.py` 的输出从"打穿率"改成"**PoV 验证通过率**"。

## 5. 三个"故意保留"的自造词

不是所有自造词都要改。以下三个**故意保留**，但必须加注说明：

| 词 | 为什么保留 | 必须加的注释 |
|---|---|---|
| **AuLE**（Adaptive Audit Last Exam） | 项目代号，对标 ALE 的 `Last Exam`，是刻意设计的双关 | 首次出现时说明"借用 ALE 的 exam 意象" |
| **难度旋钮**（difficulty knob） | 中文直觉、类比直观（相机旋钮），比 `difficulty scaling` 好懂 | 英文写作时用 `difficulty scaling`，中文保留"旋钮" |
| **考试院** | 传达"批量产题"的核心差异，对外叙事有力 | 明确这是**比喻**，并立刻给出学界说法（`vulnerability injection pipeline`）|

> **判断标准**：
> **能查到出处的词 → 一律换成学界词**（埋雷 → vulnerability injection）。
> **查不到出处但直觉强的词 → 保留 + 注明是比喻**（考试院、旋钮）。
> 别把"我们内部能用"当成"对外能说"。

## 6. 换词的风险清单（诚实说明）

**改了会不会坏？分三类：**

| 类别 | 影响 | 处理 |
|---|---|---|
| 论文/文档措辞 | 零风险 | ✅ 已改 |
| 代码标识符（21 个文件含 `planted`）| 中风险——要重建数据集 + 重跑全部结果 | ⚠️ **不改**，见 §3 |
| 数据集目录名 | 高风险——7 样本 + 所有 results/*.json 引用 | ❌ **不改** |

**所以本次改动只发生在措辞层，不动代码数据结构。**
唯一例外：如果将来要写论文，建议在**代码里加一层别名**（比如
`injected_source` 作为 `planted_source` 的 property），这样论文里的词
和代码能对上，又不用动数据集——这个等真的要写论文时再做。

## 7. 对外场合的措辞速查（照着念就行）

| 场景 | ❌ 别用 | ✅ 用 |
|---|---|---|
| 介绍方法 | "我们的埋雷引擎" | "我们的 **vulnerability injection** 引擎"（中文可说"漏洞注入引擎"）|
| 讲输入 | "健康合约" | "**seed program**"（中文"种子程序"）或 "clean version" |
| 讲输出 | "埋雷版" | "**injected version**"（中文"注入版"）|
| 讲诱饵 | "诱饵函数" | "**chaff bug**"（引 arXiv:1808.00659），中文可说"诱饵漏洞" |
| 讲验证 | "差分验证" | "**differential validation** / **differential PoV oracle**" |
| 讲 Level 2 | "PoC 打穿率" | "**PoV 验证通过率**"（更准确，且是标准词）|
| 讲框架 | "我们重新发明了流水线" | "沿用 **DataFlow**（arXiv:2512.16676）的算子/流水线抽象" |
| 讲难度 | "难度旋钮" | "**difficulty scaling**"（中文可保留"旋钮"）|
| 讲整体 | "考试院" | "**a benchmark-generating pipeline**"，中文比喻可加"考试院" |

## 8. 一句话总结

> **我们方法上做的事，和学界已有术语几乎一一对应**：
> 埋雷 = vulnerability injection（LAVA 2008 起）、
> 健康合约 = seed program、
> 诱饵 = chaff bug（CCS'18）、
> 差分验证 = differential PoV oracle（CyberForge 2026）、
> PoC 打穿 = PoV verification、
> 算子流水线 = DataFlow 算子体系（arXiv:2512.16676）。
>
> **这说明我们的设计没有跑偏**——方法论早就有成熟词汇，
> 我们只是用中文比喻重新发明了一遍。
> **对外发言时改用学界词，等于直接接上了一条已有的文献链**，
> 审稿人不用先花时间理解我们的黑话，再去判断我们的工作。
>
> ⚠️ 但也要诚实说清一件事：
> **术语正确 ≠ 贡献新。** 上面这些对应关系说明我们的方法"站得住脚"，
> 但不说明我们比 LAVA 或 CyberForge 更强——
> **我们的增量在"难度连续可调"和"可再生抗污染"两处**，
> 这两个才是需要靠 §13/§12 的实测数据支撑的立论。
