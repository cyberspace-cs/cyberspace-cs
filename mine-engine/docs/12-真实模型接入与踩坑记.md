## 1. 模型名必须核对：你给的名字 ≠ 网关实际名字

这是第一个必须"跑一遍才知道"的坑。

| 你给的名字 | DeepSeek 官方网关实际行为 | 正确名字 |
| --- | --- | --- |
| `deepseek-v4.1-flash` | **直接 400**（"supported models are deepseek-flash, deepseek-v4-pro"） | 用 `deepseek-flash` |
| `deepseek-v4-flash` | **静默换成 `deepseek-flash`**（响应 `model` 字段变了，不报错） | `deepseek-flash` |
| `deepseek-v4-pro` | ✅ 可用 | `deepseek-v4-pro` |

> ⚠️ **静默换名最危险**：你以为在跑 v4-flash，其实跑的是 flash，分数还对得上，
> 直到某天换了 prompt 才发现两模型行为不同。**务必看响应里的 `model` 字段，而不是请求里的。**

DashScope 上的名字则是另一套：`deepseek-v4.1-flash`、`deepseek-v4-flash-0731`、`qwen3.8-flash`、`qwen3.8-max` 都存在（只是账户欠费调不动）。

## 2. thinking 截断陷阱（最隐蔽的坑）

DeepSeek 的模型**默认开启 thinking（推理）模式**：先烧一堆 token 在"思考链"上，再吐正式答案。

**实测**：`deepseek-v4-pro` 在 `max_tokens=1024` 时——
- `usage.completion_tokens = 1024`（正好打满）
- `content = ""`（空）
- HTTP 状态码 **200**，usage 完整

从外面看"一切正常"，分数却**悄悄变成 0**。这类"看起来正常的失败"比报错危险得多。

**已修复**（`engine/llm/client.py`）：
- 客户端默认值从 `1024` 提到 `4096`，`.env` 里给到 `8192`；
- 新增 `truncated` 判定：答案为空 且 `finish_reason=length` 或输出 token 贴着上限 → 报警（Python warning），`--strict` 时直接抛错；
- `LLM_MAX_TOKENS` / `LLM_THINKING=off` 两个环境变量可临时调（后者关掉 thinking，更快更省）；
- **按应答里实际的 `model` 字段记账**，避免"被换名"导致算错单价。

修复后用 `LLM_MAX_TOKENS=8192` 再跑，两个模型都不再出现空答案（见第 4 节）。

| model | Recall | Prec | F1 | Wall(s) | Tokens | Cost | Solved | $/solved | 空答 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| deepseek-flash | 0.757 | 0.752 | 0.730 | 12.5 | 5,391 | $0.0037 | 5/7 | $0.0007 | 0 |
| deepseek-v4-pro | 0.836 | 0.921 | 0.871 | 115.1 | 13,834 | $0.0456 | 6/7 | $0.0076 | 0 |

- 7 个样本太少了，F1 的差距**不显著**，别拿这个数当结论。

## 7. 难度旋钮实跑暴露的三个坑（第四步验收，2026-10-02 晚）

第四步的难度旋钮写完后，我第一次用真实模型扫难度曲线，**结果和预期相反**：
刻度 0 的 F1 是 0.749，刻度 1 反而涨到 0.817。查下来是三个叠在一起的坑，
每一个都单独足以让"旋钮看起来在工作、其实完全没生效"。

### 坑 7.1 · 诱饵自曝身份 → 旋钮退化成"只加长度不加难度"

最初诱饵函数长这样：

```solidity
// [decoy] external call looks risky but state is settled first
function decoyPayout(address to, uint256 amt) external { ... }
```

注释里写着 `decoy`、"looks risky"、"already guarded"，函数名还叫 `decoyPayout`。
**这等于把答案写在题面上**——模型读到注释就知道"这段是示意代码、无害"，直接跳过。
所以它从不误报，precision 不降，F1 自然不降。

真实工程里攻击者不会给代码写批注说明自己无害。修法：

- 函数名改成业务化命名：`payoutPartner` / `accrueTier` / `setRiskCap` / `maintenanceMode`；
- 注释改成"开发者自用"口吻（`// settle the affiliate share before paying out`），
  不出现 decoy / safe / already guarded / looks risky 任何一处；
- 统计"踩雷率"改为**按插入的函数名匹配**（诱饵代码里已不能出现 decoy 字样）。

自测里加了硬断言：产物中若出现泄漏词列表里的任一词即判失败
（`run_implementation_smoke.py::test_difficulty_knob`）。

> 教训：**任何"伪装"类算子，第一件事是检查它有没有自曝。**
> 这跟"埋雷注释写得越清楚越好"是相反的——雷要写得显眼，诱饵必须写得无害。

### 坑 7.2 · 插入的诱饵引用了不存在的状态变量 → 整批样本编译失败

`sample-0001` 的合约里只有 `balances`，而诱饵模板引用了 `guardian` / `riskCap` / `onlyOwner`。
本机没有 forge，跑 `batch_generate` 时不会立刻发现，但**上 CI / 交 harness 就会炸**，
而且是一整批全废。

修法：`ensure_state_decls()` 先扫合约体，缺哪个状态变量 / modifier 就补哪个声明，
且**幂等**（重复注入不会产生重复声明）。`onlyOwner` 这种 modifier 一并补全
（`address internal owner;` + `modifier onlyOwner() { require(...); _; }`）。

自测断言：注入后 `partnerShare` 声明恰好出现 1 次（幂等）、`modifier onlyOwner()` 存在。

### 坑 7.3 · `max_tokens` 在函数签名里求值 → 设了环境变量也不生效 ⚠️ 最阴

这个坑最阴，因为它**伪装成"模型能力不足"**。

```python
# 错的写法：默认值在函数定义时求值，只在 import 时算一次
def __init__(self, ..., max_tokens: int = DEFAULT_MAX_TOKENS):
```

于是 `LLMClient(model=...)` 这种**直接构造**（不走 `from_env()`）完全无视
`LLM_MAX_TOKENS`。我在命令行明明设了 `LLM_MAX_TOKENS=8192`，实际仍按 **4096** 跑——
证据是截断告警里写着 `输出 4096/4096 token`。

后果正是第 2 节那个 thinking 截断陷阱：难度一高、代码一长，thinking 烧满 4096
预算，模型返回**空答案 + HTTP 200**，F1 记 0。
我第一版扫描结果里刻度 3/4/5 各有 1–2 次截断，**那几个 0 分是假的**，
是配置没生效而不是模型不行。

修法：签名改成 `max_tokens: int | None = None`，在 `__init__` **运行时**读
`os.environ`；`thinking` 同理。自测加了 4 条断言锁住（含"显式传参优先于环境变量"）。

> 教训：**任何"可被环境变量覆盖"的默认值，都不能在函数签名里写死。**
> 写死的那个值会在 import 时被定格，之后改环境变量就像改空气。

### 坑 7.4 · 诱饵模板循环复用 → 同名函数重复定义 → 整批样本编译失败

修完前三个坑后，我专门写了个静态体检脚本（`run_difficulty_lint.py`）查"插进去的代码能不能编译"，
**当场抓出第四个**：诱饵模板只有 4 条，但刻度 5 要插 6 个，我用 `i % 4` 循环复用模板，
于是 `payoutPartner` 和 `accrueTier` 各出现两次 —— Solidity 里这是**编译错误**。

这类错误的危险之处在于**本机看不出来**（没有 forge，`batch_generate` 不跑差分验证），
一旦交到 harness / CI，整批样本全废。

修法：模板代码里用 `{fn}` 占位，`plan_decoys()` 按轮次生成唯一函数名
（`payoutPartner` / `payoutPartner2` / …），依赖声明顺带去重
（多个诱饵可能都依赖 `partnerShare`）。既避免重名，也更贴近真实项目里
"同类逻辑有多个入口"的形态。

> **这一条是"静态体检脚本"这个投资直接回本的地方**：四个坑里有两个（7.2、7.4）
> 是静态检查抓出来的，而 forge 实跑要等 CI、反馈一轮几分钟。
> 对"要反复调参"的算子来说，先写个体检脚本比反复跑 forge 划算得多。
