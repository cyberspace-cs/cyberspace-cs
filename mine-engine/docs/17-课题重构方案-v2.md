## 1. 从主页读出来的三个事实

### 1.1 事实一：DataFlow 生态是明确的六层栈（L0–L5）

主页把整个生态摆成从"数据入口"到"应用出口"的**单向管线**：

| 层 | 名字 | 项目 | 数据流形态 |
|---|---|---|---|
| **L0** | 多源异构数据 | 文档/网页/表格/**代码**/知识库/传感器 | 原始字节 |
| **L1** | 数据入口与解析 | MinerU / MinerU-HTML / Flash-MinerU / RayOrch | 原始 → AI-ready |
| **L2** | **数据资产工厂** | **DataFlow Core**（SIGMOD'27）/ DataFlow-MM / **DataFlow-Table** / DataFlow-KG | 表格/文本 + metadata |
| **L3** | **Agentic 数据与编排** | **AgentFlow** / DataFlow-Skills / DataFlow-WebUI | 轨迹（trajectory） |
| **L4** | **训练调度与评估反馈** | **DataFlex** / **One-Eval** / DataFlow Eval / **LoopAI** | 训练信号 / 分数 |
| **L5** | 应用出口 | Paper2Any / OpenWorldLib | 人类可读产物 |

**这张表的读法**：我们要插进去的位置，必须能说清楚"我属于哪一层、给谁供数、向谁取数"。说不清就没有位置。

### 1.2 事实二：**DataFlow 投的是 SIGMOD，不是 NeurIPS**

> 主页原文：*"DataFlow was accepted by **ACM SIGMOD 2027**."*

这一条的战略含义被我 v1 完全漏掉了：

- 老师是 **CSRanking 北大 AI/ML 与 AI+Data 方向在职教师第一**，主要战场在 **SIGMOD / VLDB / ICDE / KDD / WWW**。
- 也就是说，**一个"数据准备系统"在他这里是数据库顶会论文，不是 ML 顶会论文**。
- 竞争烈度完全不同：NeurIPS 2026 他一个人中 16 篇，说明那边是红海；而"可验证任务合成"在数据库圈是**新题**，且天然命中 ICDE 的 topic。

**ICDE 2027 CFP 里直接对得上我们的 topic**（原文摘录）：

- `Benchmarking, performance modeling, tuning, and testing`
- `Data quality, curation, provenance, and workflows` ← **provenance！我们"标签由构造产生"就是 provenance 的一种**
- `Data preparation, cleaning, and integration`
- `Explainability, fairness, bias, trust, authentication, and **regulatory compliance**` ← **合规，审计正对口**
- `Domain-specific data engineering`
- **EAB 赛道**：`[Experiment, Analysis, and Benchmark]` —— 标题带这个 tag 的论文，**贡献点可以是"新的评测方法"本身**

> ⏰ **ICDE 2027 Round 2 截稿：2026-11-11；通知 2027-02-10；会议 2027-05-17 哥本哈根。**
> 今天 2026-10-04，**剩 38 天**。老师在 ICDE 2027 已中 3 篇（REAL / PhyWorld-Align / CITBench），渠道是通的。

### 1.3 事实三：整条管线的质量信号，**没有一处是"算"出来的**

我把六层逐层查了一遍质量信号的来源：

| 层 | 质量从哪来 | 性质 |
|---|---|---|
| L2 DataFlow | 算子打分、启发式过滤 | **估** |
| L3 AgentFlow | depth + information richness + tool diversity | **估**（不懂语义） |
| L3 DataFlow-Agent | `TrajectoryQualityEvaluator`（goal/efficiency/coherence/tool-use，LLM 1–5 分） | **估**（会说谎） |
| L4 LoopAI Judger | **"Automatically generates evaluation cases (LLM-based)"** | **估**（而且是自评自判） |
| L4 Data-Preparation-Bench | DAS（MMD 分布距离） | **估** |
| L4 DataFlex | 训练损失/梯度 | 真信号，但弱、且是间接的 |

**结论**：**六层栈里没有一个 verifier。** 这条我在 v1 说过，但现在能说得更准——不是"某一处缺"，是**整条管线系统性缺失**，因为 DataFlow 的抽象里根本没有"执行"这个原语（只有 `LLMServingABC` 和 `SandboxClientABC` 两个外部接口，而 sandbox 是 DataFlow-Agent 才有的）。

### 1.4 补充事实：`LoopAI` 已经接了 `verl`，但 Judger 是 LLM 造的

`OpenDCAI/Dataflow-LoopAI` 的闭环是：

```
Starter(Codex SDK) → Judger → Analyzer → ObtainerCLI → Trainer(LLaMA-Factory | verl)
```

- **Trainer 支持 `verl`** —— verl 是 RLVR 的事实标准框架，接了它说明他们**打算做 RL**。
- 但 **Judger "自动生成评测用例（LLM-based）"** —— 也就是说：**RL 的 reward 源头，是 LLM 自己造的题、自己判的分。**

> 🔥 **这是整条链上最脆弱的一环，也是我们的最佳落点。**
> RL 对 reward 噪声极其敏感（reward hacking 的第一来源就是 judge 漂移）。
> 在一个接了 verl 的闭环里，把 reward 从"LLM 造题 + LLM 判分"换成"程序造题 + 程序判分"，**收益是可以直接量出来的**——下游 RL 的收敛曲线和最终准确率。

而且 LoopAI 的 Future Work 原文写着：`📏 Vertical-domain Evaluation Optimization`（垂域评测优化）——**我们要做的正是这个，且是他们自己列的待办**。

## 2. 立论（一句话）

> **DataFlow 生态把"数据"做成了可编程的资产，但"任务"和"奖励"仍然只能靠模型估。**
> **我们贡献的是把任务也变成可编程资产的那一步：每条数据自带一个可执行 verifier。**

用 lab 的语言重述一遍（这段是去谈的时候的开场白）：

> DataFlow 的算子把 `(text, metadata)` 变成资产。
> 我们的算子把 `(task, label, verifier)` 变成资产。
> 区别是：**前者的质量要判，后者的质量不用判——它是造的时候一起写下来的。**

## 3. ⚠️ 方案改动一：主战场从智能合约换成电子数据审计

**这是本版最重要的改动，也是最需要你拍板的一条。** 我的判断：智能合约降级为"工程起步验证"，电子数据审计（账套/报表）升为主战场。

### 3.1 五条论证

**① 代码领域本来就有 verifier，在那里造 verifier 构不成 novelty。**

这是致命的。合约有 `forge`/编译器/单元测试，SWE-bench 有仓库测试，ProgramBench 有 24.8 万条行为测试。**在这些领域说"我给任务配了个 verifier"，审稿人的第一反应是"那不就是测试吗？"**——而且这个反驳很难回。

**② 审计领域有 oracle 素材，但没人把它做成 verifier —— 这才是从无到有。**

审计的领域不变量是**形式化的、可计算的**，但今天它们散落在审计软件、Excel 模板和审计师脑子里，从没被抽象成可执行的 verifier：

| 不变量 | 形式 | 可否程序验证 |
|---|---|---|
| 会计恒等式 | `资产 = 负债 + 所有者权益` | ✅ 恒等式 |
| 借贷平衡 | `Σ借方 = Σ贷方` | ✅ 逐笔可查 |
| 三表勾稽 | 现金流量表期末现金 = 资产负债表货币资金 | ✅ 跨表约束 |
| 科目余额连续性 | `期末 = 期初 + 本期借方 - 本期贷方` | ✅ 递推式 |
| 税率/折旧/摊销 | 政策公式 | ✅ 参数化公式 |
| 预算执行率 | `实际支出 / 预算批复 ≤ 阈值` | ✅ 阈值约束 |
| 凭证-账簿-报表三级一致 | 汇总关系 | ✅ 聚合一致 |

**这些全是数学约束。** 一旦形式化，一个审计 agent 的回答（"第 3 笔凭证虚增收入 120 万"）就是**可判定的**——不是"评委觉得对不对"，是"把这笔冲销后，勾稽是否恢复平衡"。

**③ 决定性优势：审计的"注入"就是真实的舞弊手法。**

这是审计相对代码的**结构性优势**，值得单独讲：

- 代码注入的老批评（从 LAVA 就被反复问）：**注入的 bug 真实吗？** 真实漏洞是开发者无意写出的，注入的 bug 常常"不像人写的"，模型可能靠风格就能认出来。这个批评我们回避不掉。
- 审计领域**完全没有这个问题**：**舞弊本来就是人"注入"的。** 虚增收入、跨期调节、关联方非关联化、账外账、虚构往来款——这些手法的定义就是"人为改一笔"。**我们的注入算子 = 财政部/审计署公布的舞弊手法库，注入动作与现实同构。**

> 换句话说：**在审计领域，"合成数据不真实"这个经典质疑自动失效。**
> 这一条我认为是整个课题最硬的一块，也是代码领域给不了的。

**④ 数据可合成、不涉密，解决了审计数据不敢公开的死结。**

审计数据敏感是真实的（金审工程数据不公开）。但**账套可以按会计准则凭空生成**——科目表、凭证流、报表都是规则驱动的。合成数据 + 注入舞弊 = 完全公开可发布，且**不影响有效性**（因为判分靠勾稽恒等式，不靠真实数据）。

这同时兑现了我们的第二个结构性优势：**题目 100% 可公开也不怕被背**（ALE 只敢公开 10% 防污染）。

**⑤ 有真实甲方，且正好对上 L2 的 DataFlow-Table。**

- 甲方：审计计算机技术中心 / 金审工程 / 企业内审 —— 用户明确说过有这条线。
- 学术对接：主页 L2 明确列了 **DataFlow-Table**，以及 SIGKDD 2026 的 **ProfiliTable**（Profiling-Driven Tabular Data Processing via Agentic Workflows）。
- 我们做"**表格数据的可验证任务合成**"，是 DataFlow-Table 的自然向下游延伸，**不是另起炉灶**。

### 3.2 因此，三个领域的角色重排

| 领域 | 角色 | 理由 |
|---|---|---|
| **电子数据审计**（账套/报表/凭证） | **主战场 · novelty 来源** | oracle 天然形式化；注入=真实舞弊；可公开合成；有甲方；对上 DataFlow-Table |
| **金融**（反洗钱/信贷/舞弊识别） | **第二验证场 · 泛化性证明** | 同构（有监管规则=oracle），用来证明算子跨域可复用 |
| **代码/智能合约** | **工程起步验证 · 已有资产** | 已有引擎、已有 CI、已有难度旋钮数据；**但只作为 proof-of-concept，不作为 novelty 主张** |

> 这样排之后，"我们是做智能合约审计的"这个标签就去掉了，换成**"我们做的是跨领域的可验证任务合成，审计是第一个被攻克的领域"**。
> 后者不怕被说 region-specific，前者怕。

## 4. 科研设计

### 4.1 形式化（这部分进 paper 的 §3）

定义三元组 **VTS = (S, O, 𝒯)**：

- **S（seed space）**：合法工作产物的集合。审计域 = 满足全部会计恒等式的账套；代码域 = 编译通过且测试全绿的合约。
- **O（oracle）**：一组领域不变量 `{o₁..oₙ}`，每个 `oᵢ: S → {0,1}`，`s ∈ S ⟺ ∀i, oᵢ(s)=1`。**这是可验证性的来源。**
- **𝒯（变换族）**：`t: S × Θ → S'`，参数 θ ∈ Θ 控制注入幅度/位置/隐蔽度。

一次合成产生三元组：

```
task     = t(s, θ)                    # 被注入的变体
label    = (t, θ, loc(t), sev(t))     # 变换记录 —— 由构造保证正确
verifier = λ answer. check(answer, s, t, O)
```

**三条性质（要论证、要证伪的）**：

| 性质 | 表述 | 怎么验 |
|---|---|---|
| **P1 标签正确性** | `label` 的正确性不依赖任何模型判断，只依赖变换 `t` 被忠实执行 | 静态可证：编译/执行注入产物，断言 `oᵢ` 在注入点上确实被违反 |
| **P2 Verifier 可靠性** | verifier 的判定 = oracle 的判定，**前提是差分隔离**：`s` 与 `t(s)` 只差注入点 | 差分执行：注入前后各跑一次 oracle，断言差异集合 `== {loc(t)}` |
| **P3 难度单调性** | 存在标量刻度 κ(θ)，使模型表现随 κ 单调下降 | 扫描实验：κ=0..5 × N 样本 × R 次，报告**分样本表**（不能只报均值） |

> ⚠️ **P3 是唯一可能不成立的**，而且我们**已经有反例数据**（见 `13-难度旋钮验收.md`）：
> 对**已经饱和或已经很难**的题，加难度会**反向**（sample-0002 从 0.385 升到 0.565）。
> 所以 P3 的表述必须限定为"**在模型本可做对的题上成立**"。这个限定不是妥协，是**必须写进 paper 的诚实边界**，否则会被 reviewer 抓。

### 4.3 数据集形态（审计域）

```
seed ledger（合法账套，≈200 科目 × 若干期）
   ├─ 凭证流 voucher_stream
   ├─ 科目余额表 balances
   └─ 三大报表 statements
        │
        ├─ 舞弊算子注入（8 种手法，见 §5.2）
        │     ├─ 注入版账套          → 给模型
        │     ├─ label（手法/科目/期间/金额）
        │     └─ verifier（勾稽检查 + 冲销复算）
        │
        └─ chaff 注入（看起来可疑但勾稽仍平）
              └─ 用于测误报率
```

**8 种舞弊算子（对应真实手法，每条都能查到审计准则出处）**：

| # | 手法 | 注入动作 | 破坏哪个不变量 |
|---|---|---|---|
| 1 | 虚构收入 | 凭空增加一笔应收+收入凭证 | 三表勾稽（收入↔现金） |
| 2 | 跨期调节 | 把下期收入提前确认 | 期间归属（cut-off） |
| 3 | 费用资本化 | 费用科目→资产科目 | 资产/利润恒等式 |
| 4 | 关联方非关联化 | 拆单+改对手方 | 关联交易披露（需外部名单） |
| 5 | 账外账/体外循环 | 部分收支不入账 | 凭证-账簿-报表三级一致 |
| 6 | 虚构往来款冲抵 | 应收应付对敲 | 往来款账龄/真实性 |
| 7 | 折旧/摊销操纵 | 改折旧年限或方法 | 资产净值递推式 |
| 8 | 减值准备计提不足 | 坏账准备率下调 | 减值充足性阈值 |

## 5. 代码实现方案

### 5.1 三个包（对齐主页三层）

| 包 | 落点层 | 内容 | 量级 |
|---|---|---|---|
| **`dataflow-vts`** | **L2** | 注入算子族 + verifier 生成器 + `ArtifactStorage` 扩展 | ~2500 行 |
| **`HarborSandboxClient`** | **L3** | 实现 `SandboxClientABC`，把 Harbor 变成 DataFlow-Agent 的沙箱后端 | ~400 行 |
| **`VerifierJudger`** | **L4** | LoopAI Judger 的插件，用 verifier 替换 LLM 造题判分；输出确定性 reward 给 `verl` | ~600 行 |

**复用已有资产**：`mine-engine` 的 `engine/operators/*`（注入算子）、`engine/validators/*`（差分验证）、`engine/scorers/*`（判分）**可以直接移植**——四组件抽象本来就是领域无关的，换 adapter 即可。这是我们已经付过成本的部分。
