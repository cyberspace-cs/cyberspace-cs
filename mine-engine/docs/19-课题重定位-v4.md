## 1. v3 作废：C 类不是空白，是别人不叫这个名字

v3 的主张是"把可验证奖励从有 oracle 的域扩展到需要构造 oracle 的域，C 类是空白"。
本轮检索直接推翻：

| 论文 | 做法 | 对 C 类的覆盖 |
|---|---|---|
| **WebGrader** (arXiv:2608.06474) | NL 需求 → 可执行 **Flow Contracts** → 真实浏览器执行作 RL reward；8B 达 52.01% FSR，超匹配基线 7.88 分 | **C 类的网页版，已跑通 RL** |
| **AutoPyVerifier** (arXiv:2604.22937) | 从标注 dev set 自动合成 Python verifier 集，DAG search，**+55.0 F1** | C 类的代码版，已成熟 |
| **Pajama / Codifying the Judge** (arXiv:2607.22561) | 把 LLM 判分逻辑蒸馏成可执行程序，替代 LLM judge，**47.25× 快**；RewardBench 上超过专有 LLM 训的 RM | **"程序化 verifier 打败 LLM judge"已被证过** |
| **SpyRL / RLSVR** (COLM'26) | 任务变换产生自验证奖励，7 个推理 benchmark **+8.97%** | B 类也成熟了 |
| ⚠️ **AutoBenchmark** (Meta RAM, 2026-10) | research agent 端到端自动创建 benchmark，产出 Harbor 兼容包；held-out solver 测难度迁移 | **"让 AI 自己出题"整条路线已做完整** —— 线 A 不能再当卖点，详见 [24](./24-AutoBenchmark借鉴.md) |

**教训（比结论更重要）**：
> 判断"这块空白是不是机会"时，必须先按**功能**而非按**名字**检索。
> 我用"domain-prior oracle"这个自造词去搜，搜不到，于是误判为空白。
> 而社区的词是 *programmatic grader* / *executable verifier* / *Flow Contract* / *verifier synthesis*。
>
> **自造术语 = 检索盲区 = 把"我没搜到"误当成"没人做过"。**
> 这是术语审查（`15-术语审查与换词对照.md`）之外第二条更狠的规则。

## 2. 真正成熟度不足的地方（且是被共同暴露的）

把上面这些论文的**局限性**并排放，出现一个高度一致的缺口：

| 论文 | 自陈 / 被指出的缺口 |
|---|---|
| WebGrader | 审稿意见原文：`the paper never measures reward accuracy on the actual training distribution`。它在自造的干净样本上验 verifier（fault recall 65%→85%），然后**在已知有缺陷的 verifier 上跑完 GRPO**，报 52.01%。审稿人要求标一批 rollout 算 reward precision/recall，**没做**。 |
| Delay, Plateau, or Collapse | 原文：`we restrict ourselves to settings where V* is tractable` —— 想研究验证误差对 RL 的影响，但**必须先有人类可算的 ground-truth verifier**。 |
| Countdown-Code | 能干净分离 proxy/true reward，因为环境是**刻意造出来**的。 |
| Multilingual Verifier Bias (2608.20362) | 报出 exact-match verifier 漏判率 **JP 0.642 / EN 0.122** —— 一个极高的数，**但他们没跑 RL**，不知道这个数意味着什么。 |
| Where the Verifier Fails (2609.01354) | 用变异测试造"保义等价变体"，把 FNR 测到分类级 —— 但前提是"保义"可由**文本改写**保证。 |
| ABA (2605.26079) | 审计 168 个 benchmark / 34,285 任务，25.7% 有问题。人工标注 496 个任务烧 **89 人时**。 |
| 行业实践建议 | "Build a small audit set — 200–500 (gold, model-answer) pairs sampled from real rollouts and **labelled by hand**" |

### 归纳成一句话

> **所有关于"验证器误差如何伤害 RL"的结论，都只能在 oracle 免费可得的域（math / code / web）里得到。
> 而这正是为什么没人做审计、金融、政务 —— 不是没价值，是那个免费的 oracle 要 1100 专家小时
> （FinancialAuditBench 的 6 个 engagement 实测）。**

**所以 C 类"没人做过"不是坏信号 —— 它是护城河。**
但护城河只有在**能被被别人踩到**时才是资产。这就要求：

> **给 verifier 配一个独立的、不依赖 verifier 的第二个 oracle，
> 让"这个 verifier 到底有多差"在零人工标注下可测。**

## 3. 新主张（一句话版）

> **Verifier 的可靠性是 RL 训练的隐藏瓶颈，而它可以在零人工标注下被测量。
> 测量需要第二个参照 oracle；参照 oracle 可以被构造出来，而不必被标注出来。**

### 为什么这不是"又一个 C 类"

我们**不再主张**"能造 verifier"（那是 WebGrader / AutoPyVerifier 的地盘，已成熟）。
我们主张的是**元层面的东西**：

> **Verifier 的质量保证（verifier auditing）。**
> 现有工作在造 verifier，很少有人在**审计 verifier**；
> 而审计需要参照 oracle，所以审计只发生在便宜的地方。

### 我们的 gap（经五支柱审计改写，2026-10-05）

> ⚠️ **本节已被`benchmark-paper-template` 的 gap 四项检验修正过一次。**
> 原表述「测 verifier 需要 1100 专家小时，所以没人做」**站不住**——
> 行业实践建议明写「手工标 200–500 条 (gold, model-answer) pairs」，
> 那是"加几条样本"，按gap 分类属**成本缺口**而非**结构缺口**，
> 而成本是可以被资本解决的。完整审计见 `21-五支柱审计.md`。

改写后的陈述：

> **Existing verifier studies focus on whether a verifier can be built, operating under
> the assumption that a verifier being widely used is evidence of being adequate.
> However, in audit / finance / governance domains, verifier error is unmeasured because
> the reference oracle is assumed unobtainable — and the field's own remedy
> (hand-labelling 200–500 pairs) yields exactly one point, not the error-vs-difficulty curve
> that audit tasks require. This creates a critical blind spot: we cannot tell whether
> a verifier fails uniformly or only past a difficulty threshold — meaning a verifier
> can pass a small audit and still collapse on a harder distribution.**

**为什么"一个点 vs 一条曲线"是真实差异**（三条均有实测支撑）：

| 论据 | 状态 |
|---|---|
| 手工标注只能覆盖**一个** verifier在**一个**分布上的表现 = 一个点 | ✅ 逻辑必然 |
| 我们的注入算子可**连续参数化**（雷数 / 跨函数距离 / 诱饵密度 / 混淆度） | ✅ 已实现 4 个旋钮 |
| 边际成本≈0：10 题 → 1000 题，单题恒定 **0.35 ms** | ✅ E6 实测 |

⇒ 差异不在"能不能测"，而在**能不能测出失效的形状**。

### 三条可证伪的性质

| # | 性质 | 形式 | 实测状态 |
|---|---|---|---|
| **A1** | 参照可构造性 | 参照 oracle 的正确性可被独立核验，且成本 = 毫秒 | ✅ DIC 400/400 有效，0.64 ms/样本 |
| **A2** | 漏判率精确可测 | 无需人工标注即可给出 (FNR, FPR)，且误差为结构性而非抽样 | ✅ 7 个 verifier 全部精确测出 |
| **A3** | 后果可预测 | 给定 (FNR, FPR) 可**闭式预测** GRPO 训练失效形态，无需跑 RL | ✅ 解析式 vs MC 最大偏差 0.27 |

A3 是最值钱的一条：**审计一个 verifier 不需要跑 RL**。

### 4.1 参照 oracle 自检（前提）

```
种子账套 × 100 × 4 期 × 4 oracle   → 1600/1600 自平
DIC 有效率（4 手法 × 100 seed）    → 400/400 = 100%
干净账套违规                       → 0 例
```

### 4.2 Verifier 漏判率（精确测量，非估计）

| verifier | 检测层 FNR | 归因层 FNR | 端到端 FNR | 干净误报 |
|---|---|---|---|---|
| `tie_only`（只查报表=明细汇总） | 0.000 | 0.800 | 0.833 | 0.000 |
| `equation_only`（只查恒等式） | **1.000** | 1.000 | 1.000 | 0.000 |
| `arith_full`（三条勾稽） | 0.000 | 0.800 | 0.833 | 0.000 |
| `programmatic_full`（四条全查） | 0.000 | 0.800 | 0.833 | 0.000 |
| `strict_typed`（全判据+严定位） | 0.000 | 0.800 | 0.833 | 0.000 |
| `typed_lenient`（容忍定位不准） | 0.000 | 0.600 | 0.667 | 0.000 |
| `any_flag`（报了就算过） | 0.000 | 0.000 | 0.167 | 0.000 |

**两条实测事实**：

**① 结构性不可见（最重要的发现）**

每个手法的实际破坏集（= 它碰到的会计约束）：

```
capitalize    ['o_rollforward', 'o_tie_detail']
cutoff        ['o_rollforward', 'o_tie_detail']
depreciation  ['o_rollforward', 'o_tie_detail']
offbook       ['o_rollforward', 'o_tie_detail']
```

`o_equation`（会计恒等式）**看起来最该查，但它不在任何一个手法的破坏集里**。
于是只查恒等式的 verifier 对四种手法**恒定漏判 100%**，
且**调容差、改实现、加随机性都救不回来** —— 这是**结构缺陷**，不是概率噪声。

> 这解释了一个真实世界现象：很多"合规检查"就是查 `资产 = 负债 + 权益`，
> 而最常见的财务舞弊（费用资本化、折旧不足）在会计上**并不破坏恒等式**
> （资产与权益同增，实测差 = 0），它们破坏的是**表账一致**。
>
> **含义**：加 oracle 之前必须先看错误预算矩阵，否则会一直错误地"再加一条 oracle"。

**② 漏判必须是两层的，单层没有诊断价值**

检测层（有没有发现异常）与归因层（是不是报对了手法和定位）必须分开。
`tie_only` 检测层 FNR = 0（每次都发现了），但归因层 0.800 —— 
**它总能发现，但分不清是哪种舞弊**。只报一个聚合 FNR 会把它看成"可靠"。

### 4.3 误差是系统性的（自动判定）

```
verifier            NMI(答案类别, 判错)   零假设 95 分位   判定
tie_only                     0.501           0.000        系统性
programmatic_full           0.501           0.000        系统性
typed_lenient               0.596           0.001        系统性
equation_only               0.000           0.000        退化（全漏）
```

7/7 呈系统性。**误差可按类别预测 → 可以被定向修复**，
这与 Egashira 等人的结论（verifier 误差是系统性的、结果由误差模式而非总量决定）一致，
但我们能在**没有 V\* 的域**得出这个结论。

### 4.4 GRPO 后果：三条反直觉结论

蒙特卡洛（G=8，4 个正确解，每格 30000 次采样）：

| FNR | FPR | 正确解平均优势 | 符号翻转率 | 退化组比例 |
|---|---|---|---|---|
| 0.0 | 0.0 | **1.000** | 0.000 | 0.000 |
| 0.3 | 0.0 | **0.750** | 0.000 | 0.008 |
| 0.6 | 0.0 | **0.546** | 0.000 | 0.130 |
| 0.9 | 0.0 | **0.411** | 0.000 | 0.656 ← 无梯度 |
| 0.6 | 0.2 | 0.236 | 0.000 | 0.053 |
| 0.9 | 0.2 | **−0.170** | 0.559 | 0.269 ← 翻转 |
| 0.6 | 0.5 | **−0.106** | 0.563 | 0.009 ← 翻转 |
| 0.3 | 0.8 | **−0.122** | 0.464 | 0.098 ← 翻转 |

**结论一（推翻社区直觉）：误报率 = 0 时，漏判率升到 100% 也不会翻转符号。**

社区通行说法（Reward Engineering 博客、Huang et al. 的 GRPO 误杀论证）：
"错杀 1 个正确解 → 该解拿到 advantage ≈ −0.77，梯度主动推开它。"
这句话描述**单次事件**是对的；但推广成"漏判率一高就翻转"是**错的**。

机制：被误杀的正确解 r=0，归一化后 advantage = (0−μ)/σ 确实为负，
但它同时把 μ 拉低、σ 同步变化。存活者的高优势与被杀者的负优势放在同一组做期望，
**净效应为正**。误杀单个解 ≠ 训练方向错误。

符号翻转阈值（闭式解，二分求得）：

```
FPR = 0.00  →  不存在阈值（漏判到 1.0 也不翻转）
FPR = 0.05  →  FNR 阈值 = 0.950
FPR = 0.10  →  FNR 阈值 = 0.900
FPR = 0.20  →  FNR 阈值 = 0.800
FPR = 0.35  →  FNR 阈值 = 0.650
FPR = 0.50  →  FNR 阈值 = 0.500
```

**结论二：造成训练方向反转的是误报，不是漏判。**
机制：误报把**错误解**抬到与正确解同分，组内不再区分对错，
正确解优势被稀释到 0 以下。这是**奖励污染**，不是奖励缺失。
所以审计必须同时报 FNR 和 FPR，**只报 FNR 会让人误以为"漏判无害"** —— 这是危险的错误结论。

**结论三（第三种失效模式，此前被忽略）：无梯度退化。**
FNR → 1.0 且 FPR = 0 时，**66%–100% 的组完全无梯度信号**
（组内 reward 全同，σ=0，GRPO 直接跳过）。

> 这不是"训练变差"，是**训练直接停摆**，而且**不报错、不崩、曲线看起来正常**。
> —— 与我们在代码域发现的截断污染是同一类陷阱：**失效伪装成"模型能力不足"**。

### 4.5 我们的 verifier 的训练预算

| verifier | FNR | FPR | 正确解优势 | 退化组 | 判定 |
|---|---|---|---|---|---|
| `tie_only` | 0.833 | 0.000 | 0.225 | 48.2% | OK |
| `equation_only` | 1.000 | 0.000 | 0.000 | **100%** | **NO_SIGNAL** |
| `programmatic_full` | 0.833 | 0.000 | 0.225 | 48.2% | OK |
| `typed_lenient` | 0.667 | 0.000 | 0.409 | 19.8% | OK |
| `any_flag` | 0.167 | 0.000 | 0.854 | 0.1% | OK |

`any_flag` 的 FNR 最低（0.167），但这是**用放弃精确性换来的** ——
它的误报侧在本测量下为 0 是因为干净账套上 verifier 也不报警。
在真实场景里"报了就算过"的 verifier 精确率极低。
**这张表必须三列一起看，只看 FNR 会得出错误的最优解。**

## 5. 与 OpenDCAI 的关系（这才是能落地的部分）

新主张让合作**更具体**，因为它直接命中 DataFlow-Agent 的一处已知缺陷：

| OpenDCAI 现状 | 本工作提供的 |
|---|---|
| `TrajectoryQualityEvaluator` = **LLM-as-judge**（goal/efficiency/coherence/tool-use 四轴 1–5 分） | 测量这个 judge 的 FNR/FPR —— **零人工标注** |
| roadmap 列 `P0 data trust: verifiable rewards` | 提供 verifiable rewards，**且给出它的误差预算** |
| 不知道怎么判断自己的 judge 够不够好 | `run_vts_regression.py` 式的三列预算表 |
| LoopAI 的 Judger 是"LLM 自动生成评测用例 + 自己判分" | 参照 oracle 由构造给，不由 LLM 给 |

**交付物形态（一句话）**：
给 DataFlow-Agent 一个算子 `VerifierAuditOperator` ——
输入一批轨迹 + 任务自带 verifier，输出 (FNR, FPR, 退化组比例, 结构性不可见清单)，
**不需要任何人工标注**。

这个形态比 v3 的 `VerifierJudgeOperator` 更好卖：
不是"我给你一个更好的 judge"，而是**"我告诉你你现在这个 judge 有多差"**——
后者是所有人都需要、但都没人提供的信息产品。

## 6. 诚实边界（这段决定能不能过审）

### 6.1 什么不新

1. **RLVR / verifier 的重要性** —— 不新（R1/Tulu-3 时代）
2. **verifier 误差是系统性的** —— 不新（Egashira et al. 2026）
3. **程序化 verifier 优于 LLM judge** —— 不新（Pajama, WebGrader, AutoPyVerifier）
4. **GRPO 优势公式** —— 不新（是标准技术）
5. **vulnerability / fraud 注入造 benchmark** —— 不新（LAVA, CyberForge）

### 6.2 什么可能是新的（待审稿判断）

1. **verifier 审计的参照可以构造，而非标注** → 使审计从"只在便宜域可做"变成"任何域可做"
2. **漏判必然翻转训练方向这一直觉的错误**（结论一、二）→ 若成立，是对社区理解的实质修正
3. **无梯度退化作为独立的第三种失效模式**（结论三）→ 目前只在退化边界观察到
4. **结构性不可见的可判定性** → 形式化为"破坏集与判据集无交集 ⇒ FNR ≡ 1"

### 6.3 明确的局限（必须写在 paper 里）

- **会计域只有一个域**。4 个手法、4 条约束、100 个 seed。
  结论 4.4 的阈值表**只在 (G=8, 4 正例) 这一格验证过**，其它组大小未测。
- **答案分布是显式参数**，不是实测的模型行为。`DEFAULT_PROFILE` 是我设的，
  换成真实模型会改变绝对值，**但不会改变三条结论的符号方向**（那是解析的）。
- **`o_equation` 结构性不可见是当前算子集的性质**，换一批手法后破坏集会变，
  这一条需重跑错误预算矩阵才能断言。
- **没有真跑 RL**。结论 4.4 是解析 + 蒙特卡洛，不是训练出来的曲线。
  E2（verl 实跑）是 go/no-go 之前的最后一块，必须做。
- **verifier 侧的 FPR 是在"干净账套 + 我的 profile"下测的**，
  真实 LLM judge 的 FPR 需要接 DeepSeek 实测才作数。**这是下一步。**

## 8. 与 lab 沟通的三句话

1. **我们发现 OpenDCAI 整条 agent 数据栈没有 verifier 质量保证** ——
   `DataFlow-Agent` 的 `TrajectoryQualityEvaluator` 是 LLM-as-judge，
   而它有多差**目前无法被测量**。
2. **我们可以让它变得可测，而且不需要人工标注** ——
   用任务构造时附带的参照 oracle，零成本给出 (FNR, FPR, 结构性不可见清单)。
3. **我们还发现社区对 verifier 误差的一个通行直觉是错的** ——
   造成 GRPO 训练方向反转的是**误报**而不是漏判；
   单看漏判率会漏掉真正致命的失效形态。

第 3 条是最好的开场白，因为它**不依赖合作也能成立**，而且是别人会想追问的。
