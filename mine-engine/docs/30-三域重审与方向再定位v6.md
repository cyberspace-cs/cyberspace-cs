# 30 · 三域重审与方向再定位（v6）

> 本文档推翻 v5 的三条定位结论。核到了 ALE 五道 gate 原文，并发现两篇 2026-06/09 的
> 新工作正面占住了我们此前认为无人做过的事。
>
> **文档纪律**：本文所有 ALE 数字来自 arXiv:2606.05405v2 HTML 原文（含 Appendix B.2 /
> B.1.1 / C.1 / §2.3 / §3.1 / §3.3 / Fig.5）；三篇新工作数字来自其原文，标注了口径。
> 凡未报告的量一律写「未报告」，不推测。

## 0. 摘要：三条旧结论的死亡与一个新问题的诞生

| v5 的说法 | 实际 | 判定 |
|---|---|---|
| 「verifier 的误差率从未被量化」 | Zhong et al. arXiv:2606.08960 审计 1,968 个任务，323 个（16%）可被绕过 | **死** |
| 「会计域没人在合成账套上做 benchmark」 | FinancialAuditBench arXiv:2609.32835，6 engagement / 90 任务 / 1,100+ 审计师小时 | **死** |
| 「ALE 只管出题不管判分，判分器是空白」 | ALE 五道 gate，Final QC 明确校准 evaluation bounds | **死** |
| 「难度连续参数化是唯一空白」 | 仍成立，且**新增了两条独立证据** | 活，但含义变了 |

**新的核心问题（本轮提出，v5 没有）**：

> 同一个 verifier 的误差率，现在有两种**互不相容**的估算法：
> **攻击式下界**（对抗搜索能钻多少个空子）与**参照式速率**（真实分布上判错多少）。
> 前者给出 16%，后者在金融审计域给出 95%–100%。**两个数差了 6 倍，
> 而且没有任何论文把它们放在同一张表上比较过。**

⇒ 这才是我们真正的位置：**不是「第一个测 verifier」，而是「第一个解释这两种测量为什么对不上」。**

## 1. 纠正：我说错的三处

### 1.1 「verifier 误差从未被测过」——死

**Zhong, Segal, Bercovich, Saxena, Zhang, Raghunathan.**
*Hardening Agent Benchmarks with Adversarial Hacker-Fixer Loops.*
arXiv:2606.08960，2026-06-08，CMU + Fewshot。

必须精确记的数字（口径不同，勿混）：

| 口径 | 数值 | 含义 |
|---|---|---|
| 环境级可 hack 率 | **323 / 1,968 = 16%** | 至少存在一个确认 exploit 的**环境**比例 |
| 攻击模型 | Claude Opus 4.6 / Gemini 3.1 Pro / GPT-5.4 | 三个 frontier 模型 |
| 五个 benchmark | Terminal-Bench、TB 2.0、TB-Pro、OpenThoughts-TB-dev、SETA | 仅 TB 2.0 给出分母 89、可 hack 13（14.6%） |
| 轨迹级条件比例 | **3,632 / 4,848 ≈ 75%** | 在**已通过 verifier** 的轨迹中，被判为 hack 的比例 |
| 总体 ASR | **无法计算** | 原文未披露攻击尝试总数 |

⚠️ **16% 是"环境级 reward-hack prevalence"，不是模型 ASR。** 75% 是条件比例，
分母是"已通过 verifier 的轨迹"。引用时必须带口径，否则会被审稿人当场拆掉。

**它到底做了什么**：`hacker–fixer loop` 三个 LLM 角色轮转 —— hacker 不解题只骗过
verifier；fixer 打补丁；solver 确认补丁没误伤合法解。Hacker 在 loop 内可读 verifier
源码（挂在 `/eval_env/`），held-out 评估器是 blind。

**结果**：KernelBench held-out ASR 62%→0%；弱模型防守可压强模型攻击
（Gemini 3 Flash 的 loop 把 Gemini 3.1 Pro 与 Claude Opus 4.7 从 76%/61% 压到 0%）。

**发布**：Terminal Wrench（323 环境 + 3,632 轨迹，`github.com/few-sh/terminal-wrench`，
dataset card arXiv:2604.17596）+ harden-v0 实现。总花费约 **$5,000**，8×H200 约 24–48 小时。

### 1.2 「会计域没人在合成账套上做 benchmark」——死

**Huang, Babu, Van Buren, Wang, Pillai, Jain, Burton, Hockenmaier.**
*FinancialAuditBench: Benchmark Construction under Differential Privacy Using Real-World Priors.*
arXiv:2609.32835，2026-09-26。数据集 `modusaudit/FinancialAuditBench`（MIT，30.8MB）。

| 事实 | 数值 | 出处 |
|---|---|---|
| 合成 engagement | 6 个（manufacturing / staffing services） | 摘要 |
| 每 engagement 平均文件数 | **179** | 摘要 |
| 计算图规模 | ~**250 nodes / 1,000 edges**，三类节点（source / conditional / deterministic） | §3 |
| 任务数 | 45 完成 + **45 复核** = 90 | §5 |
| 工作底稿类型 | 8 种（AP/AR/Cash/Debt/FixedAssets/JE-completeness/JE-risk/Revenue） | 附录 Table 3 |
| 每底稿评分项 | 平均 **~10 个** | §5 |
| 专家投入 | **略超 1,100 小时** | 摘要 |
| 隐私保证 | **(3.65, 10⁻⁵)-DP**，zCDP ρ≈0.2505，36 个机制 | §5 |
| 参与咨询审计师 | 15 名（范围界定）、3 名（变量独立评估）、1 名高级审计师（>10 年经验，汇总与裁决） | §4 |
| 最佳模型 Pass@1 | Claude Opus 5.5 **69.17%**（partial credit 95.84%，$3.30，11.21 min） | 主表 |
| 最佳模型 pass^8 | **44.44%**（8 次全过） | 附录 |
| pass@8 | **87%** | 附录 |

⚠️ **69.17 / 44.44 / 87 三个数不可互换**：单次能力 / 跨重复可靠性 / 最好一次表现。

**它没做什么（这些恰好是我们的空间）**：
- **未报告评分器的 false accept / false reject 率**；明确说因反馈形成于协作讨论，
  **未报告 inter-annotator agreement**。
- **明确自陈**：「passing the rubric does not imply that a given workpaper is free of
  errors or omissions outside of the rubric's scope.」⇒ **一个自认的、未量化的 false accept 风险。**
- **没有正式难度变量**。它按 8 个工作底稿领域分组报告，但**明确声明这只是描述性结果，
  不构成难度分析**（领域间同时差在检索复杂度、文档格式、第三方证据可得性、rubric 点数）。
- 人工时间 2–12 小时只是**领域级代理指标**，作者**没有**把它转成难度分数，也未做相关性分析。

**领域级通过率的巨大落差（这是本轮最有用的新数字）**：

| 工作底稿 | 人工时间 | Agent 中位时长 | 平均 strict pass |
|---|---|---|---|
| Journal-entry completeness | 2–4h | 7 min | **94.51%** |
| Accounts payable | 4–6h | 9 min | 68.18% |
| Cash | 3–5h | 8 min | 56.06% |
| Fixed assets | 2–4h | 8 min | 54.17% |
| Debt | 3–5h | 8 min | 52.08% |
| Journal-entry risk testing | 6–10h | 12 min | 16.86% |
| Revenue | 8–12h | 10 min | **7.58%** |
| Accounts receivable | 6–10h | 12 min | **4.17%** |

⇒ **最易与最难之间差 22.7 倍。** 而作者拒绝把它叫难度。
⇒ 这**直接支持**「难度是被测量的关键混淆变量」这个论点，且现在有一个第三方的大规模数字可引。

**四类真实工程难题**（审计师定性归因，非互斥，**论文未给数量分布**）：
1. 修改/新增信息后**未考虑下游影响**；
2. **检索不足** —— 只查最明显的文件，不继续找更完整证据；
3. **证据来源评估不足** —— 用客户自编的 cash receipts report 而不是 bank statement 去 vouch；
4. **不愿留下未解决事项** —— 信息不足仍强行完成，不声明程序无法按设计执行。

第 4 条是审计学的经典难题（**professional skepticism**），第 2、3 条是 RMM 里
**inspection risk** 的行为侧实现。⇒ 三域不是并列关系，审计域提供的是**其余两域缺的构念**。

### 1.3 「ALE 只做内容不管判分」——死

ALE 真实流程是**五道 gate**（Appendix B.2）：

```
Expert sourcing → Task submission and editing → First-pass review
→ Task implementation → Final QC and acceptance
```

**准入三原则**（先于 gate）：`Representativeness`（须用领域专家真实使用的软件，
反例：不用 AutoCAD 做 2D→3D）/ `Complexity`
（"The key distinction is between a workflow and an action"）/ `Verifiability`。

**内部执行契约**（Appendix C.1，⭐ 这是我此前完全没核到的）：
每个 instance 是一个可执行 `main.py`，编码五项
（description / input assets / required software / **reference assets** / evaluation criteria），
暴露三个生命周期函数：

| 函数 | 职责 |
|---|---|
| `load()` | 声明任务描述、metadata、**compute requirements** |
| `start()` | 配 VM、复制 input、启动软件、置**确定性初始状态** |
| `evaluate()` | 读 agent artifact，对照 reference 或 rubric，返回 **[0,1] 归一化分数** |

**四目录契约**（§3.1）：`input/` 只读 / `software/` 预装 / `output/` **agent 唯一可写** /
`reference/` **对 agent 隐藏，仅用于评分**。

**六种 artifact comparison modes**（§3.3）：
exact/hash、structured numeric with **manifest-driven tolerances**、
geometric distance、**visual appearance（vision-LLM judge）**、
behavioral world state under fixed trajectory、free-text rubric。

**两种组合模式**：`gate-and-score`（gate 失败 ⇒ 该任务直接 0，"regardless of partial
progress"）与 checklist / per-file 平均。

**Final QC 的四项检查**（专家委员会）：
reference-output correctness、**evaluation bounds calibration
（"neither impossibly narrow nor spuriously permissive"）**、context sufficiency、reproducibility。

**一条明确的拒收条款**：唯一评分方案是「ask a model whether the result looks correct」
的任务，**在 QC 阶段被拒绝并重新设计为暴露可检查 artifact**。

⇒ **ALE 对 evaluation bounds 的定性校准，正是我们 FPR/FNR 的定性版本。**
⇒ 但它靠专家委员会的人工判断，**不把两个比率算成实数、不给置信区间、不分层**。
⇒ **校准是流程里的一个动作，不是可复现的测量。这就是我们全部的立足点。**

⚠️ ALE 自身数字不一致（引用须带版本 `ALE-V1, 2026/06`）：
专家数 250+ vs 结论段 300+；公开任务 150 vs 正文「152-task public set」vs 三层 67+55+38=160；
私有状态 正文称 remainder 在 private pool，Fig.5 实为 1,017 private + **323 pending QC**。
**323 不是"已失败"，是"待QC"** —— 不可写成 QC 失败数。

## 2. 三域的真实工程难题（这才是选题的地面）

### 2.1 财务报表审计域

| 难题 | 证据 | 学科名 |
|---|---|---|
| 判据覆盖不全 ⇒ 误接受 | FinancialAuditBench 自陈 rubric 外错误不计分，平均仅 10 项/底稿 | **inspection risk**（AS 1101 Detection Risk） |
| 不愿留未解决事项 | 四类错误之第 4 条 | **professional skepticism**（AS 1101） |
| 检索与证据充分性 | 四类错误之 2、3 条 | **sufficiency of appropriate audit evidence**（ISA 500） |
| 跨期与完整性 | F4 验收实测：四个算子违反签名原本全同 | **cutoff / completeness assertions** |
| 判分器极性可能接反 | S1 实测 pro 检测层 J=+0.130 为正、端到端 −0.180 | **Youden's J**（Youden 1947） |

**最难的一点（有硬数字）**：JE-completeness 94.51% vs AR 4.17%，**22.7 倍落差**。
这类域天然是**难度长尾**——最难的恰恰是审计实务里最耗时的那类
（Revenue 人工 8–12h、AR 6–10h，strict pass 7.58%/4.17%）。

### 2.2 金融域

| 难题 | 证据 | 边界 |
|---|---|---|
| LLM verifier 在干净报表上大量误报 | FinVerBench arXiv:2605.29586：43 家 S&P 500 真实 XBRL，**9/14 个 run 在干净报表上 95–100% 误报** | 测的是"LLM 当审计员答得好不好"，非"当判分器错多少" |
| 图验证参照仍误接受 | SSRN 6482162：grounded 配置 72.2% 一致但 **31.7% 误接受**；**工作论文、0 引用、单模型、无难度维度** | 证据强度弱，只能作旁证 |
| 误导性披露叙事 | AuditFraudBench arXiv:2606.08345：现有金融/审计 benchmark **很少测误导性披露叙事** | 测"能否识破误导"，非判分器可靠性 |
| 长时程成本 | 金融审计约 15 人时 | ⚠️ **业界报告非同行评审，须标注来源** |

⇒ 金融域提供的是**误报侧的极端案例**（95–100% FPR），审计域提供的是**难度长尾**。
两者都不是 coding 域能提供的。

### 2.3 Coding / terminal 长时程域

| 难题 | 数字 | 来源 |
|---|---|---|
| **verifier 可被绕过** | 16% 环境（323/1,968）；已通过轨迹中 75% 是 hack | 2606.08960 |
| **修 verifier 会误伤合法解**（solution narrowing） | TB 轨迹级拒绝率 23.9%→**34.8%（+10.9pp）**；task-level 15.6%→26.0% | 同上 |
| raw loop 的极端形态 | KernelBench 不做 autopatch 时：ASR 0% 同时 benign pass 也 **0%** | 同上 |
| 任务被 reward-hack 的既有证据 | >15% 任务可被 hack（**guideline 论文，非测量论文**） | Bercovich arXiv:2604.28093 |
| 主动绕过 verifier | SWE-Marathon arXiv:2606.07682：**13.8% rollout 呈 exploit 形态，10.2% 明确提交 verifier bypass** | 2606.07682 |
| 长时程本身 | SWE-Marathon 平均 **27.2M tokens**，frontier agent <30% pass@1；**73% 失败是实现失败与超时，99.6% 呈 validation weakness** | 同上 |

⚠️ **引用歧义（须在论文里澄清）**：SWE-Marathon 把「五个 terminal-agent benchmark 中
>15% 任务可被 reward-hack」归给 Bercovich et al.（2026-04-19），但"五个 benchmark、
1,968 任务"这个描述**只匹配 Zhong et al. 2606.08960**。Bercovich 本人是两篇的共同作者，
2604.28093 是**设计指南**（提出 adversarial / difficult / legible 三原则），
其 15% 数字是**引用他人**。⇒ 三篇关系须核原文引用节后写清，不可含糊。

**coding 域给我们的独有东西**：`solution narrowing`（+10.9pp）**是唯一有人量化过的
verifier 误拒数字**。但它有三个致命缺陷（我们 §3.2 的立论基础）：
1. **solver 失败 ≠ verifier 误拒**。solver 失败可能是 solver 太弱。
   他们每任务只跑 **3 次** held-out solver，**穷举不了合法解空间**。
2. **precheck 造成选择偏差**：solver 4 次全失败的任务被**排除**，
   Terminal-Bench 由 **100 减到 77**。⇒ 他们只测了「至少被采样 solver 解出来一次」的任务，
   **恰恰漏掉了对正常 solver 太难但仍有合法解的那批**——而那正是误拒最可能出现的地方。
3. **修完后的数字依赖 autopatch 事后放宽**，不是 raw loop 原样输出。

⇒ **这个 +10.9pp 是「代理量」不是 FNR，而它的偏差方向恰好掩盖了我们最想测的东西。**

## 3. 威胁坐标：谁测了什么、没测什么

### 3.1 三个正面对手的方法学光谱

| | Zhong 2606.08960 | FinancialAuditBench 2609.32835 | **我们** |
|---|---|---|---|
| 域 | terminal / coding | 财务报表审计 | 会计（可扩） |
| 被测对象 | outcome verifier（可补丁） | rubric grader（程序 + LLM fallback） | judge / scorer |
| 估计量 | **攻击式下界**（能钻几个空子） | **未测**（自陈覆盖不全） | **参照式速率**（自然分布判错多少） |
| 需要对抗 agent | **是**（hacker 角色） | 否 | 否 |
| 成本 | **$5,000 / 48h / 8×H200** | **1,100+ 审计师小时** | 边际 **0.35 ms/题**，零人工标注 |
| FPR（误接受） | 16% 环境 / 75% 轨迹 | 未报告 | 逐臂 + CI |
| FNR（误拒） | 仅代理量，且有选择偏差 | 未报告 | 逐臂 + CI |
| 难度轴 | **无**（自陈） | **无**（自陈，且拒绝把领域差当难度） | 4 档 assertion + 旋钮（F4 已验收） |
| 参照真值来源 | 攻击者构造 | CPA 专家逐底稿 + 高级审计师裁决 | **构造性 oracle（差分隔离）** |
| 能否随难度重造 | 否（固定任务集） | 否（每档都要专家） | **是**（参数化） |
| RL 后果 | **未做实验**，仅论述 | 未涉及 | 解析 + 待跑 verl |

### 3.2 三个被反复问到的空白，现在可以精确表述

**空白 A：两种估计量从未在同一张表上比较过**

| 域 | 攻击式下界 | 参照式速率 | 倍数差 |
|---|---|---|---|
| terminal / coding | 16% | 未测 | — |
| 金融审计 | 未测 | **95%–100% FPR**（FinVerBench，9/14 run） | — |
| 会计审计 | 未测 | 未测 | — |

⇒ 攻击式下界与参照式速率**不是同一个量**：前者是"给定预算下最强攻击者能钻的空子数"
（**下界**，因为攻击不完备）；后者是"真实分布上的判错率"（**点估计**，因为参照可构造）。
**它们相差 6 倍以上，且没有任何论文同时报过这两个数。**
⇒ 若我们的会计域参照式 FPR 也落在高位，就构成一个**可直接检验的悖论**：
**benchmark 宣称可解的题，其中有多少是被 verifier 放过去的？**

**空白 B：误拒（FNR）至今没有干净的测量**

三篇都承认或暴露这个问题，但都不干净：
- Zhong：代理量 + precheck 选择偏差（100→77），偏差方向恰好掩盖难任务上的误拒；
- FinancialAuditBench：未报告；
- Bercovich 指南：只提出"real difficulty is conceptual, not environmental"，无测量。

⇒ **FNR 侧的干净测量本身就是可发表的空缺**，且我们有构造性参照这一独门手段。

**空白 C：难度轴在两个最大规模的工作里都被显式放弃**

- Zhong：无难度变量，precheck 只用于排除。
- FinancialAuditBench：**明确声明领域间通过率差异不是难度**，因为同时混杂检索复杂度、
  格式、第三方证据可得性、rubric 点数。

⇒ **"把难度从其他混杂因素里分离出来再测误差"这件事，目前没有一篇做。**
⇒ 而我们的 F4 验收（7/7 oracle 无死代码、主算子签名 4/4 分离）**正是前置条件本身**。

### 3.3 我们仍未获得的东西（诚实边界）

- **没有与 Zhong 的 hacker–fixer loop 做过正面对比实验**，他们的数据集是公开的，
  但本机无 forge，coding 域复现受阻。
- **没有 FinancialAuditBench 的 re-scoring 结果**。它的任务是基于 xlsx keyed rubric 的
  工作底稿，我们的构造性 oracle 面向复式记账账套，**不能直接套用**。
  ⇒ 跨基准 re-scoring 只能作为未来工作，现在不能写进贡献。
- **我们只有 2 个 LLM arm 的实测**（flash / pro），金融域 11 模型、审计域 11 模型都是对照。
- **A0（4 档 × ≥6 模型，约 $8–12）仍未跑**，难度曲线目前一个点都没有。

## 4. 新方向定稿 v6

### 4.1 一句话立论

> **verifier 的误差率现在有两种互不相容的估算法：攻击搜索给出的是下界，参照比较给出的是
> 速率。我们用构造性参照把后者做成零人工标注的曲线，并用它解释前者在金融审计域为何
> 低估一个数量级。**

- 这**不再**是「第一个测 verifier」——那已被 2606.08960 占。
- 这**不再**是「第一个做审计域 benchmark」——那已被 2609.32835 占，且它做得比我们扎实。
- 这**是**「第一个把两种估计量放在同一坐标里，并给出差异机制」。

### 4.2 三条贡献与杀死它们的数字

| # | 贡献 | 什么数字能杀死它 |
|---|---|---|
| **C1** | 攻击式下界与参照式速率的**系统性对照** | 若我们的会计域 FPR 落在低位（如 <10%），则「低估一个数量级」的说法崩塌，v6 立论退回 v5 |
| **C2** | **难度依赖的 verifier 误差曲线**（F4 已验收前置） | 若 4 档的 FPR 曲线无单调性或被算子强度混淆，则「难度是混淆变量」不成立，贡献降为 case study |
| **C3** | **verifier 误拒的干净测量**（补 2606.08960 的选择偏差） | 若构造性参照无法给出误拒的可信区间，则 C3 死 |

⚠️ **C1 是单点依赖**：它要求我们在会计域的**干净账套上 FPR 很高**。
这个假设有先验支持（S1 实测 pro FPR=0.800、FinVerBench 95–100%），
**但从未在合成账套上被系统测过**。⇒ **A0 不只是"花钱买曲线"，它同时是 C1 的生死判据。**

### 4.3 RQ 重写

| RQ | 内容 | 现状 |
|---|---|---|
| **RQ1** | 零人工标注下，判分器的 FNR/FPR 随难度（4 档 assertion）的形状是什么？ | 🔴 未跑，A0 约 $8–12 |
| **RQ2** | 攻击式下界与参照式速率差多少倍？差异能否由「攻击不完备性」解释？ | 🔴 未做，依赖 RQ1 |
| **RQ3** | 用构造性参照测出的误拒，与 adversarial hardening 报告的 +10.9pp 是否一致？ | 🟡 需 coding 域，本机无 forge |

### 4.4 叙事顺序（承接 v4 的三张牌，但换了顺序）

1. **先讲监管追问**（PCAOB journal-entry testing 检查缺陷，证据强度中）——
   准则要的是可辩护的过程，不是正确的结果。
2. **再讲 2606.08960 的 16%** —— 它证明 verifier 确实会被钻，
   但它是**下界**、**要 $5,000**、**只在 coding 域**。⇒ 我们的方法论是同一问题的另一侧。
3. **再讲 FinancialAuditBench 的 69.17% → 44.44%** —— 它证明 agent 在审计域能做事，
   但它自陈 rubric 外错误不计分，**且未报告 grader 的误报率**。
4. **收在构造性参照**：把这两者都缺的 (FNR, FPR, J, CI) 用毫秒级、零人工标注算出来，
   并沿难度给出曲线。

**两张牌的地位变化**：
- **「题目可再生」从卖点降为可行性前提**。FinancialAuditBench 用 1,100 小时证明
  专家构造不可扩展 ⇒ 可再生不是我们的功劳，是**唯一可行的路**。
  ⚠️ 对外必须如实说，不能把它当创新。
- **「难度连续可调」从卖点升为 C2 的技术前提**。两个对手都放弃难度轴，
  这个空白比 v5 认定的更值钱，但**必须配 F4 验收数字**（0/600 误报、4/4 签名分离、
  6/6 两两可区分、7/7 无死代码），否则等于没测。

## 6. 待你判断的四件事

1. **是否接受 C1（两种估计量对照）作为主命题？** 它的全部重量压在「会计域干净账套
   FPR 很高」这个**尚未测过的假设**上。若这个假设不成立，v6 立论会退回 v5。
2. **是否接受把「题目可再生」从卖点降为前提？** 1,100 小时的对照让这更像必然而非创新。
3. **是否要接 Terminal Wrench 做 coding 域的 FNR 对照？** 数据公开、无难度标签，
   但本机无 forge ⇒ 只能做静态分析，不能跑 agent。
4. **A0 是否改成「先跑 FPR 高位验证再跑全曲线」？** 这样一个 $2–3 的小实验就能先
   判定 C1 生死，避免 $8–12 白花。**我建议改。**
