## 2. 立论重构：从"能不能造"改成"oracle 从何而来"

### 2.1 核心洞察：可验证性有三种来源，是一个**光谱**不是布尔

现有所有工作都在做"造出可验证任务"，但**它们造验证信号的方式完全不同**。这个分类本身没有人明确做过——这是我们能占的位置。

| 类 | oracle 从哪来 | 代表 | 特征 | 局限 |
|---|---|---|---|---|
| **A 类 · 过程执行型** | **任务本身定义成功**，跑一遍看终态 | CUA-Gym、SPYRL、Centific | 任务=过程，终态=答案 | 每个任务要单独设计 reward；reward 好不好只能靠 LLM 投票/rollout 过滤 |
| **B 类 · 抽取型** | 从已有语料**挖**一段当答案 | Golden Goose、Self-Instruct 系 | 免费、规模化 | 抽错=答案错；只测识别不测推理；本质是降级成 MCQ |
| **C 类 · 领域先验型** | **oracle 独立于任务存在**，由领域不变量定义 | **我们** | 见下三条 | 前提是领域真有可执行不变量 |

### 2.2 C 类独有的三条性质（这才是我们的贡献）

> **C 类的 verifier 不是为这道题造的，是领域里本来就有的。** 由此得到三条 A/B 类都不具备的性质：

**① oracle 复杂度与任务复杂度解耦**
一个会计恒等式 oracle 可以判任意多个账套任务（10³–10⁶ 量级）。
> A 类：每题一个 reward function，成本随题数线性增长。
> B 类：每题一个抽取，成本线性增长。

**② 调难度时 oracle 不变**
注入参数 θ 变（跨期→跨表→组合手法），**oracle 一行不改**。
> A 类：改难度常常要改 reward——因为"难"和"终态变了"绑在一起。
> 这直接对应我们在代码域已经实测到的现象：**难度旋钮对已饱和题无效甚至反向**（sample-0002 从 0.385 升到 0.565）。
> C 类是把难度参数化和 oracle **解耦**的唯一一类。

**③ oracle 的正确性可以被独立审计**
审计师能验证"资产=负债+权益"这条规则写对了没有，而且**能验证我们的注入是不是真的只破坏了这一条**（差分隔离，见 §3.2）。
> A 类：Discriminator 是 LLM 写的——**谁来审它？** CUA-Gym 用两道过滤缓解，但那是启发式，不是证明。
> B 类：抽取正确性无法审计，只能抽样估计。

### 2.3 一句话主张（替换 v2）

> **可验证性不是一个布尔值，而是一个有来源的光谱。我们研究 C 类——领域先验型可验证性：
> 在没有天然 oracle 的领域，注入式任务合成提供一个 verifier，其正确性由领域不变量与差分隔离共同保证，
> 且复杂度不随题数增长、难度参数化与 oracle 解耦。**
>
> 验证场：审计与财务报告（第一批）。

**为什么这个定位比 v2 硬**：它不是"我们也能造 verifier"（三个人已经这么说了），
而是**"我们第一次把 oracle 的来源分了类，并指出 C 类的三条性质是可检验的"**——
这是一条分析 + 方法的主张，别人得写实验来反驳，而不是一句话就能 rebuttal 掉。

### 3.1 E0 的设计（必须做，且要诚实设计）

**不能自证。** 做法：
1. 我们随机抽 50 个注入样本，输出 `(task, verifier 判定, 我们声称的 label)`。
2. **3 名审计师**（甲方渠道）**盲审**：只看账套，不看我们的 label，独立指出舞弊位置。
3. 算三方一致率：verifier 判定 / 专家判定 / 我们的 label。
4. **如实报告**，包括不一致的样本类型。

**风险预判（写进论文的 threats to validity）**：
- 专家可能看得出"这是合成的"而给出不同判断 → 这是**真实有效性威胁**，必须报告。
- E0 的成本约 20–30 人天。**这就是 FAB 花 1100 小时的对应物**——我们要证明这是**必要且充分的最小量**。

### 3.2 P2 性质现在有了具体形式：差分隔离证书（DIC）

C 类的 oracle 正确性由两条合起来保证，写成可核验的形式：

> **差分隔离证书（differential isolation certificate）**
> 对 seed `s` 与注入结果 `t(s)`，跑一遍 oracle 集合 `O = {o₁..oₙ}`：
> - `violated  = { oᵢ | oᵢ(s)=1 ∧ oᵢ(t(s))=0 }` —— 实际被破坏的不变量
> - `declared  = { oᵢ | 算子 t 声明应破坏 }`
> - `unexpected = violated \ declared` —— **声明外也被破坏（注入污染）**
> - `missing    = declared \ violated` —— **声明了却没破坏（注入无效）**
>
> **证书有效 ⟺ `unexpected = ∅` 且 `missing = ∅`**

> ⚠️ **判据是被实测修正过的，不是设计出来的。** 详见 §4.7。

### 3.3 ✅ 已实测：DIC 机制可行（`vts/audit_core.py`）

**这是本方案里第一个被真实数据验证的部分，不是设想。**

| 指标 | 实测结果 |
|---|---|
| 种子账套自检 | **3200/3200 通过**（200 份 × 4 期 × 4 oracle） |
| DIC 有效率 | **800/800 = 100.00%**（4 算子 × 200 seed） |
| DIC 单样本耗时 | **0.64 ms**（含注入 + 4 个 oracle 前后各跑一遍） |

**这三条数字是论文 Table 1 的内容**，也是回应 CUA-Gym 的第一手证据。

### 4.4 会计 oracle（已实现 4 条，纯函数，s → {0,1}）

| oracle | 形式 | 破坏它的手法 | 会计依据 |
|---|---|---|---|
| `o_equation` | `资产 − 抵减项 = 负债 + 权益` | 单边改报表（账外账的现金部分） | 会计恒等式 |
| `o_tie_detail` | 报表数 = 明细账结转后 | **几乎所有注入** | 账证相符 |
| `o_rollforward` | 期末 = 上期 + 本期发生额 | 跨期调节、资本化 | 递推关系 |

## 4.7 ✅ 实测发现：两条反直觉的会计结论（写进 paper 的方法节）

这两条是跑 DIC 才发现的，**推翻了方案 v3 初稿里的两个假设**，而且都是原创发现。

### 发现 1：「每个手法恰好破坏一条 oracle」在会计域**不成立**

原方案 §3.2 要求 `|violated| == 1`。实测发现：

> **改动报表期末数，必然同时破坏两条 oracle** ——
> `o_tie_detail`（表账一致）和 `o_rollforward`（递推），
> 因为报表数同时被这两条约束。
> 只有当改动**同时落在资产与权益两侧**时才额外破坏 `o_equation`。

| 算子 | 实测违反集 | 声明是否匹配 |
|---|---|---|
| 账外账 / 折旧不足 / 费用资本化 | `{tie_detail, rollforward}` | ✅ |
| 跨期调节 | `{tie_detail, rollforward}` | ✅ |

**修正后的判据**：`unexpected = ∅` 且 `missing = ∅`，
**允许连带破坏，但不允许声明外的意外项，也不允许声明了却没破**。

> **这本身就是一条可发表的观察**：可验证性的"干净"不等于"单一"，
> 而"什么是意外"必须由领域知识（算子声明）给出，不能由集合相等推断。
> A 类的 LLM judge 连这个问题都问不出来。

### 发现 2：**费用资本化与折旧不足在会计上并不破坏会计恒等式**

我原以为这两类手法必然破坏 `资产 = 负债 + 权益`。**实测是错的**：

| 注入 | 资产变化 | 权益变化 | 恒等式差 | 实际破坏 |
|---|---|---|---|---|
| 费用资本化 | +amt | +amt | **0** | 表账一致、递推 |
| 折旧计提不足 | 累计折旧 +amt | +amt | **0** | 表账一致、递推 |

**这是会计上正确的**：把费用记成资产，资产与权益同增，恒等式仍然成立。
舞弊的可检测性来自**明细账与报表的账证不符**，而不是"报表看起来不平衡"。

> 🔑 **这条发现恰恰是 C 类 oracle 存在的理由。**
> 如果只用"资产 ≠ 负债 + 权益"这种朴素判据，这两类**最常见的财务舞弊会全部漏检**。
> 必须用**会计意义上的**约束（表账一致、递推、政策区间），而不是"看起来不平"。
>
> **这正面回应了 FinRule-Bench 那条批评**——
> 他们批评"在合成破坏数据上做异常检测"，我们的回答是：
> **判据不是"有没有不平"，而是"违反了哪条会计约束"**，
> 而且这套判据是准则给的、审稿人可自行查验的。

### 实测数据（论文 Table 1）

| 指标 | 值 |
|---|---|
| 种子账套自检 | 3200/3200（200 × 4 期 × 4 oracle） |
| DIC 有效率 | 800/800 = **100.00%**（4 算子 × 200 seed） |
| DIC 单样本耗时 | **0.64 ms** |
| θ 改变时违反集 | **完全不变**（性质②确认） |
| DIC 抓到的污染样本 | 早期版本在 100 seed 中抓到 1 例（`o_equation` 意外破坏），**修正金额上界后消失** |

> 最后一行值得注意：**DIC 真的抓出过污染**。

> 导致注入金额与账套量级脱节 → 恒等式被意外破坏 → DIC 报 `unexpected = {o_equation}`。
