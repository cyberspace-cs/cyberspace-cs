## 一、8 个一级页面

飞书桌面端左侧是一根 68px 深色图标栏，把产品切成互不干扰的空间。关键判断：**只有「消息」是实时流，其余都是结构化数据页**。

|---|---|---|---|---|
| 01 | 消息 | 图标栏 68 / 会话列表 300 / 聊天区 / 工具条 40 | tab（全部·@我·未读·云文档）、会话行 64px、气泡、引用块 | **已实现（简化版）** |
| 02 | 日历 | 迷你月历 + 日历分组 + 周视图时间轴 | 新建日程浮层、忙碌/空闲、会议室 | 未实现 |

## 二、消息页拆解（唯一值得对标的页面）

| 区域 | 规格 |
|---|---|
| 分栏 | 图标栏 68px（#2B2F36，图标 24 + 文字 10）→ 会话列表 300px → 聊天区 → 工具条 40px |
| 顶部标题栏 | 高 48px，深色延续；居中超宽搜索框（跨人/群/消息/文档） |
| 会话列表顶部 | 五个 tab：全部 / @我 1 / 未读 4 / 云文档 / 更多；**@我与未读是两套独立计数** |
| 会话行 | 高 64px，头像 40px，红点胶囊（>99 显示 99+），名称 14/500，时间 12/#8F959E，第二行灰字摘要；选中 #E1EAFF，hover #F2F3F5 |
| 消息气泡 | 他人 #F2F3F5 / 自己 #D6E4FF，圆角 6px；可嵌引用块（左侧竖线 + 被引内容 + 引用人） |
| 输入区 | 工具栏在输入框**右侧**：Aa / 表情 / @ / 剪贴板 / + / 全屏 / 发送；聚焦时 1px 蓝框 |

## 三、设计令牌（直接对齐 app.css）

| 令牌 | 值 | 令牌 | 值 |
|---|---|---|---|
| 品牌蓝 | `#3370FF` | 主文字 | `#1F2329` |
| 次文字 | `#646A73` | 弱文字 | `#8F959E` |
| 图标栏 | `#2B2F36` | 页面底 | `#F5F6F7` |
| 他人气泡 | `#F2F3F5` | 自己气泡 | `#D6E4FF` |
| 会话选中 | `#E1EAFF` | 未读红点 | `#F54A45` |
| 分割线 | `#DEE0E3` | 气泡/卡片圆角 | 6px / 12px |

尺寸：图标栏 68 / 会话列表 300 / 会话行 64 / 头像 40 / 正文 14 / 时间 12 / 行内留白 16。

飞书**不用大圆角、不用彩色渐变**，靠留白和 1px 细线分层。我们的 8px 圆角略大，气泡用 6px 更贴近。

## 四、后端接口缺口

现有 9 个：`conversations`、`users`、`members`、`messages`、`receipt`、`seed`、`seed_big`、`healthz`、`ws`。
只够跑通「发消息 + 已读」。以下是补齐飞书同级界面需要的 19 个。

### P0 · 不补就跑不通真实场景（4）

| 接口 | 用途 | 为什么是 P0 |
|---|---|---|
| `POST /api/auth/login` | uid → token | 现在 `?uid=3001` 明文传，改数字即可冒充 |
| `POST /api/conversations` | 建单聊/群聊 | 只能靠 `/api/seed` 造数据 |
| `GET /api/messages?after_seq=` | 增量补拉 | 只有 `before_seq` 往前翻，重连拿不到漏的消息 |
| `POST /api/conversations/{id}/members` | 加人/踢人/退群 | 群成员固定，无法运营 |

### P1 · 界面上肉眼可见（10）

| 接口 | 用途 | 对应界面元素 |
|---|---|---|
| `GET /api/unread/summary?uid=` | 总未读 / 会话数 / @我数 | 图标栏红点「49」+ tab「未读 4 · @我 1」 |
| `GET /api/search?q=&scope=` | 跨消息/联系人/会话搜索 | 标题栏居中搜索框 |
| `GET /api/mentions?uid=` | @我的消息（消息带 at_uids） | 「@我 1」tab |
| `POST /api/conversations/{id}/settings` | 置顶 / 免打扰 / 标记未读 | 会话右键菜单 |
| `POST /api/messages/{id}/recall` | 2 分钟内撤回 | 消息「…」菜单 |
| `POST /api/messages/{id}/reaction` | 表情回应 | 气泡下方表情条 |
| `POST /api/upload` | 图片/文件上传 | 输入框右侧 `+` |
| `GET /api/user/{uid}` | 用户详情：部门/职位/邮箱 | 头像名片 |
| `GET /api/org/tree` | 组织架构树 | 通讯录页 |
| `WS send: reply_to` | 引用回复 | 气泡内引用块 |

### P2 · 有则更好（5）

| 接口 | 用途 |
|---|---|
| `WS typing / presence` | 正在输入、在线状态 |
| `GET /api/receipt?offset=&limit=` | 回执名单分页（500 人群必须） |
| `GET /api/read/state?uid=` | 多端已读位置同步 |
| `POST /api/messages/forward` | 转发 / 合并转发 |
| `GET /api/notifications` | 系统通知中心 |

## 五、结论

存储层（扩散读 + 水位线 + 单条回执）是对的，也够用。真正缺的是两侧：

- **写入侧的会话管理**：建会话、改成员、撤回、上传
- **读取侧的聚合查询**：搜索、@我、未读汇总、回执分页

存储模型不用动，加接口即可。

落地顺序建议：① 鉴权 + 建会话 + 增量拉（把假的变真的）→ ② 未读汇总 + @我 + 置顶（补全会话列表）→ ③ 上传 + 引用 + 表情 + 撤回（把消息做实）→ ④ 搜索 + 名片 + 通讯录。
